# 使用 Redis 扩展自主数据源获取

阶段 5A.5 将 RSSHub 上游的缓存、每路由限流和并发容量协调放入独立 Redis。RSSHub 使用 DB 0，
`feed-supplier` 使用 DB 1；两者的状态都可从权威路由配置和上游响应重建。生产 Redis 不暴露宿主端口，
关闭 RDB/AOF，使用 `noeviction` 和内存上限运行。达到上限时供给端失败关闭，不能通过淘汰活动租约绕过
容量保护。

供给端只缓存有界的成功响应，并以逻辑 URL 的 SHA-256 作为 key。同进程相同逻辑 URL 和相同条件请求头的
cache miss 被合并。固定窗口限流用原子 Lua 计数器实现；全局与每路由并发使用带过期时间的 Redis sorted-set
租约，避免进程崩溃后永久占用容量。精确路由、目录路由和兼容地址使用不同的稳定策略 key。

缓存命中不占用上游配额；连接测试绕过响应缓存但必须获取限流和并发租约。生产配置缺少 Redis 时拒绝启动，
运行中 Redis 协调失败返回 503 并使 readiness 失败，而不是退化为各副本互不一致的内存控制。普通 RSS 与
页面变化调度不使用这些配额。

这一决策使多副本共享缓存、限流和容量状态，并让缓存丢失保持无损。代价是限流采用固定窗口而非平滑算法，
并发 cache miss 的请求合并只在单进程内生效；若真实数据灰度表明跨副本缓存击穿成为问题，再引入带有界
等待的分布式 single-flight，不在当前切片中提前增加复杂度。
