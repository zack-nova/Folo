# 每日简报作为 Folo 任务报告交付

## 背景

自动评估上线后（ADR-0035），每条新条目都有当前评估：三维评分、综合分、推荐理由和 Taxonomy 分类。实例
每天新增几百条，其中综合分达到精选门槛（≥70）的约 80–110 条，集中在科技产业、国际局势和财经商业。
精选视图能按排序分浏览，但所有者仍要自己逐条翻；需要的是每天早上一份成文的简报：按主题归纳过去一天
值得看的内容，每个要点能直接点回原文。

Folo 客户端已经有这种形态的功能。AI 任务（`/ai/task`）按计划运行一段提示词，结果写成一个 AI 对话会话，
会话 ID 以 `ai-task-{taskId}` 开头，在 AI 页面的"任务报告"里按未读提示。客户端的任务设置、计划选择、
报告列表和 Markdown 渲染都现成，而且报告里的 `[文字](entry_<24位十六进制>)` 链接会直接打开条目预览，
自有服务的条目 ID 正好是这个格式。能力契约里已经有 `ai.scheduled_tasks`（本地提供方，未实现）。

缺口在服务端和两处客户端门控：

- 自有服务没有 `/ai/task` 和 `/ai/chat-sessions` 的任何路由，所有 `/ai*` 未知路径都返回 `ai.chat` 未实现。
- AI 面板和 `/ai` 页面由状态配置的 `AI_CHAT_ENABLED` 控制，自有服务返回 `false`，因为通用 AI 对话
  （`POST /ai/chat`、附件、模型配置）不在实现范围内。
- 设置页只在没有宣告 `ai.provider_configuration` 时显示"AI 任务"一节；自有服务宣告了它，所以这一节被隐藏。

## 决策

### 复用 AI 任务和任务报告，不做通用对话

- 实现 `ai.scheduled_tasks`：`/ai/task` 的列表、读取、创建、更新、删除和试运行，响应形状与 SDK 的 `AITask`
  一致（`lastRunAt`、`nextRunAt`、`runCount`、`lastResult`、`lastError` 都返回，客户端目前不显示）。
- 新增能力 `ai.task_reports`：`/ai/chat-sessions` 的列表、读取、消息、标记已读、未读列表、改名和删除，
  只覆盖任务产生的会话。这些 API 从 `ai.chat` 的清单移到这里；`ai.chat` 仍为不可用。
- `GET /ai/chat/:chatId/stream` 对任务会话返回 204（"没有进行中的流"），否则客户端打开任何会话都会先把它
  标成错误。`POST /ai/chat` 继续返回 `ai.chat` 未实现。
- 简报也是一个任务：所有者在设置里建一个每天早上运行的任务，提示词写简报的要求（侧重、篇幅、语气）。
  任务数沿用客户端上限 10 个，所以以后可以再建工会通知之类的专题简报，不需要新功能。

### 客户端改动保持最小，只按能力放开

- 设置页：宣告 `ai.scheduled_tasks` 时显示"AI 任务"一节，不再只看 `ai.provider_configuration`。
- AI 页面与入口：宣告 `ai.task_reports` 而 `AI_CHAT_ENABLED` 为假时进入"仅报告"模式。`/ai` 页面、
  个人菜单入口、任务项的"查看报告"和试运行可以打开会话；输入框、新建对话、模型选择隐藏，历史列表只列
  任务会话。`AI_CHAT_ENABLED` 为真时行为与上游完全相同。
- 任务弹窗：宣告 `ai.task_reports` 时隐藏邮件通知选项（见下文）。
- 改动只放在能力判断和 AI 页面的显示分支上，便于以后同步上游时解决冲突。

### 任务与报告的存储

- `ai_tasks`：所有者、名称、提示词、是否启用、计划（原样保存客户端的 schedule JSON）、选项、
  `next_run_at`、`last_run_at`、`run_count`、`last_result`、`last_error`。
- `ai_task_runs`：每次运行一行，`(task_id, scheduled_for)` 唯一，记录窗口起止、候选数、状态、尝试次数、
  错误、token 用量和产出的会话 ID。唯一键保证重启或多次触发不会重复生成同一期。
- `ai_chat_sessions` 与 `ai_chat_messages`：字段按 SDK 形状保存（`chatId`、`title`、`lastSeenAt`；消息的
  `role`、`messageParts`、`status`、时间）。每次运行一个会话，`chatId` 为 `ai-task-{taskId}-{runId}`，
  标题为"任务名 · 日期"。会话里只有一条 assistant 消息，内容是一段 `text` part。
- 删除任务不删除已有报告；报告由所有者在界面里删除，服务端不自动清理。

### 计划与运行

- 支持客户端的全部四种计划（一次、每天、每周、每月）。客户端用浏览器本地时间生成 ISO 字符串（UTC），
  没有时区字段；服务端只取 `timeOfDay` 的 UTC 时和分，所以北京时间 07:30 存为 UTC 23:30，跨夏令时的
  时区会偏一小时，当前部署不受影响。
- 一个独立的调度器每分钟检查到期任务，用 `next_run_at <= now` 加行锁领取，先插入 `ai_task_runs` 再算下一次
  `next_run_at`。服务停机错过的运行只补最近一期，更早的跳过并在运行记录里标为 `skipped`。
- 失败按 5、15、45 分钟退避重试，最多 3 次。最终失败也生成一个会话，内容是简短的失败说明和原因，因为
  客户端不显示 `lastError`，否则所有者看不到当天为什么没有简报。
- 试运行同步执行并返回 `{taskId, sessionId}`。它不推进计划，不计入 `run_count`，但同样写会话和运行记录
  （`kind=test`）。客户端试运行超时是 80 秒；超时时会话仍会生成，在报告列表里出现。

### 简报内容

- **候选**：窗口内首次导入（`inserted_at`）且有当前评估、综合分 ≥70 的条目。窗口是上一期成功运行的窗口
  终点到本次运行时刻；第一次运行或上一期失败时取一个计划周期（每天 24 小时，每周 7 天，每月按上月同日）。
  用导入时间而不是发布时间，迟到的条目不会漏，也不会两期重复。
- **排序与截断**：按精选排序分取前 60 条，每个主分类最多 20 条，避免快讯流挤掉其他主题。运行记录写明
  候选总数、入选数和窗口内尚未评估的条目数，报告末尾附一行说明。
- **模型输入**：system 消息是简报指令、输出 schema 和当前画像快照；user 消息是任务提示词（从客户端的
  Lexical 编辑器 JSON 提取纯文本，提及节点取显示文字）和候选条目，每条带 `entry_id`、标题、来源名、订阅
  分类、主分类和标签、综合分、推荐理由，以及已有摘要或 300 字以内的正文摘录。条目整体声明为不可信数据，
  与评估提示词的做法相同。
- **模型输出**：JSON，形状如下。服务端校验 `entry_ids` 必须来自本次输入，丢弃无法对应的要点，再渲染成
  Markdown：每个要点后面附 `[来源名 · 标题](entry_…)` 链接。链接由服务端生成，模型不能编造条目或网址。
  回复不是合法 JSON，或者校验后没有任何要点，按失败处理并重试。

  ```json
  {
    "overview": "...",
    "sections": [{ "heading": "...", "points": [{ "text": "...", "entry_ids": ["..."] }] }]
  }
  ```

- **提供方**：经 `AIProviderRouter` 解析，按所有者发起的工作对待（`ownerRequested: true`），所以 Codex
  在 `manual` 和 `all` 范围下都会接手，每期一次调用，计入 Codex 每日上限；没有 Codex 时用 API 提供方。

### 可见性

- `/metrics` 增加 `folo_ai_task_runs_total{kind="scheduled|test", status="succeeded|failed|skipped"}` 和
  简报 token 计数。
- 运维页"需要处理"增加一项：启用中的任务最近一期最终失败，或 `next_run_at` 已过去超过一小时仍未运行。

### 邮件通知

客户端可以勾选邮件通知，但自有服务没有发信能力。带 `notifyChannels: ["email"]` 的创建和更新返回 400
（`notify_channel_unsupported`），客户端相应隐藏这个选项。

## 未采用的方案

- **把简报作为时间线里一个私有"简报"源的条目：** 已读未读、手机网页阅读都现成，但主方案明确"不创建
  假聚合 Feed"，而且合成条目会进入评估、精选和同步日志，需要处处排除。任务报告是 Folo 本来就有的
  产物形态。
- **打开 `AI_CHAT_ENABLED`，实现完整的 AI 对话：** 范围远大于简报（流式对话、工具调用、附件、模型配置），
  只为看报告不值得；以后要做对话时，`ai.task_reports` 的存储可以直接沿用。
- **按分类把窗口内全部条目交给模型归纳：** 一天几百条，多数是低分快讯，调用量大且容易淹没重点。复用
  已有评估做筛选，模型只负责归纳和成文。
- **复用 `processing_jobs` 运行任务：** 处理作业以条目为单位（有 `entry_id`、内容版本和评估快照），简报
  是按计划、跨条目的运行，硬塞进去会让作业表的约束和清理规则都要开例外。
- **让模型直接写 Markdown 和链接：** 无法保证链接指向真实条目；结构化输出加服务端渲染可以校验每个引用。

## 影响

- 客户端在能力门控下多了一种"仅报告"的 AI 页面模式，设置页和任务弹窗各有一个条件变化；上游同步时
  需要留意这三处。
- 新增四张表和一个每分钟运行的调度器；每天一期简报是一次模型调用，输入约 60 条条目的元数据。
- 手机浏览器上 `/ai` 页面能否正常阅读报告需要在实现时验证；不行的话再决定是否给报告加一个轻量的
  只读页面。
- 简报质量依赖评估质量；评分偏差会直接体现在入选条目上，复核打分时一并看简报。
