# 自动评估按批调用模型

## 背景

阶段 2 的评估流程是一篇条目一次模型调用（`stage-2-ai-processing-backend.md`）。这个设计在按 token 计费的
API 提供方下是合理的：画像和 Taxonomy 放在 system 消息里，连续调用共享前缀缓存，每条只为自己的正文付费。

Codex CLI 作为提供方接入后（PR #30、#31），成本结构变了。它按次运行完整的代理：每次调用约 1.4 万输入
token，其中 1.2 万是指令和缓存命中的固定开销，条目本身只占很小一部分；而且 ChatGPT 套餐限制的是调用频率，
不是 token。实例当前每天新增约 600 条待评估条目，多数是 X 帖子和通讯社短讯（100–500 字），逐条调用意味着
每天几百次完整代理运行，会撞上套餐的速率限制，也把 Codex 限制在"只接所有者手动发起的工作"。

## 决策

### 自动评估合批，手动评估和重试保持单条

- 工作线程一次领取最多 `PROCESSING_BATCH_SIZE`（默认 10）个待处理 Job，按所有者、画像快照和 Taxonomy 快照
  分组，同组的条目在一次模型调用中评估。
- 只有自动入队的 Job 在第一次尝试时参与合批。所有者发起的重评（`force_rerun`）保持原来的单条提示词；
  任何第二次及以后的尝试都单条执行，所以一批里的坏回复不会反复拖累同批的其他条目。
- 一批的条目纯文本总量不超过 `PROCESSING_BATCH_MAX_CHARS`（默认 40000 字符）。超出的条目顺延到下一批，
  长文不会把整批的上下文挤满。只剩一条时直接走单条路径。

### 提示词与回复

- 合批的 system 消息只换指令段（"评估一批条目，返回 `{"evaluations": [...]}`，每项带 `entry_id`"），输出
  schema、画像和 Taxonomy 的序列化与单条完全相同，所以同一配置下所有批次仍共享字节相同的前缀。指令明确
  要求逐条独立判断，批只是传输方式。
- user 消息是 `{"entries": [{entry_id, entry, source}, ...]}`，每项与单条请求的 `entry`、`source` 相同；整个
  文档仍声明为不可信数据。
- 回复按 `entry_id` 对应到 Job。缺失或形状不对的条目单独失败（`invalid_ai_response`），进入现有的指数退避
  重试，并在重试时单条执行；多余或重复的 `entry_id` 忽略。整条回复不是合法 JSON 时整批失败，同样各自重试。
- 综合分公式、评估记录的不可变性、摘要保存和幂等键都不变。评估记录的 `details` 增加 `batch.size`，token
  用量记录的是整批的用量，以便区分。

### 可见性

- `/metrics` 增加 `folo_ai_evaluation_calls_total{kind="single|batch|batched"}`：单条调用数、合批调用数和
  经合批评估的条目数。配合已有的 token 计数可以验证合批是否生效。
- 评估 token 计数按调用累计一次，不按条目重复计。

### 与 Codex 的关系

合批之后，Codex 可以改为处理全部作业（`AI_CODEX_SCOPE=all`）：每天约 600 条按 10 条一批是几十次调用，
在每日上限和套餐速率之内；每日上限按调用计数，不受合批影响。这是部署配置，不是代码行为。

## 未采用的方案

- **在数据库层面增加"领取一批"的查询：** 现有的逐个领取已经是独立事务并带 `SKIP LOCKED`，在服务层连续
  领取再分组不需要迁移，也不改变"同一条目同一目的最多运行一个 Job"的约束。
- **只对 Codex 提供方合批：** 合批对 API 提供方同样减少调用次数和输出格式开销，而且评估逻辑不应知道提供方
  是谁。提供方差异只体现在路由（ADR 之外的 `AIProviderRouter`）。
- **整批失败时立即把每条拆开重试：** 会让一次坏回复在同一轮里再发 N 次请求。沿用退避重试，并在重试时自动
  单条，行为可预期且不需要新的状态。
- **在批内让模型比较排序：** 会让分数依赖同批的其他条目，批之间不可比。指令要求独立判断。

## 影响

- 自动评估的模型调用次数下降约一个数量级；单条路径和手动重评的行为不变。
- 一批中的条目共享同一次调用的 token 用量记录，按条目看用量时需要除以 `batch.size`。
- 分数一致性依赖模型是否真的逐条独立判断；试运行期间用 `/metrics` 和抽样对比单条评估确认。
