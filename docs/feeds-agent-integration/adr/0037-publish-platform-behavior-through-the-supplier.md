# 平台行为作为供给端的行为源发布

## 背景

所有者想把自己在各平台上的个人动作逐步接进阅读器，先从 B 站开始。旧 Feeds Agent 的设计（`feeds-agent-CONTEXT.md`
的“平台行为同步”）已经定下第一版范围：B 站新关注的 UP 主和新收藏的视频；首次同步只记基线，之后只把新增的关注
和收藏变成卡片；一次同步里的新关注合成一张，新收藏一个视频一张；登录态只用凭据引用。ADR-0023 拆分核心和供给端时
把平台行为同步、快照和差分都划给供给端，并让核心把它们当作普通 Feed 条目，所以核心里原来的行为卡片界面和
“收集个人行为”按钮都已删除，这部分一直没有重新实现。

PersonalOS 的采集脚本（`personalos-collectors/bilibili`）在 2026-06 用浏览器 Cookie 做过一次全量导出：
关注 1871 个、收藏夹 24 个、去重收藏视频 709 个，验证了关注列表 `x/relation/followings`、收藏夹列表
`x/v3/fav/folder/created/list-all` 和收藏内容 `x/v3/fav/resource/list` 三个接口与字段。2026-10-22 不带 Cookie 实测：
关注列表返回 -101（未登录），收藏夹列表为空，匿名读取已不可用。

## 决策

### 一种新的来源：行为源

- 供给端新增 `behavior://<uuid>` 来源。一个行为源只看一个平台账号的一种动作（`follows` 或 `favorites`），账号和
  动作建好后不可修改，换账号就是新来源、新基线。
- 共用部分在 `PlatformBehaviorService`：建删改、试读、检查、基线、差分、失败退避、调度和 RSS 输出。平台差异只在
  `PlatformBehaviorAdapter` 里：读取当前列表（对象键、动作时间、对象快照），以及把新对象写成条目。接下一个平台
  只需新增一个适配器文件并登记平台名。
- 存储三张表：来源、见过的对象（含首次见到时的快照和发布它的条目）、已发布条目（不可修改）。条目 GUID 由对象键
  的哈希决定，重复检查不会重复发布。

### 只发布基线之后出现的对象

- 第一次成功检查只把读到的对象记为已见，并把检查时间记为基线，不发布条目。
- 之后的检查只发布“从没见过，且动作时间晚于基线”的对象；没见过但更早的对象只记下不发布。
  这条规则让只读最新几页的做法也安全：取消关注把旧关注挤上第一页、上次预算内没读完的收藏夹、超过读取页数的旧内容，
  都不会冒充新动作。B 站给出关注时间（`mtime`）和收藏时间（`fav_time`），所以规则可以直接用平台时间。
- 第一版不发布取消关注和取消收藏，也不保存消失的对象。

### 没有平台时间的列表先读完整基线

（2026-10-23 接入知乎时补充。）知乎的关注列表不给关注时间，上面的时间规则用不上：只读第一页记基线的话，取消关注会把
没见过的旧关注挤上第一页，冒充新动作。对这类列表：

- 基线必须读完整个列表才算完成；一次检查读不完时，来源记下读到的位置（`baseline_cursor`，迁移 010），15 分钟后接着读。
  完成之前检查结果为 `baseline_in_progress`，不发布任何条目。
- 基线完成后，每次只读最新几页，遇到已见过的对象就停（适配器通过 `known` 询问已见对象），没见过的就是新动作，以发现时间
  发布。取消关注只会让已见过的对象前移，不会产生误报。
- 适配器的试读（`test`）只读每个列表的第一页，避免为了预览读完整个列表。
- 抖音的关注和收藏同样没有可靠时间（2026-06 的 1830 条收藏导出里收藏时间全为空），接入时沿用这条规则。

### 抖音经 F2 边车读取

（2026-10-23 接入抖音时补充。）抖音网页接口要求 a_bogus 等签名，算法混淆且常变。所有者选择不在 TypeScript 里移植签名，
而是在 Mac mini 上加一个只在内部网络可达的 `douyin-reader` 容器，用维护中的 Python 库 F2 发请求：

- 供给端每页一次请求，把解密后的 Cookie、账号和游标交给边车；边车只返回需要的字段，不保存、不记录 Cookie，用独立令牌认证，
  并核对 Cookie 所属账号与来源账号一致，只能读所有者自己的列表。
- F2 按提交固定（`douyin-reader/requirements.txt`）。实测 F2 0.0.1.7 正式版读收藏会被抖音网关 403 拒绝（2026-08 起要求
  `x-tt-argus` 请求头），之后的提交已修复。抖音再改签名时升级 F2 提交即可，供给端不用改。
- 实测关注列表 `source_type=1` 按关注时间从新到旧，但每个账号没有关注时间（`create_time` 是账号注册时间）；收藏列表也只有作品
  发布时间。两者都按“没有平台时间的列表”处理。页间至少 3 秒。
- 边车用 Compose profile `douyin` 启动，只在读抖音的节点运行；未配置 `DOUYIN_READER_URL` 时供给端不提供抖音平台。

### 对平台克制地读

知乎的收藏夹列表带更新时间，实测与收藏夹里最新一条的收藏时间一致，所以基线之后只读变过的收藏夹，平时约 3 个请求
（所有者的 56 个收藏夹全读一遍要约 60 个）。其余规则与 B 站相同。

B 站：

- 只读配置的账号：关注列表最新一页（50），收藏夹列表加每个收藏夹最新一页（20）；只有整页都晚于上次检查时才翻页，
  每个列表最多 3 页。请求间隔默认 1 秒，一次检查最多 120 秒，读不完的收藏夹留到下次。默认 6 小时一次，最短 1 小时。
- -412 / -352 / -509 / -799 和 HTTP 412、429 视为风控，-101 视为登录失效，两者都至少 6 小时后再试。错误信息只写
  我们自己的说明和错误码，不转述响应正文。
- 匿名读取收藏夹列表为空时直接失败，而不是记下一个空基线：否则补上登录后，全部私密收藏都会被当作基线之前的
  旧对象，永远不发布。

### 登录态放在加密凭据库

- 行为源可以绑定一个供给端凭据（ADR-0026 的加密凭据库），值是 `SESSDATA` 或一整行 Cookie，只在请求时解密放进
  `Cookie` 头；拒绝多行值，避免头部注入。凭据用途报告把它列为该来源使用的登录。
- 管理接口只在管理员令牌下注册，不暴露给核心持有的管理令牌，因为行为源绑定的是个人登录。

### 与核心和读者的关系

- 核心不需要改动：同机核心可以订阅 `behavior://` 地址（经内部 Feed 路由），其他读者通过公开订阅链接读取；订阅预设
  也接受 `behavior://`。
- `/v1/providers` 暂不报告行为源：旧核心会拒绝未知的提供方 ID（见 ADR-0034 的教训）。
- 按节点分工，这类个人信息来源部署在 Mac mini 节点。

## 未采用的方案

- **用 RSSHub 的 B 站收藏夹、关注列表路由：** 最快，但关注列表会整份列出，做不到“只推新增、合并成一条”，也没有
  基线；每个平台的语义都要再补一层，不适合当后续平台的样板。
- **按快照差分判断新增（不看平台时间）：** 只读最新几页时，取消关注或预算截断都会让旧对象“出现”，必须读全量才
  安全；全量读取 1871 个关注、24 个收藏夹的请求量不符合克制读取的要求。
- **把行为卡片作为核心里的特殊条目类型：** ADR-0023 已决定核心只接收标准 Feed，专用展示以后需要时再经扩展契约
  进入核心。

## 影响

- 供给端多一个每分钟轮询的调度器和三张表；所有者需要自己在 B 站登录后填入 `SESSDATA`，并在过期时更新。
- 一次收藏检查约 25 个请求（1 个收藏夹列表加 24 个收藏夹），每天约 100 个；关注检查每天约 4 个。
- 以后接知乎、抖音、GitHub Star 等平台时，复用同一套表和服务；新平台各自确认动作时间是否可靠，没有可靠时间的平台
  要单独说明退化为发现时间后的取舍。
