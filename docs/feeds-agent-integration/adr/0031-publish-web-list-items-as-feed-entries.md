# 把网页列表条目逐条发布为 Feed Entry

阶段 5A.6 把旧 Feeds Agent 的 `generic-web-list` 与 `generic-json-list` 能力迁入 `feed-supplier`。政府公告、
高校通知等站点没有 RSS，但有稳定的列表页或列表 JSON。页面变化源（ADR-0027）只能把整个区域的变化合并为
一条消息，无法表达“列表新增了三条通知”，因此列表源使用独立的数据模型，而不是扩展页面变化状态机。

列表源使用 `weblist://<source-uuid>` 作为稳定 Feed 身份；目标 URL、选择器、JSON 路径、过滤规则、时区和
调度状态只存在供给端。每次检查抽取列表顶部最多 `maxItems` 个条目，以规范化 URL（或配置的 JSON ID）的
SHA-256 作为条目身份；从未见过的条目写入不可变的 `web_list_items`，并与来源状态在同一事务中提交。
首次检查发布当前列表中的全部条目，之后只发布新出现的条目。已发布条目不会因为列表标题或详情页变化而改写，
这与“新 RSS Entry 对应新消息”的主路径一致。

详情页抓取是可选步骤：只对新条目执行，结果经过白名单清洗后作为 `content:encoded`。详情失败或详情不是 HTML
（例如 PDF 附件）不会阻塞条目发布，条目仍以列表标题和链接进入 Folo，用户可以使用既有 Readability。
旧工具在详情失败时下次重试；新实现选择“先发布、不重试”，避免永久失效的详情页让新通知一直无法到达。

列表页、分页、meta refresh 与详情页全部经过与页面变化源相同的逐跳 SSRF 校验、超时、响应大小限制和字符集
识别（含 GBK/GB18030）。Folo 核心只读取供给端物化的 RSS，Feed 请求过程中不访问目标站点。普通 RSS、
`rsshub://` 和 `pagechange://` 的抓取、调度与导入语义保持不变。

第一版不支持 JavaScript 渲染、登录 Cookie、自定义请求头和 POST 请求；JSON 接口所需的查询参数直接写在
目标 URL 中。这些能力出现真实需求时再单独评估，不得通过扩大核心 RSS 抓取器的职责实现。
