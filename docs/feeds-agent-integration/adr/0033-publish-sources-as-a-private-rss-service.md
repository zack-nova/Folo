# 将供给端发布为可独立部署的私有 RSS 服务

## 背景

旧 Feeds Agent 的采集能力已经迁入 `apps/feed-supplier`：平台类来源映射到自建 RSSHub 路由目录（5A.7），
政府公告、高校通知等列表页是网页列表源（5A.6），页面变化是 `pagechange` 来源（5A.3）。供给端输出的
已经是标准 RSS，但存在两个限制：

- `/v1/feeds/*` 只接受核心持有的内部 Bearer 令牌。普通阅读器和官方 Folo 不能携带自定义请求头，
  因此只有自托管 Folo 核心能订阅。
- 供给端与核心写在同一个生产 Compose 中，不能单独部署。

应用所有者希望把这部分做成独立的 RSS 推送服务，先部署好再导入阅读器，并且同时用于自托管 Folo
和官方 Folo。这些来源不能向所有人开放。

## RSS 的访问控制

RSS/Atom 规范本身没有访问控制，限制只能在 HTTP 层完成。可选机制及其适用范围：

| 机制                             | 自托管 Folo                     | 官方 Folo                    | 其他阅读器 | 结论             |
| -------------------------------- | ------------------------------- | ---------------------------- | ---------- | ---------------- |
| 自定义请求头 / Bearer            | 内部通道已在用                  | 不支持                       | 基本不支持 | 只用于内部通道   |
| HTTP Basic（URL 内嵌凭据）       | 设计上拒绝（`http-fetcher.ts`） | 未验证                       | 部分支持   | 不作为主机制     |
| 网络限制（IP 白名单、私网、VPN） | 适用                            | 不适用：抓取出口不受我们控制 | 视情况     | 只用于内部通道   |
| 地址中的不可猜令牌（能力地址）   | 适用                            | 适用                         | 普遍适用   | 公开通道的主机制 |

能力地址的本质是“持有链接即可读取”，安全性取决于令牌强度、泄露面和撤销能力，下面的决策围绕这三点。

## 决策

### 独立部署

供给端成为可独立运行的私有 RSS 服务，拥有自己的 Compose：`feed-supplier`、`rsshub`、`redis`、
`feed-supplier-postgres`，对外只经过终止 TLS 的反向代理。核心变为可选使用方，通过 `FEED_SUPPLIER_URL`
连接已部署的服务；两者在同一宿主时走 Docker 私有网络，不同主机时走私网或 WireGuard/Tailscale 隧道。

### 两条订阅通道并存

1. **内部通道（不变）。** 自托管 Folo 继续订阅 `rsshub://`、`pagechange://`、`weblist://` 逻辑地址，
   由核心用内部令牌换取 RSS。运维诊断、发现表单、网页列表管理和 AI 来源信息等现有集成全部保留。
   内部通道只在私有网络上暴露。
2. **公开通道（新增）。** 供官方 Folo 和其他阅读器使用的 `https://<域名>/f/<令牌>` 订阅地址。它是唯一
   允许经反向代理暴露到公网的路径；管理、内部、目录接口不经公网代理。

### 订阅授权

公开通道以**订阅授权**为单位管理访问：

- 每个授权对应一个使用方（例如“官方 Folo”“手机阅读器”），有名称、作用域（一组类别或指定来源）和状态。
- 授权作用域内的每个来源有一个独立地址，令牌为 256 位随机值（base64url）。泄露一个地址只暴露一个来源，
  不能借此枚举同一授权下的其他来源。
- 数据库只保存令牌的 SHA-256 摘要用于查找，另以现有凭据密钥（AES-256-GCM，见 ADR-0026）加密保存原文，
  以便重新导出 OPML；读取 API 不返回原文，只有显式导出操作返回。
- 可以单独轮换某个来源的地址，也可以作废整个授权使其全部地址失效。
- 每个授权记录最近访问时间、来源 IP 和 User-Agent，用于发现泄露。

### 公开通道加固

- 无效、已作废或超出作用域的令牌一律返回 404，不区分原因，避免成为令牌探测的判定依据。
- 按授权和客户端地址限流；反向代理与应用日志对 `/f/` 路径中的令牌脱敏。
- 响应带 `X-Robots-Tag: noindex`、`Cache-Control: private`，不提供任何公开的列表或目录接口。
- 支持 `ETag` / `If-None-Match`，与内部通道一致，减少重复抓取。

### 个人凭据的可见性

使用个人凭据抓取的来源不受限制，可以加入任何授权；所有者选择以统一可见代替默认排除。每个来源记录它
依赖的个人凭据（只记凭据名称与类型，从不记录或返回凭据值），来源分三类：

1. **路由绑定凭据：** 路由实例的秘密查询参数绑定到供给端加密凭据（ADR-0026），由绑定关系自动得出。
2. **RSSHub 部署凭据：** `TWITTER_AUTH_TOKEN`、平台 Cookie 等只存在于 RSSHub 容器环境（5A.7），供给端
   无法从路由推断。路由目录模板必须声明其路由依赖的 RSSHub 凭据名称，导入预设时对照固定 RSSHub 镜像的
   路由要求核对；未声明的模板显示为“凭据依赖未知”，而不是视为不需要凭据。
3. **网页列表源与页面变化源：** 第一版不支持登录 Cookie 和自定义请求头（5A.6），因此不使用个人凭据。

管理接口和命令行提供统一的凭据使用总览：哪些来源用了哪些个人凭据（或依赖未知），以及它们经哪些授权
暴露给了哪些使用方。创建或修改授权、导出 OPML 时，输出同样列出作用域内使用个人凭据的来源。

经公开通道交给官方 Folo 的内容会被官方服务器抓取和缓存，使用个人凭据的来源会把以该账号视角取得的内容
交给对方。官方 Folo 是否会让带令牌的地址或其 Feed 出现在其他用户的发现与搜索中，目前未经验证；在用于
真实来源前，先用一个标题唯一的测试来源订阅，再从另一个账号搜索确认。

### 分类与导入

按功能类型区分的是供给端的 provider（RSSHub 路由、网页列表、页面变化），面向阅读的分组是**来源类别**。
网页列表源和页面变化源目前没有类别字段，类别只存在于仓库外的本地订阅预设中；本决策为全部来源类型增加
类别，作为授权作用域和导出分组的依据。按授权导出 OPML，类别成为 outline，可直接导入官方 Folo、
自托管 Folo 或其他阅读器；导出内部通道时仍输出逻辑地址（5A.7 现有行为）。

### 管理入口

公开通道的授权管理只经 `ADMIN_TOKEN` 管理接口和命令行提供，不进入核心，也不经公网代理。自托管 Folo
设置页继续只管理网页列表源（ADR-0032）。

## 修订：类别与凭据声明的落点（2026-10-03）

实现第 3 步时确认，供给端并不保存所有订阅：宽松模式下多数 `rsshub://` 地址没有注册为路由实例，原生 RSS
订阅也不经过供给端。所有者决定以仓库外的订阅预设作为“读什么”的唯一清单，因此上文“为全部来源类型增加
类别”改为：

- 类别和标题来自订阅预设，发布时写到每条公开链接上（`title`、`category`），导出时按类别分组；
  原生 RSS 订阅原样进入同一份 OPML。供给端来源表不增加类别字段。
- RSSHub 部署凭据以结构化字段 `rssHubCredentials`（环境变量名及是否必需，允许 `BILIBILI_COOKIE_*` 这类
  通配名）声明在路由目录模板上。`null` 表示未声明、按“依赖未知”报告，空数组表示确认不使用。
- 凭据密钥轮换（ADR-0026）同时重新加密公开链接令牌，旧密钥可以安全退役。

## 未采用的方案

- **只用一个全局令牌：** 无法区分使用方，泄露后只能全部重置。
- **令牌放在查询参数：** 与路径同样会进入日志和历史，却更容易被中间组件丢弃或改写，且路径形式更容易
  统一脱敏。
- **让核心代理公开订阅：** 会把核心重新变成采集入口并扩大其暴露面，违背 ADR-0025 的边界。
- **以 HTTP Basic 为主：** 自托管 Folo 设计上拒绝 URL 内嵌凭据，官方 Folo 的支持情况未知。后续可以作为
  其他阅读器的可选方式加入，但不替代能力地址。
- **默认排除使用个人凭据的来源：** 所有者需要在官方 Folo 中读到这些来源，逐个放行只会增加操作而不增加
  知情程度；改为强制可见：凭据依赖必须可查，未知依赖显式标出。
- **授权按类别发放一条地址：** 一条地址泄露会暴露整个类别，且无法单独轮换某个来源。

## 影响

- 供给端可以先于核心单独部署和试运行，这也为一直延后的 5A 真实来源灰度提供了落地方式。
- 公开通道使供给端首次直接面向公网，安全基线（TLS、限流、脱敏、只暴露 `/f/`）成为部署的必要条件。
- 经公开通道订阅的 Folo 只看到普通 RSS：运维诊断、来源元数据和管理界面不随之提供，这些能力只在内部
  通道可用。

## 待验证

- 官方 Folo 对带令牌地址的抓取频率、缓存行为，以及该 Feed 是否会被其他用户发现。
- 官方 Folo 抓取时的 User-Agent 和出口特征，用于在访问记录中识别它。
