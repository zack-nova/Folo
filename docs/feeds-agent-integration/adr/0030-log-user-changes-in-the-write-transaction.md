# 在写事务内记录用户变更日志

上游客户端的增量同步引擎要求服务端提供按用户的变更日志：客户端保存已应用的最大 `lastSyncId`，只拉取
其后的动作。游标一旦越过某个尚未提交的行，这个变化就会被永久漏掉。上游用“忽略一秒内插入的行”规避，
但事务一旦超过一秒仍会漏掉。

自有后端把日志行写在产生变化的同一个数据库事务里，作为事务的最后一条语句；插入前先取得该用户的事务级
advisory lock（`pg_advisory_xact_lock`），持有到提交。同一用户的写事务因此串行地分配 id 并提交：任何
事务能看到某用户 id 为 X 的行时，该用户所有更小 id 的行都已提交。涉及多个用户的写（Feed 抓取的新条目
提示、删除列表）按用户 id 排序加锁，避免死锁。读取日志和未读快照使用只读 repeatable-read 事务，使
动作、`lastSyncId` 和未读数来自同一快照。

日志由数据层自己写入，而不是由路由在写入后补记：已读翻转、真正插入的新条目（`xmax = 0`）和重复加星
只有数据层知道；放在同一事务里也保证进程在两步之间崩溃时不会出现“有变化无日志”。动作形状集中在
`apps/server/src/sync/actions.ts`，PostgreSQL 与内存实现共用；因此 API 形状函数从 `server.ts` 移到
`apps/server/src/api-shapes.ts`，使数据层依赖的是纯函数而不是路由模块。

代价是每个同步写多一次加锁和插入，同一用户的并发写在提交阶段串行；对自托管规模可以忽略。变更响应的
`lastSyncId` 取用户当前最新 id，而不是该请求自己产生的 id：它可能略大，但一定是已存在的 id，客户端只会
稍晚释放本地覆盖，不会出错。
