# Feeds Agent

Feeds Agent helps an individual manage personal information sources, keep collection channels working, collect content through available backends, and browse collected content from local storage. The first frontend product surface is **个人信息流** / **Personal Feeds**.

## Language

**个人信息流**:
前端产品表面名称，强调这是用户日常浏览已采集信息并管理信息来源的窗口。
_Avoid_: 控制台, 后台, AIHOT

**本地优先**:
第一版产品形态中配置、凭据引用、运行状态和阅读产物都以用户本机为主要控制边界。
_Avoid_: SaaS, 远程爬虫平台, 多租户服务

**单人私有部署**:
将一个 Feeds Agent 实例部署到受保护的线上环境，仅供唯一应用所有者远程访问的产品形态。
_Avoid_: SaaS, 多租户部署, 公开站点

**私有内容边界**:
仅允许已建立所有者会话的访问者读取内容、媒体、导出和知识库文档的可见性边界。
_Avoid_: 公开信息流, 匿名只读, 搜索引擎页面

**私有部署实例**:
在服务器上统一运行前端、应用 API、调度器、采集任务并持有主存储的单个 Feeds Agent 运行边界。
_Avoid_: 本机代理, 云端控制面, 多节点集群

**持久数据目录**:
私有部署实例中挂载持久卷并集中保存 SQLite、用户配置、凭据和运行产物的服务器目录。
_Avoid_: 容器临时目录, 仓库工作树, 前端静态资源目录

**私有部署备份**:
用于将私有部署实例的主存储恢复到既定时间点的持久卷备份与应用数据快照。
_Avoid_: Git 提交, 容器镜像, 普通 Markdown 导出

**恢复演练**:
在不复用现有持久卷的条件下验证备份可以重建可用私有部署实例的操作。
_Avoid_: 查看备份状态, 重新部署, 数据导出

**私有部署切换**:
将当前本地实例的数据一次性迁移到私有部署实例并使后者成为唯一主实例的上线过程。
_Avoid_: 双向同步, 持续复制, 多主运行

**私有部署发布**:
通过测试、数据快照和人工确认后将一个应用版本切换为私有部署实例当前版本的过程。
_Avoid_: 本地启动, 自动热更新, 数据恢复

**部署存活检查**:
不读取私有数据即可确认私有部署实例进程正在响应的公开探针。
_Avoid_: 持续监控, 应用首页, 通路自检

**部署就绪检查**:
确认私有部署实例能够访问持久数据目录和 SQLite 并可以接收业务请求的受保护探针。
_Avoid_: 部署存活检查, SQLite 完整性检查, 通路自检

**部署告警**:
私有部署实例出现持续不可用、采集连续失败、存储异常或备份过期时主动通知应用所有者的信号。
_Avoid_: 采集运行事件, 前端错误提示, 普通日志

**所有者时区**:
用于向应用所有者展示时间并安排日历型后台任务的私有部署时区设置。
_Avoid_: 数据库存储时区, Railway 服务器时区, 信息源发布时间

**应用所有者**:
拥有并使用单人私有部署实例中全部配置、凭据引用、运行状态和阅读产物的唯一自然人。
_Avoid_: 租户, 客户, 普通用户, 管理员

**所有者认证**:
私有部署实例确认当前访问者是唯一应用所有者的访问控制过程。
_Avoid_: 用户注册, 租户登录, 平台凭据认证

**所有者会话**:
应用所有者通过认证后获得并可主动结束的私有部署访问状态。
_Avoid_: 平台登录态, 采集凭据, API Key

**所有者设备**:
通过一个独立所有者会话访问私有部署实例的浏览器或终端。
_Avoid_: 应用用户, 外部平台设备, Railway 实例

**本地应用服务**:
前端用于读取和改变配置、触发检查、执行采集、生成安装计划和浏览内容的本机服务边界。
_Avoid_: 远程 API, YAML 直写, 多租户后端

**本地 HTTP API**:
本地应用服务向前端暴露的资源接口，用于控制配置、检查、采集运行、安装计划和内容浏览。
_Avoid_: 远程 SaaS API, 前端调用 CLI, 文件系统直连

**自有权威服务**:
FOLO 融合目标中由应用自行部署和控制的业务服务，持有 Feed、Subscription、Entry、Action、处理结果、处理作业、用户画像和分类规则等主数据；FOLO 官方 API 只能作为可替换能力提供方。
_Avoid_: FOLO 官方云, 客户端 SQLite 缓存, feed_supplier

**FOLO 官方能力适配器**:
自有权威服务按需调用 FOLO 官方 API 的隔离层，用于复用摘要、翻译、Readability、Feed 发现等能力，并把返回内容转换为本应用内部契约。
_Avoid_: 数据主存储, 客户端直接依赖, 官方 Entry ID 作为内部主键

**FOLO API 兼容门面**:
自有权威服务面向 FOLO 客户端提供的兼容 API 边界，在当前固定 Client SDK 版本要求的路径、请求、响应、错误和流式格式上保持兼容，并在内部选择本地实现或官方能力。
_Avoid_: 完整复刻官方后端, 客户端双 API, 数据双写

**已验证兼容组合**:
经过契约、鉴权、流式响应、适配器回归和数据库兼容检查的一组 FOLO 客户端版本、Client SDK 版本与官方适配器协议版本。
_Avoid_: 官方最新版, 浮动依赖范围, 仅能编译的版本组合

**API 兼容子集**:
FOLO API 兼容门面中由本应用前端实际使用、或官方能力适配器完成已启用能力所必需的接口集合。
_Avoid_: 官方完整 API 镜像, 未验证透传, 未来功能占位实现

**自有扩展 API**:
位于 `/api/extensions` 下、承载 Entry Evaluation、Processing Job、用户画像、Taxonomy 和获取诊断等本应用新增能力的独立契约；它不修改 FOLO 官方兼容响应。
_Avoid_: 官方响应私有字段, Client SDK 补丁, 官方 API 透传

**Entry 扩展投影**:
时间线按一组 Entry ID 批量读取的轻量扩展数据，包括列表展示所需的评估摘要和处理状态；它不包含完整推荐理由或处理尝试详情。
_Avoid_: 逐条 N+1 查询, Entry 主数据, 完整处理审计

**活跃处理投影轮询**:
当前可见页面存在排队或运行中的处理作业时，客户端每五秒刷新一次 Entry 扩展投影，并在页面失焦或全部进入终态后停止的首期更新机制。
_Avoid_: 固定永久轮询, WebSocket, 后台作业调度

**处理执行历史保留**:
处理作业摘要长期保留，而成功尝试保留三十天、失败尝试保留九十天、大体积原始诊断载荷保留七天的分层清理规则。
_Avoid_: 处理结果生命周期, Entry 内容保留, 永久原始模型日志

**能力提供方**:
实际完成某项读取或生成能力的服务实现，可以是自有服务或 FOLO 官方能力；它不改变该数据在 **自有权威服务** 中的所有权。
_Avoid_: 数据所有者, Feed 来源, 处理器类型

**能力路由策略**:
**FOLO API 兼容门面** 为一项能力选择本地实现、官方能力或允许的降级顺序的服务端规则。自动降级只适用于幂等读取或生成型能力，不适用于权威写操作。
_Avoid_: 客户端条件分支, 双写, 失败后跨后端重放写请求

**官方账号关联**:
应用所有者显式授权 **自有权威服务** 使用其 FOLO 官方账号能力的连接关系；它与所有者会话相互独立。
_Avoid_: 所有者认证, 转发本地会话 Token, 默认登录官方云

**官方后台凭据**:
官方账号关联中由自有服务加密保存、用于后台调用 FOLO 官方能力的可撤销凭据；优先使用长期 Token，官方仅支持 Cookie 时才使用兼容会话凭据。
_Avoid_: 所有者会话, 浏览器 Cookie 自动采集, 日志明文 Token

**外部资源映射**:
本应用内部资源 ID 与某个 **能力提供方** 资源 ID 之间的可选对应关系，用于调用只接受提供方资源 ID 的能力。
_Avoid_: 内部主键, 跨 Feed 去重, 自动同步全部内容

**Feed 获取提供方**:
为一个 Feed 订阅实际发现、轮询或转换外部内容的可替换能力提供方，例如自有标准 Feed 轮询、FOLO 官方托管 RSSHub 或自建 RSSHub；它不拥有本地 Feed 订阅和 Entry 主数据。
_Avoid_: Feed 订阅所有者, 采集供给端, AI 处理器

**官方托管 Feed 获取**:
通过 **FOLO 官方能力适配器** 借用 FOLO 官方维护的 RSSHub、社交平台路由、轮询缓存和相关反爬维护来取得 Feed 内容的可选获取方式。
_Avoid_: 官方数据主存储, 通用反爬 API, 官方同步服务

**官方影子订阅**:
为了使用 **官方托管 Feed 获取**，可能需要在已关联的 FOLO 官方账号中创建、但不作为本应用用户配置主数据的对应官方 Feed 或 Subscription。
_Avoid_: 本地 Feed 订阅, 双写阅读状态, 跨设备同步副本

**官方获取授权**:
应用所有者针对单个本地 Feed 订阅，明确允许自有服务创建和使用 **官方影子订阅** 的授权；它不表示允许同步其他 Feed 或个人阅读与处理数据。
_Avoid_: 全局同步开关, 官方账号关联, 隐式数据上传

**影子订阅待删除期**:
本地取消订阅、切换 Feed 获取提供方或撤销官方获取授权后，官方影子订阅停止使用但暂不删除的七天恢复窗口。
_Avoid_: 继续获取内容, 本地内容保留期, 软删除本地订阅

**官方获取连接**:
本地 Feed 订阅与其官方影子订阅之间异步建立、可重试的获取关系；连接失败不撤销或阻塞本地订阅保存。
_Avoid_: 本地订阅事务, 所有者登录连接, 同步双写

**获取提供方降级**:
首选 Feed 获取提供方持续不可用时，系统自动切换到用户预先配置的候选提供方，并保持使用该候选方直到用户显式切回的运行状态。
_Avoid_: 任意后端探测, 自动切回, 双提供方并行导入

**暂时获取故障**:
Feed 获取提供方发生的超时、限流、网络错误或服务端 `5xx`；单次故障不足以触发获取提供方降级。
_Avoid_: 路由不支持, 配额拒绝, 授权失效, 参数错误

**官方授权恢复窗口**:
FOLO 官方账号授权失效后，相关官方获取暂停但暂不降级的二十四小时恢复期限。
_Avoid_: 影子订阅待删除期, 登录会话有效期, 自动重试间隔

**提供方切换重叠窗口**:
Feed 获取提供方切换或恢复后，从新提供方重新读取最近七天内容的导入窗口，用于弥补游标和缓存差异，并通过跨提供方身份信号避免重复 Entry。
_Avoid_: 正常轮询周期, 内容保留期, Entry 内容版本

**Entry 提供方映射**:
一个本地 Feed Entry 与一个或多个 Feed 获取提供方 Entry ID 之间的对应关系；本地 Entry ID 不随提供方切换而改变。
_Avoid_: 本地 Entry 主键, 跨 Feed 聚合, 内容版本

**跨提供方重复候选**:
同一本地 Feed 订阅中，由不同获取提供方返回，且标题、发布时间或正文指纹显示可能属于同一消息但不足以自动合并的多个 Entry。
_Avoid_: 已确认重复, 跨 Feed 重复候选, 自动去重结果

**Entry 提供方补齐**:
确认是同一 Feed Entry 后，新的获取提供方只为既有 Entry 的空字段补充发布内容，并记录字段来源和补齐时间的操作。
_Avoid_: 覆盖非空内容, 内容版本, 新 Entry

**Entry 提供方冲突**:
确认是同一 Feed Entry 后，不同获取提供方对同一非空发布字段给出实质不同值的诊断事实；系统保留首次导入值，不自动覆盖。
_Avoid_: 页面变化消息, 重复候选, 自动内容更新

**获取诊断**:
Feed 订阅详情中渐进披露获取提供方、官方影子订阅、降级、失败计数、外部映射、重复候选和字段冲突的运维区域。
_Avoid_: 普通 Entry 卡片, 默认时间线信息, 全局后台页面

**配置主存储**:
用户可编辑并可版本管理的 YAML 配置文件集合。
_Avoid_: SQLite 配置表, 运行状态

**配置同步**:
将配置主存储中的 YAML 配置校验并同步为 SQLite 配置快照的产品能力。
_Avoid_: 自动保存, 配置编辑, 数据库迁移

**配置对象 ID**:
信息源和采集通路等 YAML 配置对象使用的人工可读 slug。
_Avoid_: 内容条目 ID, 数据库自增 ID

**归档配置**:
旧版 Feeds Agent 中将关注主体或信息源移出常规管理视图但允许恢复的能力；FOLO 融合阶段暂不实现。
_Avoid_: 停用, 删除, 历史内容, 回收站, 删除记录

**彻底删除**:
旧版 Feeds Agent 中从归档配置永久移除配置对象的危险操作；FOLO 融合阶段不依赖该两阶段删除流程。
_Avoid_: 归档, 停用

**设置**:
前端中承载低频全局配置、运行历史和本地维护入口的产品区域。
_Avoid_: 系统管理, 后台管理, 顶层工作区

**设置子页面**:
设置总览页下承载低频全局配置、运行历史或本地维护任务的独立页面。
_Avoid_: 顶层导航, 工作区, 弹窗配置

**本地存储**:
设置中用于查看配置目录、SQLite 内容存储和 **知识库路径** 状态的页面名称。
_Avoid_: 内容浏览, 数据迁移, 路径配置

**知识库路径**:
用户在 **设置** 中显式配置的本地目录路径，用于保存 **保存到知识库** 生成的知识库文档。
_Avoid_: 默认导出目录, 完整 Markdown 导出目录, 内容存储

**关注主体**:
用户用来组织多个信息源的宏观关注对象，可以是人、组织、项目、品牌或关键词主题；FOLO 融合首期暂不实现该概念。
_Avoid_: 信息源, 账号, 采集通路, 信息源分组

**关注主体格式**:
模块间共享的关注主体最小数据结构，用于保存主体名称、内容领域分组、描述和归档状态。
_Avoid_: 信息源格式, 信息源分组, 关注集合

**主体分组**:
关注主体上的内容领域分组，例如经济、政治或历史。
_Avoid_: 关注主体, 信息源分组, 关注集合

**信息源**:
现有实现中同时承载外部采集目标和用户订阅偏好的兼容概念，目标架构中拆分为 **采集源** 与 **Feed 订阅**。
_Avoid_: 在目标架构中继续作为配置对象名称

**采集源**:
采集供给端中需要被持续访问并转换为 Feed 的外部网页、账号、关键词或平台内对象。
_Avoid_: Feed 订阅, 信息流核心信息源, 内容条目

**Feed 订阅**:
信息流核心中指向一个可订阅 Feed，并附带用户分组、标签、轮询频率和处理策略的长期配置对象。
_Avoid_: 采集源, 平台账号, 采集通路, Feed 内容条目

**Feed 条目**:
一个 Feed 中可被独立识别、处理和阅读的不可变发布消息；同一网页后续发生变化时由采集供给端发布新的 Feed 条目。
_Avoid_: Feed 订阅, 跨 Feed 聚合内容, 抓取结果

**订阅条目身份**:
由 Feed 订阅身份和该 Feed 提供的不透明稳定条目 ID 共同构成的 Feed 条目身份。
_Avoid_: 全局 URL 身份, 内容指纹, 跨 Feed 内容身份

**跨 Feed 重复候选**:
来自不同 Feed 订阅但因 canonical URL 等信号而可能指向相同外部内容的多个 Feed 条目。
_Avoid_: 已自动合并内容, 同一 Feed 条目版本, 去重主键

**原文锚点源**:
用于建立事实、政策、法律、官方立场或机构发布基准的低噪声信息源，通常来自官方原文、权威数据、公告、法院文件或国际组织发布入口。
_Avoid_: 新闻雷达, 热点流, 全量媒体订阅, 舆情监测源

**解释分析补充源**:
为原文基准提供结构理解、风险框架或政策解释的低频专业分析信息源。
_Avoid_: 原文锚点源, 事实终点, 新闻雷达

**国际事实报道补充源**:
用于补充国际事件事实基线、背景入口、地区视角或市场影响线索的二手专业媒体信息源。
_Avoid_: 原文锚点源, 事实终点, 全量媒体订阅, 舆情监测源

**国家产业政策主线**:
第一批国内政策 **原文锚点源** 的筛选范围，覆盖国务院和中央政策、宏观产业部门、数据要素、中小企业专项和教育部正式文件。
_Avoid_: 地方政务流, 本地机会流, 采购交易流, 考试招聘公告

**信息源格式**:
模块间共享的信息源最小数据结构，暂不包含固定目标类型字段。
_Avoid_: 添加表单, AI 识别结果

**信息源 AI 处理开关**:
信息源格式中的配置，用于决定该信息源产生的内容版本是否进入全局 AI 处理流水线，默认开启。
_Avoid_: 信息员开关, 信息源处理开关, 信息源类型, 清洗配置, 单个信息源处理规则

**信息源来源处理配置**:
信息源格式中的顶层 `source_processing` 配置，用于声明是否把该信息源采集载荷中的 **来源自带处理信号** 转换为完整 **处理结果**，以及具体 **来源自带处理信号映射**。
_Avoid_: 清洗配置, 信息源 AI 处理开关, 全局处理规则

**信息源管理**:
用户保存、组织、启停和调整长期关注目标及扫描配置的产品能力。
_Avoid_: 抓取配置, 通路配置, 采集能力管理

**信息源分组**:
信息源上的内容领域分组，例如经济、政治或历史。
_Avoid_: 关注主体, 主体分组, 关注集合

**信息源标签**:
用户在信息源配置上维护的补充标记，可作为内容条目的来源标签。
_Avoid_: 内容标签, AI 分类结果

**扫描配置**:
信息源上的定时采集和采集安全边界设置，不表达用户采集目的。
_Avoid_: 采集通路配置, 处理规则, scan.mode, 扫描模式, 采集意图

**扫描频率**:
信息源定时采集的时间间隔。
_Avoid_: 刷新窗口, 扫描模式

**扫描进度**:
某个信息源通过某条采集通路执行扫描时保留的游标和运行记忆。
_Avoid_: 扫描配置, 采集运行

**采集意图**:
用户为信息源指定的原始采集目的，决定该信息源是跟踪目标变化、持续获取新内容，还是采集本次发现的全部条目。
_Avoid_: 监测语义, 扫描语义, scan.semantics, scan.mode, 页面快照, 条目流, 增量扫描, 刷新扫描, 全量扫描, 采集执行形态

**列表页面**:
通过网页呈现多个可独立采集内容入口的页面。
_Avoid_: 页面快照, RSS, 账号动态

**列表抽取参数**:
信息源中描述如何从特定列表页面识别条目、标题、链接，以及特殊页面分页覆盖规则的参数。
_Avoid_: 采集通路, 通用列表能力

**分页识别规则**:
采集通路在条目发现中识别“下一页”或更多结果入口的默认规则。
_Avoid_: 单个信息源必填参数, 每页上限, 详情采集配置

**分页停止条件**:
`collect_all_items` 跨分页发现条目候选时停止继续翻页的安全规则。
_Avoid_: 每页上限, 完整内容采集失败, 删除判断

**快照抽取参数**:
信息源中描述跟踪页面变化时只使用目标页面某个区域作为内容和指纹输入的参数。
_Avoid_: 列表抽取参数, 采集通路, 监测语义

**内容清洗**:
采集保存前按信息源绑定规则将标准采集结果转换为稳定可读、可去重、可处理内容的环节。
_Avoid_: 处理规则, 身份规范化, AI 摘要, 原始内容

**清洗配置**:
信息源格式中的顶层 `cleaning` 配置，用于声明该信息源的内容清洗开关和源绑定规则。
_Avoid_: params, 处理规则, 采集通路配置, 采集后端配置

**清洗脚本**:
由信息源清洗配置引用并在本机执行的用户脚本，用于处理该信息源特有的网页结构或 API 载荷。
_Avoid_: 采集后端, 处理 agent, 数据库脚本, 通用工作流

**清洗脚本契约**:
统一采集执行通过 stdin/stdout JSON 与清洗脚本交换采集结果和清洗结果的接口约定。
_Avoid_: 数据库写入接口, 处理回填格式, 临时命令参数

**清洗降级保存**:
清洗脚本失败时仍保存未清洗展示内容并记录清洗失败状态的采集保存策略。
_Avoid_: 静默成功, 内容条目失败, 丢弃原始内容

**清洗状态**:
保存在原始内容版本元数据中的内容清洗结果摘要，用于追溯清洗成功、降级保存或未配置清洗。
_Avoid_: 采集运行状态, 处理结果状态, 独立清洗记录

**清洗失败事件**:
清洗脚本失败但内容已降级保存时产生的采集运行事件。
_Avoid_: 内容条目失败, 静默降级, 普通保存事件

**重新清洗**:
用户对已有原始内容版本重新执行信息源清洗配置以更新展示内容和清洗状态的产品动作。
_Avoid_: 重处理, 重新采集, 配置同步

**平台**:
承载一种或多种采集能力的外部网站、应用或服务。
_Avoid_: 来源, 渠道

**采集通路**:
用户配置并验证某类在线内容是否可被系统访问和采集的能力边界。
_Avoid_: 技术配置, 信息通路, 爬虫配置, 抓取脚本, 数据源

**采集能力管理**:
系统为采集通路寻找、安装、检查和切换可用采集后端的产品能力。
_Avoid_: 信息源管理, 手动安装说明, 临时命令调用

**RouteChannel**:
采集通路对应的能力包装层，负责自检、选择后端并将后端输出转成项目统一格式。
_Avoid_: RouteExecutor, Backend, RouteBackend

**RouteBackend**:
RouteChannel 使用的具体采集执行后端，例如解析库、HTTP 客户端、浏览器自动化或 CLI 工具。
_Avoid_: RouteChannel, 采集通路, 采集通路配置, Web 后端

**采集后端**:
采集通路使用的具体执行后端，例如解析库、HTTP 客户端、浏览器自动化或 CLI 工具。
_Avoid_: 后端, Web 后端, API 服务端, 采集通路

**CLI 采集后端**:
通过本地命令行工具或命令式 SDK 包装获取内容的 RouteBackend。
_Avoid_: 公开 API, 授权 API

**替代采集后端**:
同一采集通路下可互相替换的采集后端，用于在能力、配置难度或可用性不满足需求时切换。
_Avoid_: 备用通路, 新信息源, fallback 脚本

**配置难度**:
RouteBackend 被用户配置到可用状态所需的设置复杂度。
_Avoid_: 运行状态, 自检结果

**凭据引用**:
采集通路或平台行为同步中指向外部凭据存储、本机登录态或凭据文件路径的标识符，不包含密钥、Cookie、Token 或登录态本体。
_Avoid_: API Key, Cookie, Token, 登录态

**服务器兼容通路**:
无需个人电脑、桌面应用或交互式浏览器登录即可在私有部署实例中持续运行的采集通路。
_Avoid_: 全部本地通路, 临时人工采集, 本机代理

**公网采集目标**:
经 DNS 解析和每次重定向校验后仍指向公网地址的 HTTP 或 HTTPS 信息源目标。
_Avoid_: 本地文件, 回环地址, 私网服务, 云元数据地址

**部署内置脚本**:
随应用镜像发布并允许私有部署实例执行的受信任清洗脚本。
_Avoid_: 用户上传脚本, 持久卷脚本, 任意命令

**通路匹配**:
为信息源选择可用采集通路的过程，默认由系统自动完成并允许用户覆盖。
_Avoid_: 采集, 自检, 路由

**通路自检**:
对单个采集通路执行的可重复测试，用于确认该采集能力当前是否可用。
_Avoid_: 信息源验证, 登录检查, 健康检查

**通路自检结果**:
通路自检执行后保存在 SQLite 中的状态、时间和错误信息。
_Avoid_: 通路自检配置, 采集通路配置

**安装计划**:
系统在改变用户本机工具链前生成的可审查操作清单，必须由用户确认后才能执行。
_Avoid_: 静默安装, 自动修复, 背景安装

**环境安装**:
设置中用于查看缺失本地工具、生成并确认安装计划的页面名称。
_Avoid_: 安装计划, 自动安装, 静默安装

**统一采集执行**:
系统调用采集后端并将结果转换为内容条目、原始内容、内容索引和内容存储的采集责任边界。
_Avoid_: Agent 直接调用, 临时工具调用, 手动脚本执行

**标准采集结果**:
采集后端返回给统一采集执行的内容候选结构，包含保存内容条目所需的来源身份、标题、原始内容和元数据。
_Avoid_: 仅发现链接, 数据库记录, Markdown 文档, 原始内容版本

**条目候选**:
获取新内容入口发现的、尚未保存为完整内容条目的候选身份。
_Avoid_: 占位内容条目, 临时内容, 链接队列, 详情任务

**条目发现**:
获取新内容采集中从入口识别新内容身份、标题和可访问入口的执行形态。
_Avoid_: 获取列表, 列表后端, 链接抓取

**完整内容采集**:
将条目候选或单条入口获取为可保存原始内容并形成标准采集结果的执行形态。
_Avoid_: 最终内容后端, 详情任务, 二阶段队列

**批量详情采集**:
一次性将多个条目候选获取为完整内容并形成多个标准采集结果的执行形态。
_Avoid_: 条目流, 监测语义, 批量扫描

**详情采集配置**:
获取新内容采集中决定如何把条目候选升级为标准采集结果的采集通路选择规则，可以包含默认通路和有序回退通路。
_Avoid_: 后续后端, 固定采集后端, 详情队列配置, 临时脚本

**采集运行**:
一次手动或定时执行采集任务的可查看结果记录。
_Avoid_: 日志文件, 通路自检, 内容条目

**采集工作流**:
一次用户或脚本触发的应用级采集编排，按顺序完成必要的 **配置同步**、**统一采集执行**，并在产生新的可处理 **原始内容版本** 后执行 **处理触发**。
_Avoid_: 采集后端, 处理流水线, 临时脚本补丁

**采集执行槽位**:
私有部署实例允许一个采集工作流占用并限制其内部并发和运行时间的共享资源边界。
_Avoid_: 任务队列, Railway 副本, 单个信息源

**立即采集**:
用户主动触发一次 **采集运行** 的产品动作。
_Avoid_: 手动采集, 保存并采集, 配置同步

**收集全部信息源**:
用户从阅读页触发全部启用信息源立即采集的产品动作。
_Avoid_: 采集全部候选, collect_all_items, 定时采集, 配置同步

**定时采集**:
**设置** 中用于启停本地 **调度器** 并查看定时采集状态的页面名称。
_Avoid_: 调度器, 自动监测, 定时任务

**调度器**:
在 **本地应用服务** 中按 **扫描频率** 发现到期 **信息源** 并触发定时 **采集运行** 的运行组件。
_Avoid_: cron, 外部计划任务, 采集通路

**调度配置**:
保存 **调度器** 启停偏好和检查间隔的全局配置对象。
_Avoid_: 扫描频率, 扫描配置, 处理规则

**采集运行事件**:
采集运行中针对单个信息源、内容条目或错误产生的结构化结果记录。
_Avoid_: 日志行, 内容条目

**采集记录**:
前端中用于查看采集运行历史和采集运行事件的页面入口名称。
_Avoid_: 日志, 内容记录, 已采集内容

**采集日期**:
系统成功获取内容条目原始内容的日期，用于稳定记录内容版本和生成知识库文档分目录。
_Avoid_: 发布日期, 处理日期

**内容条目**:
从信息源采集后可独立保存、索引、处理和阅读的最小内容单位。
_Avoid_: 信息源, 原始内容, Markdown 文件

**内容条目 ID**:
内容条目的 16 位十六进制稳定身份标识；列表型采集意图优先来自平台外部 ID，其次来自规范化 URL，不使用内容哈希兜底。
_Avoid_: 文件名, 数据库自增 ID

**内容身份别名**:
详情采集或后续解析发现的额外平台外部 ID、canonical URL 或规范化 URL，用于映射到既有内容条目，但不重写内容条目 ID。
_Avoid_: 主键替换, 重命名内容条目, 内容版本

**身份规范化**:
将内容身份别名转换为 `item_identities.normalized_value` 的最小稳定规则。
_Avoid_: 内容指纹, 激进 URL 清洗, 跨信息源去重

**内容指纹**:
采集供给端从页面观测内容计算出的稳定摘要，用于判断页面是否发生变化。
_Avoid_: Feed 条目身份, 核心内容版本, URL 规范化

**原始内容**:
从信息源采集到且未经 AI 判断删除的 HTML、JSON 或其他源格式内容。
_Avoid_: 阅读内容, 摘要, Markdown

**原始内容版本**:
已废弃的核心领域概念；目标架构不在信息流核心中保存同一 Feed 条目的多个内容版本。
_Avoid_: 页面观测快照, Feed 条目, 处理结果

**页面观测快照**:
采集供给端为比较目标页面是否变化而保留的最近一次观测内容与内容指纹。
_Avoid_: Feed 条目, 核心内容版本, 阅读历史

**页面变化消息**:
采集供给端识别到页面内容指纹变化后发布的一个具有新条目身份的不可变 Feed 条目。
_Avoid_: 更新既有 Feed 条目, 原始内容版本, 采集运行事件

**内容索引**:
用于查找、去重、状态管理和批量操作的 SQLite 元数据记录。
_Avoid_: Markdown 主存储

**内容存储**:
SQLite 中保存已采集内容条目的正文、原始载荷和浏览所需字段的主存储。
_Avoid_: Markdown 主存储, raw 文件主存储, 文件夹归档

**内容浏览**:
用户查看、筛选和阅读 SQLite 中已采集内容条目的产品能力。
_Avoid_: 原始内容管理, 文件夹浏览, 调试输出

**信息流核心**:
以可订阅 Feed 为输入并负责订阅、条目去重、处理、存储和展示的通用产品边界。
_Avoid_: 平台爬虫集合, 采集后端中台, RSSHub

**采集供给端**:
将外部平台或网页的专有采集能力转换并发布为可订阅 Feed 的独立能力边界。
_Avoid_: 中台, 信息流核心, 内容存储, 采集通路

**供给采集**:
采集供给端按自身调度访问外部平台或网页并更新可发布内容的过程。
_Avoid_: Feed 读取, 信息流订阅, 信息流核心采集

**物化 Feed**:
采集供给端根据最近一次成功供给采集结果保存并可重复读取的 Feed 快照。
_Avoid_: 实时爬取接口, 信息流核心内容存储, 临时采集结果

**Feed 核心进程**:
运行信息流核心的独立进程，负责 Feed 订阅、内容存储、处理和产品界面 API。
_Avoid_: 采集供给端进程, 平台采集进程, 前端单独进程

**Feed 供给进程**:
运行采集供给端的独立进程，负责供给采集、供给状态和物化 Feed 发布。
_Avoid_: Feed 核心进程, 信息流处理进程, 共享后台线程

**Feed Core 包**:
只包含信息流核心业务代码并且不依赖采集供给端实现的顶层 Python 包。
_Avoid_: feeds_agent 兼容杂物包, 共享业务包, Feed Supplier 子模块

**Feed Supplier 包**:
只包含采集供给端业务代码并且不依赖信息流核心实现的顶层 Python 包。
_Avoid_: feeds_agent 兼容杂物包, 共享业务包, Feed Core 子模块

**Feed Common 包**:
两个进程可以共同依赖但不得包含订阅、采集、处理、存储或展示等业务语义的最小工具包。
_Avoid_: 共享领域模型, 共享数据库层, 共享配置模型

**标准 Feed**:
任何兼容 RSS 或 Atom 的订阅客户端都可以直接消费的 Feed。
_Avoid_: Feeds Agent 私有接口, 数据库记录, 标准采集结果

**扩展 Feed 契约**:
为保留标准 Feed 无法完整表达的身份、版本或来源元数据而提供的可选专有订阅输入契约。
_Avoid_: 必选 RSS 扩展, 采集后端输出, 内部数据库格式

**全部信息流**:
内容浏览中的默认时间线视图，可以混排内容条目卡片和行为卡片。
_Avoid_: 内容存储, 信息源管理, 平台行为主存储

**平台行为**:
用户在外部社交或内容平台上发生的关注、收藏等可回看的个人动作。
_Avoid_: 信息源, 关注主体, 内容条目, 采集运行事件

**平台状态快照**:
系统在一次平台行为同步中读取的外部平台关注、收藏等当前状态。
_Avoid_: 信息源, 内容存储, 平台行为

**平台行为同步**:
读取平台状态快照并通过差分生成平台行为的本地同步能力。
_Avoid_: 信息源采集, 采集运行, 定时采集, 处理流水线

**收集个人行为**:
用户手动触发一次平台行为同步的产品动作。
_Avoid_: 立即采集, 定时采集, 信息源采集, 重处理

**平台行为主存储**:
Feeds Agent SQLite 中保存平台状态快照和平台行为记录的运行时主存储。
_Avoid_: 内容存储, 配置主存储, PersonalOS, 平台资产暂存

**基线同步**:
某个平台行为同步范围内首次保存平台状态快照但不生成历史行为卡片的同步。
_Avoid_: 历史导入, 全量采集, 首次采集

**行为卡片**:
呈现一次或一组相关平台行为的阅读卡片，主语是用户动作而不是外部内容本身。
_Avoid_: 内容条目, 信息源, 采集运行事件, 通知

**时间线卡片**:
前端阅读时间线使用的统一卡片协议，可以承载普通 **内容条目** 或 **行为卡片**。
_Avoid_: 仅内容卡片, 数据库表模型, 平台行为主存储

**关注合并行为卡片**:
一次平台行为同步中将多个新增关注对象合并展示的行为卡片。
时间线摘要应全量展示新增关注对象，避免被预览截断后无法回溯。
_Avoid_: 关注主体, 信息源集合, 内容条目列表

**收藏视频行为卡片**:
呈现单个新收藏视频对象快照的行为卡片，视觉上接近内容卡片但语义仍是平台行为。
_Avoid_: 内容条目, 完整内容采集, 视频信息源

**收藏内容条目化**:
被收藏对象在可得信息满足内容条目最小条件后生成或关联为普通内容条目的升级动作。
_Avoid_: 行为卡片美化, 自动创建信息源, 深度内容采集

**对象快照**:
平台行为记录中保存的被关注或被收藏对象的最小展示信息。
_Avoid_: 原始内容, 完整内容采集, 信息源配置, 内容存储

**行为卡片保存**:
用户将行为卡片中的平台行为和对象快照保存为知识库文档的产品动作。
_Avoid_: 清洗正文保存, 简要信息保存, 完整内容采集, AI 处理结果保存

**行为发生时间**:
外部平台明确提供的用户平台行为实际发生时间。
_Avoid_: 采集日期, 行为发现时间, 发布时间

**行为发现时间**:
系统通过平台状态快照差分首次发现某个平台行为的时间。
_Avoid_: 行为发生时间, 发布时间, 采集日期

**金融数据**:
用户查看金融与宏观经济指标时间序列的产品能力。
_Avoid_: 宏观数据, 内容浏览, 信息源管理, 实物数据

**实物数据**:
用户查看商品、货物、能源、运输和库存等实物链条指标时间序列的产品能力。
_Avoid_: 金融数据, 内容浏览, 供应链管理

**媒体预览**:
从内容条目中选出用于内容卡片展示的一张图片或视频封面线索。
_Avoid_: 媒体存储, 附件, 多模态处理输入

**来源**:
内容浏览中以分类按钮样式展示的信息源入口过滤项，用于按网页、RSS、推特等入口形态快速缩小信息流。
_Avoid_: 平台, 采集通路, 信息源分组, 主体分组, 分类规则配置

**FOLO 订阅分类**:
FOLO Category 中用于组织 Feed 或 Subscription 的阅读分组，不表达单条 Entry 的内容语义。
_Avoid_: 一级分类, 二级分类, Taxonomy 分类

**一级分类**:
AI 后处理为内容条目选择的唯一必填主分类，对应用户 PersonalOS 信息源分类规则中的一级标题。
_Avoid_: 条目标签, 信息源分组, 多值分类

**二级分类**:
AI 后处理可选回填的结构化细分分类，对应用户 PersonalOS 信息源分类规则中某个一级标题下的二级分类；不匹配一级分类时可丢弃。
_Avoid_: 条目标签, 自动挑选的普通标签

**分类规则配置**:
用户维护的 **一级分类** 允许列表和 **二级分类** 层级关系，用于约束 AI 后处理分类和知识库目录归档。
_Avoid_: 代码硬编码分类, 信息源分组, 条目标签

**条目标签**:
阅读界面展示的多值补充标签统称，使用时必须区分 **评估标签** 与 **用户条目标注** 的来源。
_Avoid_: 一级分类, 二级分类, FOLO 订阅分类

**评估标签**:
处理器在 Entry Evaluation 中生成并随评估历史不可变保存的多值内容标签。
_Avoid_: 用户条目标注, FOLO List, FOLO Category

**用户条目标注**:
应用所有者手动维护在 Entry 上的可变标签或备注，不修改 Entry Evaluation。
_Avoid_: 评估标签, 处理结果, AI 标签

**标题文件名**:
知识库文档保存到文件系统时使用内容标题派生出的可读 Markdown 文件名。
_Avoid_: 内容条目 ID 文件名, 日期文件名

**信息提醒**:
某次新增、变化或异常值得打扰用户的通知事实。
_Avoid_: 内容条目, 采集运行事件, 推送消息

**简要信息保存**:
用户将内容条目的摘要、链接、评分、标签和必要来源信息保存为便于检索和查找的简洁 Markdown 记录的产品动作。该动作是缺少清洗后可读正文阶段的过渡或辅助输出，不是 **保存到知识库** 的最终主语义。
_Avoid_: 原文导出, 清洗正文保存, 机器索引导出

**简要信息文档**:
**简要信息保存** 生成的 Markdown 文件，用于面向人阅读和查找 AI 摘要、推荐理由、评分、标签和必要来源信息。
_Avoid_: 原始内容, 阅读文档, 数据库记录, 自动生成的主存储

**清洗正文保存**:
用户将最新 **原始内容版本** 的清洗后展示内容保存到 **知识库路径** 的产品动作，是“保存到知识库”的目标主语义。
_Avoid_: 原始内容导出, 调试导出, 简要信息保存

**清洗正文文档**:
**清洗正文保存** 生成的 Markdown 文件，用于面向人阅读完整正文，并保留 AI 摘要、推荐理由、评分、标签和必要来源追溯信息。
_Avoid_: 原始 HTML, 原始 JSON, 简要信息文档, 内容存储

**处理规则**:
用户定义的全局 AI 后处理策略，用于对已采集内容进行筛选、打分、分类、摘要或整理。
_Avoid_: 信息源配置, 抓取规则, 信息源分组规则

**处理流水线**:
全局内容后处理的整体任务，开启后为待处理内容生成完整 **处理结果**。
_Avoid_: 自由编排, 工作流, 可拆分步骤开关

**待处理条目**:
需要进入处理流水线且尚未得到完整有效处理结果的 Feed 条目。
_Avoid_: 未评分消息, 数据库待办, AI 任务

**处理批次**:
处理流水线一次交给 AI 判断并等待回填处理结果的一组待处理条目。
_Avoid_: 消息列表, 分页结果, 队列任务

**处理提示词**:
本地应用服务为一次 **处理触发** 拼接出的完整 agent 输入，包含处理指令、用户画像快照、处理批次内容和回填要求。
_Avoid_: AI 处理 skill, 系统提示词, 数据库读取说明

**处理回填检查点**:
**处理提示词** 对 agent 回填节奏的协议要求，要求 agent 在处理批次内按配置的条目数或正文字符数分段调用 `write-batch`，使已完成结果可以尽早写回。它不是本地应用服务能够强制执行的事务边界，也不改变外层 **处理批次** 的选择规模。
_Avoid_: 处理批次上限, 后端强制 Flush, 独立 agent 调用, 数据库提交间隔

**agent 命令模板**:
配置中声明本地应用服务如何启动外部 agent CLI 的命令参数模板。
_Avoid_: 固定 codex 命令, 处理队列配置, AI 模型配置

**agent 并行数**:
一次自动处理触发内允许同时运行的外部 agent CLI 数量。
_Avoid_: 处理队列长度, 采集并发数, 信息源并发数

**处理触发**:
本地应用服务在采集完成、用户操作或后续自动化条件满足时启动一次 AI 后处理的动作。
_Avoid_: 采集运行, 处理运行, 队列任务

**处理失败**:
某个 Feed 条目在 **处理流水线** 中因处理器失败、超时或无效回填而未得到完整 **处理结果** 的终态；它不会作为普通 **待处理条目** 自动重跑，需用户显式发起 **重处理** 才再次进入处理队列。
_Avoid_: 处理中, 暂时等待, 采集失败, 普通待处理

**处理状态**:
用户在内容浏览中看到的 AI 后处理可见状态，由 **本地应用服务** 基于处理作业和 **处理结果** 统一返回；前端只展示该语义，不自行推断后台是否卡住。
_Avoid_: 前端猜测状态, 数据库原始字段, 队列实现细节

**处理状态提示**:
内容浏览中的非布局占位全局提示，用于说明当前存在 **处理失败** 并提供查看失败项、重试失败项和关闭提示的入口；用户关闭提示只影响本地显示，不改变后端 **处理状态**。
_Avoid_: 停止处理, 取消任务, 错误弹窗

**处理异常筛选**:
用户在当前阅读页显式开启的内容筛选，当前阶段用于只查看 **处理失败** 的内容条目；它应可见且可一键清除。
_Avoid_: 隐式跳页, 偷偷改筛选, 伪装成分类筛选

**处理异常**:
面向用户聚合展示的 AI 后处理问题集合；当前阶段等同于 **处理失败** 集合。
_Avoid_: 单一错误码, 处理中, 普通待处理

**最近一次异常发生时间**:
某个 Feed 条目最近一次进入 **处理失败** 的时间，用于 **处理异常筛选** 的排序和卡片上的轻量说明；当前阶段由处理作业时间稳定计算，前端不根据轮询时间或本地状态变化临时推断。
_Avoid_: 内容发布时间, 采集时间, 首次失败时间

**处理异常原因摘要**:
由 **本地应用服务** 返回给前端的简短异常原因说明，当前阶段来自处理作业的失败摘要；它帮助用户判断是否值得重试，但不直接暴露完整 stderr 或底层命令输出。
_Avoid_: 原始堆栈, 长日志, 模糊状态名

**用户画像文档**:
用户提供给 AI 判断内容相关程度的 Markdown 背景资料。
_Avoid_: 账号资料, 应用设置, 提示词

**处理结果**:
处理器针对应用所有者的画像和分类规则，对 Feed 条目给出的个性化结构化评估，包括重要性、时效性、用户相关程度、综合推荐分、推荐理由、分类，以及处理方式、用户画像和分类规则的追溯信息；AI 是主要处理方式但不是唯一处理方式。
_Avoid_: 原始内容, 采集结果, 处理作业, AI 对话报告

**评估历史**:
同一个 Feed Entry 每次成功处理产生的不可变处理结果集合，用于比较评分、处理器、用户画像和分类规则变化。
_Avoid_: 处理尝试, Entry 内容版本, 当前评估覆盖

**当前评估**:
时间线、精选和默认详情使用的 Entry Evaluation，由独立指针选择评估历史中的一条记录。
_Avoid_: 最新处理作业, 唯一评估记录, entries.settings

**精选排序分**:
由当前评估综合分乘以基于 Entry 年龄和分类半衰期的时间衰减系数得到的可重建展示排序值；它不是处理结果字段。
_Avoid_: 综合推荐分, AI 评分, 永久评估历史

**精选候选**:
当前评估综合推荐分大于等于 70 的 Feed Entry，可进入精选视图排序。
_Avoid_: 全部已评估条目, 已排序精选结果, AI 标签

**精选年龄基准**:
计算精选排序分时使用的 Entry 时间，依次选择可靠原始发布时间、提供方首次发现时间和本地首次导入时间。
_Avoid_: 处理时间, 阅读时间, 查询缓存时间

**评估回滚**:
用户把某条历史评估重新选为当前评估的操作；它只切换当前指针，不重新执行处理器。
_Avoid_: 重处理, 重试作业, 恢复 Entry 内容

**配置过期评估**:
当前评估所引用的处理器版本、评分公式版本、用户画像快照或 Taxonomy 快照不是最新处理配置，但仍可继续读取和使用的评估状态。
_Avoid_: 无效评估, 处理失败, 自动重评队列

**范围重评**:
用户按发布时间、Feed、Entry 内容分类、精选范围或明确 Entry 集合，预览数量和成本后显式发起的批量重新评估。
_Avoid_: 配置保存副作用, 自动全量重评, 处理失败重试

**条目动作设置**:
FOLO `entries.settings` 在本地 Entry 投影中保存的 Action 生效指令或行为开关，例如是否执行摘要或翻译；它声明要做什么，不保存处理器生成的完整结果。
_Avoid_: 处理结果, 摘要正文, 翻译正文, 处理作业

**条目摘要结果**:
Feed Entry 的阅读辅助摘要，作为摘要 Action 或处理器附带产物保存，不属于 Entry Evaluation。
_Avoid_: 推荐理由, 评估历史, entries.settings

**处理器**:
为 Feed 条目生成完整或部分处理结果的执行者，可以是 AI、确定性规则、外部服务或人工回填。
_Avoid_: 采集后端, AI 任务, 处理作业

**评分公式版本**:
把处理器产出的评分维度计算为综合推荐分的后端公式版本。
_Avoid_: AI 模型版本, Taxonomy 版本, 精选排序分

**处理作业目的**:
Processing Job 要产出的处理能力，例如条目评估、摘要或翻译；它不是 Action 命中、范围重评或手动重试等触发来源。
_Avoid_: 触发来源, UI 入口, 错误原因

**处理作业幂等键**:
由 Entry、处理作业目的、处理器及其版本、评分公式版本、用户画像快照和 Taxonomy 快照组成的唯一业务键，用于避免同一处理目标被重复排队。
_Avoid_: Processing Job 主键, 触发来源, Entry 去重指纹

**处理作业取代**:
同一 Entry 的更新配置处理作业使尚未开始的旧配置处理作业进入不再执行的终态。
_Avoid_: 取消运行中作业, 删除处理历史, 评估回滚

**已满足评估**:
当前评估已经由同一处理作业目的、处理器及其版本、评分公式版本、用户画像快照和 Taxonomy 快照生成，可直接满足自动触发或默认范围重评。
_Avoid_: 活跃作业, 失败作业, 强制重评

**强制重评**:
用户明确要求即使存在已满足评估，也重新生成一条同配置评估历史的操作。
_Avoid_: 自动 Action 命中, 失败重试, 配置过期提示

**来源自带处理信号**:
信息源在采集载荷中提供的部分可信摘要、评分、分类或推荐强度线索，不要求天然满足完整 **处理结果** 契约。它是 **来源自带评分信号** 和 **来源自带分类信号** 等来源线索的总称。
_Avoid_: 内容清洗, 清洗脚本, 处理流水线, 采集结果, 完整处理结果

**来源自带评分信号**:
信息源在采集载荷中提供的可信评分或推荐强度信号，经配置或适配规则转换为 **处理结果** 中的重要性评分、时效性评分、用户相关程度评分或综合推荐分输入。
_Avoid_: AI 评分, 内容指纹, 信息源标签

**来源自带分类信号**:
信息源在采集载荷中提供的可信主题、栏目、类别或精选标记，经配置或适配规则转换为 **处理结果** 中的 **一级分类**、**二级分类** 或 **评估标签**。
_Avoid_: 信息源分组, 主体分组, 内容清洗

**来源自带处理信号映射**:
信息源格式中声明如何把 **来源自带评分信号** 和 **来源自带分类信号** 转换为完整 **处理结果** 的规则，包括固定评分、来源分数字段、分类对应关系、摘要和推荐理由来源。
_Avoid_: 采集后端逻辑, 全局处理规则, 清洗配置

**来源自带处理信号映射失败**:
系统保存原始内容版本后，无法按 **来源自带处理信号映射** 生成完整有效 **处理结果** 的情况，例如来源分数字段缺失、固定评分配置不合法、分类映射不满足当前 **分类规则配置**，或摘要、推荐理由等必填字段无法形成。
_Avoid_: 清洗失败, 采集失败, AI 处理失败

**重处理**:
用户显式要求某个 **处理失败** Feed 条目重新进入 **处理流水线** 的产品动作；它不触发重新采集，也不发现新内容。
_Avoid_: 自动失效, 重新采集, 配置同步

**重处理请求**:
用户发起的显式恢复请求；当前阶段仅选择仍处于 **处理失败** 的 Feed 条目重新入队。
_Avoid_: 处理运行, 队列任务, 删除处理结果

**批量重处理**:
用户对一组进入 **处理失败** 的内容条目发起的恢复动作；当前阶段按当前已应用阅读视图条件预览数量，并在用户确认后重新入队完整匹配结果集。
_Avoid_: 重新采集, 超时强制重跑, 全量重算

## Relationships

- 一个 **单人私有部署** 实例恰好属于一个 **应用所有者**
- **单人私有部署** 第一阶段不提供注册、邀请、成员、角色或租户数据隔离
- FOLO 融合后由 **自有权威服务** 持有业务主数据，客户端 SQLite 只保存可重建的本地投影
- **FOLO 官方能力适配器** 可以复用官方 API，但官方服务端缓存和排序实现不构成本应用的数据契约
- FOLO 客户端默认只连接 **FOLO API 兼容门面**，不在业务组件中直接切换自有 API 与官方 API
- **FOLO API 兼容门面** 只承诺兼容当前固定 Client SDK 版本中本应用实际使用的接口子集
- **API 兼容子集** 只包含前端实际调用和已启用官方适配器必需的接口，不完整镜像官方后端
- 未进入 **API 兼容子集** 的路径统一返回 HTTP `501` 和稳定错误码 `capability_not_implemented`
- 客户端以能力清单隐藏未实现入口，不能把 `501` 当作正常能力探测机制
- 新的前端调用进入兼容子集前必须同时增加服务端实现和契约测试
- Entry Evaluation、Processing Job、用户画像、Taxonomy 和获取诊断通过 **自有扩展 API** 提供
- FOLO 官方兼容的 Feed、Subscription 和 Entry 响应不加入本应用私有字段
- 前端通过组合查询与本地缓存投影关联官方兼容资源和 **自有扩展 API** 资源
- **自有扩展 API** 独立版本化，不与 Client SDK 版本强耦合
- **FOLO 订阅分类** 只组织订阅，不接收 **当前评估** 的 **一级分类** 或 **二级分类** 回写
- **一级分类** 和 **二级分类** 只来自 Entry Evaluation 与 Taxonomy，用于 Entry 筛选、精选解释和知识库路径
- **评估标签** 只保存在 Entry Evaluation 的 `tags_json` 中，不同步为 FOLO Category、FOLO List 或用户人工标签
- FOLO 融合首期不实现 **用户条目标注** 的 UI、API 或同步投影，只保留独立模型边界
- 后续用户手动整理 Entry 时应创建或修改 **用户条目标注**，不得改写既有评估历史中的 **评估标签**
- **条目摘要结果** 复用 FOLO 原有摘要结果存储和界面，不写入 `entry_evaluations`
- 时间线通过 **Entry 扩展投影** 批量读取当前页评估摘要和处理状态，不逐条请求
- 单次 Entry 扩展投影最多接收 100 个 Entry ID，并对缺失结果返回明确空状态
- 时间线投影只包含列表展示字段；完整推荐理由、处理尝试和错误详情使用单条扩展接口
- Entry 扩展投影写入客户端本地 SQLite 缓存，离线时可以展示最后同步结果
- 当前可见页面存在 `queued` 或 `running` 状态时启用五秒一次的 **活跃处理投影轮询**
- 页面或应用失焦、或当前页全部进入终态后停止活跃处理投影轮询；重新聚焦时立即刷新一次
- 投影轮询网络失败使用退避，不改变服务端 Processing Job 状态
- 首期不使用 WebSocket；未来跨设备实时更新可以增加 SSE 投影失效事件
- 当前评估和 Processing Job 摘要长期保留
- 每次成功重处理都新增不可变 **评估历史** 记录，并在同一事务中更新 **当前评估** 指针
- 成功重评总是更新 **当前评估**，即使新综合分下降、分类变化或不再满足 **精选候选** 门槛
- 成功重评后精选列表必须按新的 **当前评估** 重新计算；系统不得为了保留精选展示而继续使用旧高分评估
- 重评失败只更新 Processing Job、Attempt 和错误摘要，不清空、不覆盖、不标记不可用 **当前评估**
- 重评失败后时间线和精选继续使用原 **当前评估**；若原评估是 **配置过期评估**，可以叠加显示重评失败提示
- 历史评估默认保留最近十个，且至少保留最近一百八十天；当前指针引用的评估不得清理
- 时间线和精选只读取 **当前评估**，详情页可以查看历史与差异
- **评估回滚** 只切换当前评估指针，不重新执行 AI 或其他处理器
- 综合推荐分是不可变评估事实，不因内容变旧而修改
- 精选先筛选当前评估综合推荐分大于等于 70 的 **精选候选**，再使用 **精选排序分** 排序
- **精选候选** 门槛首期为全局固定规则，不按 Taxonomy 分类覆盖
- **精选排序分** 默认按七天半衰期对综合推荐分做时间衰减
- Taxonomy 分类可以覆盖默认半衰期，使长期内容使用更慢的时间衰减
- **精选年龄基准** 优先使用可靠原始发布时间，缺失时依次回退到提供方首次发现时间和本地首次导入时间
- 原始发布时间晚于查询时刻超过二十四小时时视为不可信并回退
- 精选排序分在查询时计算或缓存为可重建投影，不写回评估历史
- 精选界面展示原综合分，并说明时间会影响排序；详情可以显示采用的年龄基准，同排序分时按年龄基准时间降序
- 处理器版本、评分公式版本、用户画像或 Taxonomy 更新后，新 Entry 使用最新处理配置，既有当前评估不自动重算
- 当前评估引用旧处理器版本、旧评分公式版本、旧画像或旧 Taxonomy 时标记为 **配置过期评估**，但不删除或覆盖
- **配置过期评估** 继续参与精选，不降低原综合分，也不因配置更新退出精选
- 时间线与精选为配置过期评估显示轻量“旧配置”标识，并支持筛选
- 用户可以从旧配置筛选结果直接发起 **范围重评**
- 用户通过 **范围重评** 选择发布时间、Feed、Entry 内容分类、精选范围或 Entry 集合后批量创建或复用 Processing Job
- 范围重评提交前必须预览匹配数量、预计调用量或成本，以及将使用的配置版本
- 范围重评提交结果必须区分新建、复用、已满足、被取代和跳过的条目数量
- 创建 Processing Job 时必须使用 **处理作业幂等键** 检查是否已有同目标的排队或运行作业
- **处理作业幂等键** 用于排队和运行中的活跃作业判重，不阻止终态作业之后通过 **强制重评** 产生新的同配置历史
- 自动 Action 命中 **已满足评估** 时不创建 Processing Job
- 默认范围重评命中 **已满足评估** 时不创建 Processing Job，并在结果中计入 `already_satisfied`
- 已有同 **处理作业幂等键** 的排队或运行作业时，不创建重复 Processing Job，自动 Action 命中和范围重评都复用既有作业
- 新请求优先级更高且既有作业尚未开始时，可以提升既有 Processing Job 的优先级
- **处理作业幂等键** 不包含触发来源；Action 自动命中、范围重评和手动入口只作为审计元数据或结果计数
- 用户对失败作业发起重试时复用原 Processing Job 并增加 Attempt，不创建并行 Job
- 已失败的 Processing Job 不因后续自动 Action 再次命中而自动重试
- **强制重评** 可以在没有同目标活跃作业时创建新的同配置 Processing Job，成功后新增一条不可变评估并更新 **当前评估**
- **强制重评** 遇到同目标排队或运行作业时复用该活跃作业，不创建并行作业
- 评估处理器可以附带生成 **条目摘要结果**，但评估成功只依赖 Entry Evaluation 写入成功
- 附带摘要写入失败只影响摘要产物状态，不回滚 **评估历史** 或 **当前评估**
- 同一 Entry 的同一 **处理作业目的** 首期最多同时存在一个运行中的评估 Processing Job
- 同一 Entry 已有旧配置评估 Job 正在运行时，新配置评估 Job 可以排队等待，但不得并行运行
- 同一 Entry 已有旧配置评估 Job 尚未开始时，新配置评估 Job 可以通过 **处理作业取代** 使旧 Job 进入 `superseded` 终态
- 被 **处理作业取代** 的 Job 不产生 **评估历史**，也不更新 **当前评估**
- 旧配置运行中 Job 完成后可以按正常事务产生评估；若此时已有更新配置 Job 排队，该评估会作为 **配置过期评估** 暂时存在，直到更新配置 Job 成功后更新 **当前评估**
- 更新用户画像或 Taxonomy 本身不删除、不覆盖已有评估历史
- **处理执行历史保留** 对成功 Attempt 使用三十天期限，对失败 Attempt 使用九十天期限
- 原始模型响应、完整堆栈、stderr 等大体积诊断载荷默认七天后清理
- Attempt 和诊断载荷清理后，Job 继续保留累计尝试次数、关键时间和最后错误摘要
- 处理历史清理不影响当前有效评估或 Entry 可读性
- FOLO 客户端、Client SDK 和官方适配器只使用 **已验证兼容组合**，不自动跟随官方最新版
- 升级 **已验证兼容组合** 必须人工发起，并通过请求响应、流式格式、鉴权、适配器和数据库兼容测试
- 升级后保留回滚到上一 **已验证兼容组合** 的能力
- 官方接口未预期变化时只熔断受影响能力，并通过能力清单告知客户端，不影响自有核心能力
- **能力路由策略** 由服务端维护；客户端通过能力清单判断功能是否可用
- 权威写操作只写入 **自有权威服务**，不得在自有服务与官方后端之间自动降级或双写
- 摘要、翻译、Readability 等幂等读取或生成型能力可以选择 **能力提供方** 并安全降级
- **官方账号关联** 不复用或转发所有者会话凭据
- **官方后台凭据** 优先使用官方长期 Token，并在服务端凭据库静态加密保存
- 官方只提供会话 Cookie 时可以作为兼容凭据，但必须记录获得、验证和可确认的过期时间
- 系统不得自动读取或上传浏览器 FOLO Cookie；用户必须显式完成官方账号关联
- 官方后台凭据失效后进入 **官方授权恢复窗口**，由用户重新关联，不从其他会话静默补充
- 撤销官方账号关联立即停止官方调用；相关影子订阅进入各自的七天待删除流程
- 官方后台凭据轮换不改变本地资源身份或外部资源映射
- 只接受官方资源 ID 的能力必须先存在 **外部资源映射**，路径和响应兼容本身不足以让本地 Entry 使用该能力
- 创建 **官方影子订阅** 必须先获得单个 Feed 粒度的 **官方获取授权**
- **官方获取授权** 只允许官方保存该 Feed 及其获取到的 Entry，不允许同步其他订阅、已读状态、收藏、Action、处理结果、用户画像或 Taxonomy
- 本地 Feed 订阅始终是配置主数据，**官方影子订阅** 只服务于官方托管获取
- 保存本地 Feed 订阅不等待 **官方获取连接** 建立；自有服务先提交本地主数据，再由后台异步创建官方影子订阅
- **官方获取连接** 失败时保留本地订阅，记录错误摘要和重试时间，并允许用户重试或切换获取提供方
- 官方影子订阅创建成功后才保存外部资源映射并把该获取关系标记为可用
- **官方获取连接** 持续失败时，只有存在用户预先配置的候选提供方才允许自动执行 **获取提供方降级**
- **获取提供方降级** 后只使用当前候选提供方导入新 Entry，不允许两个提供方并行写入
- 官方恢复后不自动切回；用户测试连接成功并显式确认后才恢复官方获取
- 每次 **获取提供方降级** 保存原提供方、当前提供方、原因和发生时间，并在界面显示“降级运行”
- 路由不支持、明确订阅配额拒绝等不可重试能力拒绝，在存在候选提供方时立即触发 **获取提供方降级**
- **暂时获取故障** 必须连续发生至少三次，且首次到末次失败跨越至少三十分钟，才允许触发 **获取提供方降级**
- 任意一次成功获取都会清零暂时获取故障的连续失败计数
- FOLO 官方账号授权失效时立即暂停官方获取并进入二十四小时 **官方授权恢复窗口**；到期未恢复后才对有候选提供方的 Feed 降级
- 输入参数错误、本地配置错误或候选提供方不可用不触发自动降级
- 降级条件由后端根据规范化错误类型和持久化失败状态计算，前端不自行推断
- 切换 Feed 获取提供方不改变本地 Feed 订阅身份，并使用七天 **提供方切换重叠窗口**
- 重叠导入中，稳定 GUID 相同，或 canonical URL 与发布时间同时相同，才自动确认是同一个本地 Entry

- 正常 Feed 订阅只在订阅列表显示轻量获取来源标签，不在普通 Entry 卡片展示提供方运维信息

- 官方清理失败只进入后台重试和错误记录，不得重新启用已经停止的官方获取

- **收集全部信息源** 触发全部启用 **信息源** 的 **立即采集**，不等同于 `collect_all_items` 信息源的 **采集全部候选**
- 第一版 **收集个人行为** 与 **收集全部信息源** 不并发执行；任一收集动作运行中，两个全局动作都应禁用或展示忙碌状态
- 任一阅读页全局收集动作开始后即启动同一套实时信息流刷新会话；采集中持续拉取已保存或已完成 AI 回填的内容，采集结束后若 AI 仍在处理则延续该会话直到处理稳定或超时
- 实时信息流刷新按当前筛选条件重新读取用户已加载的页数；用户离开列表顶部时，新出现的头部条目先显示轻量提示，避免打断当前阅读位置
- 阅读页使用轻量游标分页接口增量加载时间线卡片，并通过独立元数据接口读取今日统计和筛选选项；不再为每次刷新全量读取整页 feed
- 阅读页全局收集动作完成后用轻量提示展示结果摘要，不自动跳转页面
- **收集全部信息源** 的完成提示应展示本次新增、更新和失败数量
- **收集个人行为** 的完成提示应展示新增关注数、新增收藏数、条目化收藏视频数和失败原因摘要
- 阅读页全局收集动作不展开详细日志；详细日志或诊断入口后续单独设计
- 前端阅读页不直接建模 **内容条目** 与 **行为卡片** 的底层差异，而是渲染统一 **时间线卡片**
- **行为卡片** 的特殊处理应留在后端领域链路中，包括基线同步、对象快照、合并规则、条目化和知识库保存
- **全部信息流** 的公开读取接口应可以返回普通 **内容条目** 与 **行为卡片** 混排后的 **时间线卡片** 列表
- **行为卡片** 进入时间线时，排序时间优先使用 **行为发生时间**，缺失时回退到 **行为发现时间** 或卡片创建时间
- **关注合并行为卡片** 的 **行为发生时间** 使用集合内最后一条新增关注的关注时间；集合内没有可靠关注时间时使用卡片创建时间
- 已执行 **收藏内容条目化** 的收藏视频在时间线中仍优先体现用户收藏行为时间，视频发布时间作为内容元数据保留
- 第一版 **平台行为同步** 只由用户手动触发，不接入 **调度器**，也不新增后台定时任务
- 第一版 Bilibili **平台行为同步** 使用 **凭据引用** 或本机已有登录态读取平台数据，不把 Cookie、Token、SESSDATA 等凭据本体写入 SQLite、YAML 或日志
- Bilibili **平台行为同步** 因登录态失效失败时，只提示登录态不可用或已过期，不输出敏感凭据字段
- **平台状态快照** 和 **平台行为** 的第一版 **平台行为主存储** 是 Feeds Agent SQLite
- PersonalOS 可以作为 **平台行为** 的可选导出或长期归档位置，但不参与运行时差分、去重或 **全部信息流** 读取
- 每个 Bilibili **平台行为同步** 范围的首次成功同步是 **基线同步**，只保存 **平台状态快照**，不生成历史 **行为卡片**
- **基线同步** 之后的成功同步才将相对上一份 **平台状态快照** 的新增关注或新增收藏生成 **平台行为**
- 第一版 **平台行为** 只对新增关注和新增收藏产生 **行为卡片**；取消关注和取消收藏先只作为状态变化保留，不进入日常阅读流
- 第一版 **平台行为** 接入范围只覆盖 Bilibili 新关注 UP 主和 Bilibili 新收藏视频
- 一次 **平台行为同步** 中的多个 Bilibili 新关注 UP 主合并成一张 **关注合并行为卡片**
- **关注合并行为卡片** 保持纯 **平台行为** 记录，不执行 **收藏内容条目化**，也不生成普通 **内容条目**
- **关注合并行为卡片** 的时间线摘要和摘要链接应全量列出本次新增关注对象，不使用“等 N 项”预览截断
- Bilibili 新收藏视频一条视频生成一张 **收藏视频行为卡片**
- **收藏视频行为卡片** 是被收藏视频成为普通 **内容条目** 之前的过渡展示形态
- 当被收藏视频的可得信息满足 **内容条目** 最小保存条件时，应通过 **收藏内容条目化** 生成或关联普通 **内容条目**
- 第一版 Bilibili 收藏视频满足 **收藏内容条目化** 的最小条件是：平台、视频 ID 或 BV 号、标题和视频链接
- 收藏视频的封面、作者、简介、收藏夹名称、收藏时间、发布时间和播放统计等字段能从当前平台同步结果获取时应写入 **对象快照** 或 **原始内容版本** 元数据，但不作为 **收藏内容条目化** 的阻塞条件
- 如果当前平台同步结果缺少视频 ID/BV、标题或视频链接，收藏视频先保留为 **收藏视频行为卡片**，不伪装成普通 **内容条目**
- 满足最小条件的 Bilibili 新收藏视频应在 **平台行为同步** 中立即执行 **收藏内容条目化**，不要求用户再手动转换
- 条目化后的普通 **内容条目** 保留对应 **平台行为** 引用，用于解释该内容进入信息流的原因是用户新收藏
- 条目化后的 Bilibili 收藏视频第一版 **原始内容版本** 使用当前平台同步结果拼成结构化 Markdown，包括标题、UP 主、简介、视频链接、收藏夹、收藏时间、发布时间、时长和播放/收藏/弹幕统计等可得字段
- 条目化后的 Bilibili 收藏视频可以把封面写入 **媒体预览** 元数据，不把封面 URL 当作正文主体
- 条目化后的 Bilibili 收藏视频不得把当前未获取的字幕、评论或完整视频内容伪装成已采集正文
- **收藏内容条目化** 后，被收藏视频进入 **内容存储**、AI **处理流水线**、普通内容卡片展示和普通 **保存到知识库** 语义
- 平台提供可靠时间时，**行为卡片** 使用 **行为发生时间** 排序和展示
- 平台不提供可靠时间时，系统用平台状态快照差分生成 **平台行为**，并用 **行为发现时间** 排序和展示
- 第一版 **行为卡片** 只保存被操作对象的 **对象快照**，不自动执行 **完整内容采集**
- Bilibili 新关注 UP 主的 **对象快照** 优先包含平台、动作、UP 主 UID、昵称、签名、头像、主页链接和行为时间；平台同步未能获取的字段可以缺省，不阻塞卡片生成
- Bilibili 新收藏视频的 **对象快照** 优先包含平台、动作、视频 ID/BV、标题、作者、封面、视频链接、收藏夹名称和行为时间；平台同步未能获取的字段可以缺省，不阻塞卡片生成
- 第一版 **对象快照** 不包含 AI 标签、分类、评分或摘要
- **行为卡片** 可以混排到 **全部信息流**，但仍然独立于 **内容条目** 和 **内容存储**
- 第一版 **行为卡片** 提供 **行为卡片保存**，不要求 **完整内容采集** 或 AI **处理结果**
- **行为卡片保存** 的知识库目录第一版固定为 **知识库路径** 下的 `平台行为/Bilibili`
- **关注合并行为卡片** 保存文件名使用行为日期和平台动作，例如 `YYYY-MM-DD-Bilibili新增关注.md`
- **收藏视频行为卡片** 保存文件名优先使用视频标题，标题缺失时使用平台对象 ID
- 第一版 **行为卡片** 不提供转入 **信息源管理**、创建 **关注主体** 或创建 **信息源** 的动作
- **平台行为** 后续即使支持进入 **信息源管理**，也必须由用户显式确认，不自动创建 **关注主体** 或 **信息源**
- 第一版 Feeds Agent 是单用户、**本地优先** 的个人工具，不提供多租户账号、远程队列或共享工作区
- 前端是控制台，必须通过 **本地应用服务** 改变 **配置主存储**、触发 **通路自检**、执行 **采集运行** 和访问 **内容浏览**
- **本地应用服务** 第一版通过 **本地 HTTP API** 服务前端，CLI 保留为开发、调试和自动化入口
- **配置主存储** 是 YAML 文件集合，SQLite 保存配置快照、运行状态、扫描进度、内容索引和 **内容存储**
- SQLite 配置快照中的 **信息源** 只保存 **关注主体** 的 `subject_id` 引用，不冗余主体名称或分组
- **配置同步** 遇到不存在的非空 `subject.subject_id` 时应失败并返回可解释错误
- **本地优先** 意味着前端控制本机配置、本机工具安装、本机采集运行和本机内容浏览
- 前端不直接写 YAML；**本地应用服务** 负责配置校验、写入 YAML、同步 SQLite 和返回可解释错误
- 运行时状态不自动写回 **配置主存储**，只有用户明确保存配置变更时才更新 YAML
- `status.enabled` 是 YAML 采集开关，不表示运行成功或失败
- `status.archived` 是 YAML 归档开关，不通过移动配置文件目录表达归档
- **归档配置** 不等同于停用；停用的配置仍在常规管理视图中，归档后的配置退出常规管理视图并进入 **设置** 中的统一归档入口
- 归档 **信息源** 时应同时将 `status.enabled` 保存为 `false`
- 归档 **信息源** 不改变 `ai_processing.enabled`；恢复时保留原来的 **信息源 AI 处理开关** 偏好
- 归档 **信息源** 前需要轻确认，文案应说明会停止采集、移入 **归档配置**、可恢复，并保留历史 **内容条目** 和 **采集记录**
- 常规管理视图默认只展示 `status.archived` 不为 `true` 的配置对象，**归档配置** 入口展示 `status.archived` 为 `true` 的配置对象
- 恢复 **归档配置** 后，该配置重新回到对应的常规管理视图
- 恢复 **归档配置** 只将 `status.archived` 改回 `false`；是否重新启用采集由用户单独决定
- 恢复归档 **信息源** 时，如果原 **关注主体** 已归档或已 **彻底删除**，该 **信息源** 恢复为未归属并提示原 **关注主体** 不可用
- 恢复归档 **信息源** 不自动恢复其原 **关注主体**
- 在 **归档配置** 页面恢复配置后，前端停留在 **归档配置** 页面并显示恢复结果，可提供查看对应 **信息源** 或 **关注主体** 的链接
- **彻底删除** 只允许从 **设置** 中的归档入口触发，不作为 **信息源管理** 的行内常规操作；彻底删除配置对象时删除其 YAML 文件
- **彻底删除** 需要强确认，例如二次确认或输入 **配置对象 ID**
- 归档或 **彻底删除** 配置对象都不删除既有 **内容条目** 或 **采集记录**
- **归档配置** 第一版只覆盖 **关注主体** 和 **信息源**
- **采集通路**、**处理规则**、**存储配置** 和 **调度配置** 第一版不进入 **归档配置** 列表
- **内容浏览** 和 **采集记录** 仍展示来自归档 **信息源** 的历史来源名称，并用轻量状态标识该来源已归档
- **信息源** 被 **彻底删除** 后，既有 **内容条目** 和 **采集记录** 仍保留；来源显示应回退为“历史信息源”或“已删除配置”，并尽量保留原名称或 **配置对象 ID**
- **配置对象 ID** 使用人工可读 slug，**内容条目 ID** 使用 16 位十六进制字符串
- 当前阶段只规定模块共享的框架结构和 **信息源** 格式，不规定用户添加 **信息源** 的输入方式或 AI 识别策略
- 第一版前端实现前必须先具备 **本地 HTTP API** 契约和 **本地应用服务**，前端不直接读取 SQLite、写 YAML 或调用 CLI
- 第一版前端是连接 **本地 HTTP API** 的可操作界面，不做静态视觉原型作为主路径
- 第一版前端主工程放在 Feeds Agent 仓库内，外部 AIHOT 静态文件只作为视觉参考来源
- 第一版前端技术栈使用 Vite、React 和 TypeScript
- 第一版前端不引入重量级 UI 组件库，使用自有轻量组件和 `lucide-react` 图标承载 AIHOT 风格
- 第一版前端开发期通过 Vite 将 `/api` 代理到本地 **本地 HTTP API** 默认地址 `http://127.0.0.1:8765`，并保留 `VITE_API_BASE_URL` 覆盖能力
- 第一版 **本地 HTTP API** 按领域资源设计，而不是按页面数据设计；页面消费 `items`、`subjects`、`sources`、`routes`、`runs`、`processing`、`config-sync`、`install-plans` 和 `storage` 等资源接口
- **本地 HTTP API** 提供 `scheduler` 资源接口，用于读取和保存 **调度配置**、查看 **调度器** 运行状态并触发一次到期检查
- **本地 HTTP API** 提供 `processing` 资源接口，用于读取和保存 **处理规则** 中的 `pipeline` 与 `taxonomy`
- 第一版 `scheduler` 资源提供读取状态、保存启停配置和“检查到期信息源”动作
- `scheduler` 资源读取结果可以包含有限数量的到期 **信息源** 预览，用于 **定时采集** 页面展示调度状态
- `scheduler` 资源的到期检查动作只检查并触发到期 **信息源**，不等同于手动采集全部 **信息源**
- `sources` 资源负责返回单个 **信息源** 的 **定时采集** 摘要，例如最近尝试、最近成功、错误摘要和预计下次采集时间
- `sources` 资源负责保存单个 **信息源** 的启用状态和 **扫描频率**，不保存 **调度配置**
- 第一版 `sources` 资源可以提供只更新启用状态和 **扫描频率** 的轻量保存动作，避免定时采集设置重提交完整 **信息源** 配置
- `sources` 资源应提供轻量更新动作，用于保存 **信息源** 的启用状态、**扫描频率**、**关注主体** 归属、**信息源分组** 和归档状态，避免常规整理动作重提交完整 **信息源** 配置
- `scheduler` 资源负责返回全局 **调度器** 状态和有限的到期 **信息源** 预览，不替代 `sources` 资源的单源摘要
- **本地 HTTP API** 提供 **关注主体** 资源接口，用于列表、读取、创建和更新 **关注主体**
- `subjects` 资源应提供轻量更新动作，用于保存 **关注主体** 的名称、**主体分组**、描述、标签和归档状态
- **本地 HTTP API** 不提供按 **关注主体** 采集或启停的专用后端动作
- **主体分组** 不是独立资源对象；**本地 HTTP API** 不提供完整主体分组 CRUD
- **主体分组** 重命名或删除可以通过动作型资源表达，例如主体分组重命名动作批量修改匹配 **关注主体** 的 `group` 值，主体分组删除动作批量清空匹配 **关注主体** 的 `group` 值
- **归档配置** 应有独立读取入口，用于列出已归档 **关注主体** 和 **信息源**
- **归档配置** 的恢复动作只改变归档状态；**归档配置** 的 **彻底删除** 动作删除对应 YAML 文件
- 一个 **关注主体** 可以组织多个 **信息源**
- 没有关联 **信息源** 的空 **关注主体** 允许存在
- 一个 **关注主体** 可以表示人、组织、项目、品牌或关键词主题
- 当前阶段 **关注主体格式** 不包含显式主体类型字段
- 关键词主题类 **关注主体** 只表达用户关注的宏观主题，不保存具体搜索查询
- 具体搜索查询、平台约束和结果数量属于该主体下搜索入口 **信息源** 的 `params`
- **关注主体** 是 **信息源** 的宏观组织形式，**信息源** 是该主体下具体可采集的入口
- **关注主体** 关注用户以什么主题组织信息源，**信息源** 关注系统从哪里采集内容
- **关注主体** 不等同于 **信息源分组** 或 **主体分组**
- **主体分组** 和 **信息源分组** 表达内容领域分类，不表达 **信息源** 归属于哪个 **关注主体**
- **主体分组** 的增删改属于 **信息源管理** 的组织能力；**信息源分组** 第一版只作为 **信息源** 编辑字段，不提供独立分组管理页
- **关注主体** 是 **配置主存储** 中的独立配置对象
- **关注主体格式** 保存 **关注主体** 的名称、描述、**主体分组** 和归档状态
- **关注主体** 使用稳定的 **配置对象 ID** 作为 `id`
- **关注主体** 的显示名称保存在 `name`，重命名只修改 `name`，不修改 `id`
- 修改 **关注主体** 的 `id` 属于迁移操作，需要同步更新引用它的 **信息源**
- 一个 **关注主体** 可以拥有零个或一个 **主体分组**
- **主体分组** 是无注册表的自由字符串，不建立独立 YAML 文件或 SQLite 表
- 新增 **主体分组** 通过给一个或多个 **关注主体** 填写新的 `group` 值完成，不创建独立分组配置对象
- 重命名 **主体分组** 通过批量修改该分组下 **关注主体** 的 `group` 值完成
- 重命名 **主体分组** 时，如果新名称已经存在，应提示用户确认合并；确认后将原分组下 **关注主体** 批量移动到既有分组
- 删除 **主体分组** 通过批量清空该分组下 **关注主体** 的 `group` 值完成，被清空的 **关注主体** 进入“未分组”
- 删除 **主体分组** 不归档 **关注主体**、不归档 **信息源**，也不改变 **信息源** 的启用或停用状态
- 删除 **主体分组** 的确认文案应说明该动作只会让分组下 **关注主体** 进入“未分组”，不会删除 **关注主体** 或 **信息源**
- **信息源管理** 的主导航可以在顶层入口下展示 **主体分组**，用于帮助用户定位关注范围，不继续展开到具体 **关注主体** 或 **信息源**
- 主导航中的 **主体分组** 入口只表示 **信息源管理** 列表过滤；进入后右侧继续以 **关注主体** 折叠条组织 **信息源**
- **信息源管理** 在 **主体分组** 过滤视图中触发批量 **立即采集** 时，只采集当前 **主体分组** 下启用的 **信息源**，文案应表达当前分组范围
- **信息源管理** 未过滤时批量 **立即采集** 文案为“立即采集全部启用信息源”；按 **主体分组** 过滤时文案为“立即采集当前分组”
- **主体分组** 过滤视图中没有启用 **信息源** 时，“立即采集当前分组”不可用，且不产生空的 **采集运行**
- 主导航中的“未分组”表示没有 **主体分组** 的 **关注主体**，不包含未归属 **关注主体** 的 **信息源**
- **主体分组** 过滤视图不显示“未归属”虚拟区域；未归属 **关注主体** 的 **信息源** 只在全量 **信息源管理** 中展示
- 用户进入不存在或已变更的 **主体分组** 过滤入口时，应回到全量 **信息源管理** 并轻量提示分组不可用
- **主体分组** 名称变更后，旧 **主体分组** 过滤入口按分组不可用处理，不自动映射到新分组名称
- 当 **主体分组** 下不再有任何 **关注主体** 时，该分组不再出现在主导航中；如果用户正停留在该过滤视图，应按分组不可用处理
- **主体分组** 过滤入口使用 **主体分组** 名称本身作为可还原的入口身份，不额外生成分组 slug 或第二套分组身份
- 主导航中的“未分组”是固定虚拟过滤入口，表示 **主体分组** 为空的 **关注主体**；它不是一个真实 **主体分组** 名称，也不等同于全量 **信息源管理**
- **主体分组** 子导航只在用户位于 **信息源管理** 区域时展开，其他产品区域只保留 **信息源管理** 顶层入口
- 主导航中的 **信息源管理** 顶层入口始终进入全量 **信息源管理**，不作为 **主体分组** 子导航的展开或收起控制
- 主导航中的 **主体分组** 按名称排序，“未分组”固定放在最后；第一版不提供 **主体分组** 自定义排序
- 主导航中的 **主体分组** 子项显示 **关注主体** 数量，不显示 **信息源** 数量
- 主导航中的 **主体分组** 子项应包含该分组下没有 **信息源** 的空 **关注主体**
- 左侧 **主体分组** 导航可以在分组项上提供分组级菜单，用于重命名或删除该 **主体分组**
- 第一版不提供复杂批量选择来新建 **主体分组**；新 **主体分组** 通过新建或编辑 **关注主体** 时填写新的 `group` 值自然产生
- 第一版 **信息源管理** 不提供通用多选批量整理操作；保留明确范围的批量 **立即采集**，整理类动作通过行内“移动/归档”和分组菜单“重命名/删除”完成
- 用户选择 **主体分组** 过滤视图时，主导航中的 **信息源管理** 顶层入口和对应 **主体分组** 子项都应呈现选中状态；全量 **信息源管理** 只选中顶层入口
- 用户从 **主体分组** 过滤视图进入具体 **信息源** 详情时，主导航应保留该 **主体分组** 选中状态；直接进入详情或从全量列表进入详情时，只选中 **信息源管理** 顶层入口
- **信息源管理** 的 **主体分组** 过滤视图应轻量展示当前分组状态，并提供回到全部 **信息源管理** 的入口
- 用户从 **主体分组** 过滤视图进入具体 **信息源** 详情后，返回列表时应保留原 **主体分组** 过滤上下文
- 用户从 **主体分组** 过滤视图进入添加 **信息源** 时，添加体验可以预选该分组下的 **关注主体**，但不限制用户选择其他 **关注主体**；保存后返回原 **主体分组** 过滤视图
- 用户切换 **主体分组** 过滤视图时，右侧 **关注主体** 折叠状态不跨分组保留，默认沿用 **信息源管理** 页面全部折叠的规则
- 用户在 **主体分组** 过滤视图中将 **信息源** 移动到其他 **关注主体** 后，如果该 **信息源** 不再属于当前 **主体分组**，保存后继续停留在当前过滤视图且该 **信息源** 从列表中消失
- 用户在 **主体分组** 过滤视图中将 **关注主体** 移动到其他 **主体分组** 后，保存后继续停留在原过滤视图且该 **关注主体** 从列表中消失；如果原分组因此变空，应按分组不可用处理
- **关注主体** 可以使用标签补充 **主体分组** 之外的分类
- 一个 **信息源** 可以拥有零个或一个 **信息源分组**
- **信息源** 归属于 **关注主体** 的关系，独立于 **主体分组** 和 **信息源分组**
- **信息源分组** 不自动继承 **主体分组**
- 前端在 **关注主体** 下创建 **信息源** 时可以用 **主体分组** 预填 **信息源分组**，但保存后两者独立
- **关注主体** 标签不自动继承或默认预填到 **信息源标签**
- **信息源格式** 通过 `subject.subject_id` 引用 **关注主体**
- 一个 **信息源** 可以归属零个或一个 **关注主体**
- 非空 `subject.subject_id` 必须引用已存在的 **关注主体**
- `subject.subject_id` 为空表示未归属 **关注主体**
- 当前阶段 **关注主体** 与 **信息源** 是一对多关系，不支持 **信息源** 多主体归属
- 移动 **信息源** 的 **关注主体** 归属只改变 **信息源管理** 组织关系，不重写已采集 **内容条目**
- **信息源管理** 列表行可以提供轻量“移动”动作，用于快速更换 **信息源** 的 **关注主体**
- **信息源** 详情页提供完整编辑入口，可同时修改名称、**关注主体**、**信息源分组**、标签、目标、**采集意图** 和默认 **采集通路**
- 没有归属 **关注主体** 的 **信息源** 允许存在
- 前端以 **关注主体** 组织 **信息源** 时，应将未归属 **信息源** 放入“未归属”虚拟区域
- “未归属”不是 **关注主体**，不写入 `config/subjects/`
- **信息源管理** 中“未归属”显示为固定虚拟折叠条，展开后显示未归属 **信息源**
- “未归属”虚拟折叠条不提供 **主体分组** 或主体标签编辑
- **关注主体** 的启用或停用是前端批量操作语义，会同步应用到主体下绑定的所有 **信息源**
- **关注主体格式** 不保存 `status.enabled`
- **关注主体格式** 可以保存 `status.archived`，用于让空 **关注主体** 退出常规 **信息源管理** 视图并进入 **归档配置**
- 前端中的 **关注主体** 开关由其下 **信息源** 的启停状态派生，可以呈现全部启用、全部停用或部分启用
- 前端可以提供按 **关注主体** 触发采集的批量操作，但执行时展开为该主体下启用 **信息源** 的采集
- 后端不需要提供按 **关注主体** 采集的独立领域操作，**采集运行** 仍记录 **信息源** 列表
- **信息源** 自身的启用或停用只作用于该 **信息源**
- 后端采集执行不对 **关注主体** 启停做深度处理，仍以 **信息源** 自身启停状态作为执行依据
- **信息源管理** 中移除 **关注主体** 或 **信息源** 的常规动作是归档，不是 **彻底删除**
- 第一版不在 **信息源管理** 中提供硬删除 **关注主体**
- 归档空 **关注主体** 前需要轻确认，文案应说明会移入 **归档配置** 且可恢复
- 非空 **关注主体** 不能直接归档；归档 **关注主体** 前必须先将其下 **信息源** 移动到其他 **关注主体**、变为未归属或逐个归档
- 用户尝试归档非空 **关注主体** 时，不进入确认流程，应直接阻止并提示先移动、设为未归属或归档其下 **信息源**
- 删除 **关注主体** 配置前必须先将其下 **信息源** 移动到其他主体、变为未归属或归档
- 一个 **信息源** 可以暂时没有可用的 **采集通路**，但不应因此丢失
- 一个 **信息源** 的生命周期独立于 **采集通路**，可以先保存、后匹配、再采集
- 配置层不硬性禁止重复 **信息源**
- **信息源管理** 添加或编辑时应提示疑似重复 **信息源**
- **信息源格式** 暂不包含固定 kind 或 category 字段，先用 **信息源分组** 和 **信息源标签** 承载可扩展归类
- **信息源分组** 只表达 **信息源** 的内容领域分类，不表达 **关注主体** 归属
- **信息源格式** 中的 `subject.subject_id` 保存 **关注主体** 的 **配置对象 ID**
- 当前阶段 **信息源格式** 不包含主体内角色或用途字段
- **信息源格式** 中的 `target` 保存用户可识别的稳定入口，`params` 保存 **采集通路** 执行所需的结构化参数
- `target` 不应被当作 **采集通路** 专用参数容器
- **信息源标签** 属于信息源配置，不等同于内容条目的 AI 标签或分类结果
- **关注主体** 标签属于主体组织配置，不自动继承到 **内容条目**
- **条目标签** 按来源结构化保存，不通过字符串前缀区分来源
- **内容索引** 保存结构化 **条目标签**，不只保存合并后的标签列表
- 一个 **信息源** 通过 **通路匹配** 获得一个或多个候选 **采集通路**
- **通路匹配** 只使用 **信息源** 的目标入口、参数、**采集意图** 和 **采集通路** 能力，不使用 **关注主体** 字段
- 一个 **信息源** 在常规采集中只使用一个默认 **采集通路**，用户可以手动切换
- **信息源格式** 中的 `route.default_route_id` 可以为空，表示待匹配或未指定通路
- 候选 **采集通路** 和匹配结果属于运行状态，可在 **信息源** 详情中展示，但不写入 **配置主存储**
- 用户确认默认 **采集通路** 后，只将 `route.default_route_id` 写入 **信息源格式**
- 一个 **信息源** 可以属于零个或一个 **信息源分组**
- **信息源分组** 是无注册表的自由字符串，不建立独立 YAML 文件或 SQLite 表
- **信息源分组** 和 **主体分组** 可以使用相同的内容领域词汇，但作用在不同对象上
- **关注主体** 不是多对多的关注集合对象，不用于表达 **信息源** 多集合归属
- 一个 **信息源** 拥有一个 **采集意图**
- **采集意图** 直接绑定在 **信息源** 上，配置字段名为 `intent.type`，不属于 `scan`
- 第一批 **采集意图** 为 `track_page_change`、`collect_new_items` 和 `collect_all_items`
- `track_page_change` 表示用户要跟踪一个目标页面或入口本身的变化
- `collect_new_items` 表示用户要从一个入口持续获取当前候选窗口内的新内容条目
- `collect_all_items` 表示用户要从一个入口尽可能获取可达的全部内容条目候选
- `track_page_change` 下同一 **信息源** 始终对应同一个 **内容条目**
- `collect_new_items` 和 `collect_all_items` 下每个采集结果按外部 ID 或规范化 URL 形成独立 **内容条目**
- **采集意图** 不表达 **条目发现**、**完整内容采集** 或 **批量详情采集** 等采集执行形态
- 平台账号、公众号、RSS、搜索结果、通知列表和热榜通常使用 `collect_new_items`
- 文档页、公告页、价格页和状态页通常使用 `track_page_change`
- **采集意图** 不表达 **平台**、**采集通路** 或 **关注主体**
- **列表页面** 通常使用 `collect_new_items`
- 通用列表抽取能力属于 **采集通路**，不属于单个 **信息源**
- 特定 **列表页面** 的 **列表抽取参数** 属于 **信息源** 的 `params`
- 第一版 **列表抽取参数** 最小只包含 `item_selector`
- **分页识别规则** 默认由 **采集通路** 提供，不要求每个 **信息源** 配置
- 单个 **信息源** 只有在页面结构特殊或默认分页识别失败时，才通过 `params` 覆盖 **分页识别规则**
- **列表页面** 默认使用列表项中的第一个链接作为详情页链接
- **列表页面** 默认使用列表项链接文本作为标题，缺失时使用列表项文本
- `track_page_change` 可以使用 **快照抽取参数** 只监测目标页面的局部内容
- **快照抽取参数** 属于 **信息源** 的 `params`
- **快照抽取参数** 是高级可选参数，不作为第一版添加 `track_page_change` 信息源的必填或主配置
- 未配置 **快照抽取参数** 时，`track_page_change` 默认使用通用网页正文或整页内容
- **快照抽取参数** 仍然只产生一个 **内容条目**，不产生多个列表条目
- **列表抽取参数** 用于从一个入口产生多个 **内容条目**，不同于 **快照抽取参数**
- **内容清洗** 绑定在单个 **信息源** 上，因为网页结构和 API 返回字段通常由具体 **信息源** 决定
- **清洗配置** 保存在 **信息源格式** 顶层 `cleaning` 字段，不塞入 `params`
- SQLite 中的 **信息源** 配置快照使用 `sources.cleaning_json` 保存 **清洗配置**，不复用 `params_json`
- **本地 HTTP API** 返回和保存 **信息源** 时应保留顶层 `cleaning` 边界，不把清洗配置折叠进 `params`
- **本地 HTTP API** 和前端类型返回和保存 **信息源 AI 处理开关** 时使用顶层 `ai_processing` 对象，不展开为 `ai_processing_enabled` 字段
- 前端 **信息源** 详情展示 **清洗配置** 摘要、**清洗状态**、启停入口，并允许直接编辑 **清洗脚本** 路径和 `options`
- 前端 **信息源** 详情提供独立的 **AI 处理** 面板编辑 **信息源 AI 处理开关**；**信息源管理** 列表最多轻量展示状态，不作为主编辑入口
- **内容浏览** 卡片不为关闭 **信息源 AI 处理开关** 的内容条目新增醒目的“跳过 AI 处理”状态，只保留缺少 AI 结果时的普通空态
- YAML 仍是 **清洗脚本** 路径和 `options` 的配置来源之一，UI 保存会写回对应 **信息源** 配置
- **清洗配置** 不属于 **处理规则**；它发生在 **处理流水线** 之前，不生成 AI **处理结果**
- **信息源 AI 处理开关** 只决定对应 **信息源** 的内容版本是否进入 **处理流水线**，不覆盖全局 **处理规则**
- **信息源 AI 处理开关** 保存在 **信息源格式** 顶层 `ai_processing.enabled` 字段，缺省视为开启
- 既有 **信息源格式** 不需要批量写入 `ai_processing.enabled: true`；只有用户明确关闭时才需要写出 `ai_processing.enabled: false`
- **信息源** 的 `status.enabled` 和 `ai_processing.enabled` 相互独立；停用采集不自动改变 AI 处理开关，关闭 AI 处理也不影响采集
- **内容清洗** 作用于 **标准采集结果** 保存为 **原始内容版本** 之前，可以影响展示内容、内容指纹和后续 **待处理条目** 输入
- **原始内容** 应保留采集后端返回的未清洗载荷，便于调试、回溯和重新生成清洗结果
- **内容指纹** 基于清洗后的展示内容计算，不以未清洗 **原始内容** 作为主要变化判断输入
- **清洗降级保存** 或 `status: skipped` 时，**内容指纹** 基于降级或默认生成的展示内容计算
- 第一版 **清洗配置** 最小字段为 `enabled`、`script.path` 和 `options`
- 第一版单个 **信息源** 只支持引用一个 **清洗脚本**，不提供 steps、链式清洗或多个脚本编排
- 需要复合清洗逻辑时，第一版由单个 **清洗脚本** 内部处理
- `cleaning.script.path` 可以是相对路径或绝对路径
- 相对 `cleaning.script.path` 按 Feeds Agent 仓库根目录解析，优先鼓励脚本随项目配置一起版本管理
- 绝对 `cleaning.script.path` 允许用于个人本机脚本，但保存和执行时不自动展开 `~`
- 第一版 **清洗脚本** 必须是可执行文件，统一采集执行按 `[script.path]` 直接启动
- 第一版 **清洗配置** 不提供 `command` 数组或额外命令参数；Python、Node 或复杂环境通过 shebang 或 wrapper 脚本承接
- **清洗脚本** 执行时工作目录为 Feeds Agent 仓库根目录
- **配置同步** 只校验 **清洗配置** 的结构和字段类型，不检查 `cleaning.script.path` 对应文件是否存在或可执行
- `cleaning.enabled: true` 但 **清洗脚本** 缺失或不可执行时，采集时按清洗失败处理，进入 **清洗降级保存**
- 第一版 **清洗配置** 可以引用 **清洗脚本**，因为 Feeds Agent 是个人 **本地优先** 应用，用户可以选择信任本机脚本
- **清洗脚本** 只能转换 **标准采集结果** 的内容表示，不直接写入 **内容存储**、**内容索引** 或 **处理结果**
- **清洗脚本** 的执行仍属于 **统一采集执行** 的保存前环节，不能绕开内容身份、内容指纹、原始内容版本和采集运行事件边界
- **清洗脚本契约** 使用 stdin/stdout JSON，不使用脚本直接读写 SQLite 作为公共接口
- 统一采集执行传给 **清洗脚本** 的输入应包含 **标准采集结果** 字段、`source_id`、`source.target`、`source.params` 和 `cleaning.options`
- **清洗脚本契约** 的输入必须包含完整 `raw_content` 和 `raw_content_type`，因为网页或 API 原始载荷是 **内容清洗** 的主要处理对象
- 第一版 **清洗脚本** 输入不截断 `raw_content`；超大内容的输入上限留到后续阶段处理
- **清洗脚本** 输出必须包含 `display_content` 和 `display_content_type`，可以选择返回 `title`、`published_at` 和 `metadata_patch`
- **清洗脚本** 输出的 `display_content_type` 必须非空，`display_content.strip()` 必须非空，才视为清洗成功
- **清洗脚本** 退出成功但输出空展示内容时，按清洗失败处理并进入 **清洗降级保存**
- **清洗脚本** 输出的可选 `title` 和 `published_at` 只有在非空且格式可接受时才覆盖 **标准采集结果** 对应字段
- **清洗脚本** 输出的空字符串或 `null` 可选字段不覆盖 **标准采集结果** 原值
- **清洗脚本** 不返回或覆盖 `raw_content`；**原始内容** 始终保留采集后端返回的未清洗载荷
- **清洗脚本** 不返回或覆盖 `url`、`canonical_url`、`final_url` 或 `external_id`，不参与 **内容身份别名** 和 **内容条目 ID** 判定
- **清洗脚本** 返回的 `metadata_patch` 保存到 `content_versions.metadata_json.cleaning.output`，不覆盖采集后端元数据顶层字段
- 第一版 **清洗脚本** 固定超时为 30 秒，不按单个 **信息源** 配置超时时间
- **清洗脚本** 超时按清洗失败处理，进入 **清洗降级保存**，并在 **清洗状态** 中记录 timeout 错误
- 第一版 **清洗脚本** 失败时采用 **清洗降级保存**，不因为清洗失败丢弃已采集内容
- **清洗降级保存** 应产生 `item_cleaning_failed` **清洗失败事件**，不使用 `item_failed`，也不静默合并进普通 `item_saved`
- `item_cleaning_failed` 应计入 **采集运行** 的 `failed_count`
- 一条内容发生 **清洗降级保存** 时可以同时增加 `saved_count` 和 `failed_count`，使本次 **采集运行** 表达为部分成功
- **清洗降级保存** 使用统一采集执行的默认展示内容生成逻辑保存 **原始内容版本**
- **清洗降级保存** 必须记录清洗失败状态，不能把未清洗内容伪装成清洗成功内容
- **清洗降级保存** 形成的 **原始内容版本** 仍然进入 **待处理条目**，不因清洗失败阻塞 AI **处理流水线**
- AI **处理结果** 应能从绑定的 **原始内容版本** 元数据追溯本次输入是否来自清洗成功或清洗降级保存
- 第一版正常流程是先 **内容清洗**，再进入 AI **处理流水线**
- 第一版 **内容清洗** 不设计针对既有 AI **处理结果** 的失效、迁移或自动重算机制
- 第一版 **清洗状态** 保存在 `content_versions.metadata_json.cleaning`，不新建独立清洗运行表
- **清洗状态** 最小包含 `status: succeeded | fallback | skipped`、`script_path`、`finished_at`、`error` 和 `output_fingerprint`
- 未配置 **清洗配置** 或 `cleaning.enabled: false` 时，**清洗状态** 记录为 `status: skipped`
- `status: skipped` 应通过 `reason: not_configured | disabled` 区分未配置和显式关闭
- **重新清洗** 使用已保存 **原始内容** 和当前 **清洗配置**，不重新请求网页或 API
- **重新清洗** 不等同于 **重新采集**，不会新增外部内容发现、更新扫描进度或触发通路后端访问
- **重新清洗** 不等同于 **重处理**，第一版不要求重新清洗自动触发既有 AI **处理结果** 重算
- 第一版 **重新清洗** 可以先支持按单个 **信息源** 重新清洗最新 **原始内容版本**
- **重新清洗** 成功后覆盖同一 **原始内容版本** 的展示内容和 **清洗状态**，不新增 `content_versions.version`
- **原始内容版本** 表达外部原始内容变化，不表达本地 **清洗配置** 或 **清洗脚本** 的变化
- **重新清洗** 应在 **清洗状态** 中记录清洗时间、脚本路径、脚本指纹或输出指纹等追溯信息
- **列表页面** 通过 **条目发现** 先产生 **条目候选**，再由 **统一采集执行** 判断候选是否对应已知 **内容条目**
- **条目候选** 最小必须包含可生成稳定 **内容条目 ID** 的外部 ID 或规范化 URL，不允许用内容哈希作为候选身份兜底
- **条目候选** 可以携带标题、详情入口、列表项原始内容或发布时间，但不强制要求详情入口
- **条目候选** 的外部 ID 或规范化 URL 是 `collect_new_items` 和 `collect_all_items` 的稳定身份
- `collect_new_items` 默认只从列表入口当前候选窗口取 `scan.limits.max_items` 个 **条目候选**，不主动跟随“下一页”等分页入口扩展候选列表
- `scan.limits.max_items` 的默认值为 20，可配置；第一版 UI 可以先不突出暴露该配置
- `scan.limits.max_items` 是单次采集的候选总上限，不是每页上限；`collect_all_items` 跨分页累计计数
- `collect_all_items` 会尽可能获取列表入口可达的全部 **条目候选**；遇到“下一页”等分页入口时，会继续进入后续页面获取更多候选
- `collect_all_items` 使用 **采集通路** 默认 **分页识别规则** 扩展候选列表；单个 **信息源** 的分页覆盖只处理特殊页面
- `collect_all_items` 的“全部”限定为从目标入口和分页入口可达的 **条目候选**，并受分页能力和 `scan.limits.max_items` 总上限等安全边界限制
- `collect_all_items` 的 **分页停止条件** 包括达到 `scan.limits.max_items` 总上限、没有下一页、下一页 URL 已访问过或分页请求失败
- `collect_all_items` 命中 **分页停止条件** 后不再继续翻页，已经发现的 **条目候选** 继续进入后续采集流程
- `collect_new_items` 和 `collect_all_items` 都先把发现到的 **条目候选** 交给 **统一采集执行** 做已知候选预检查；只有未知候选才进入后续 **完整内容采集** 和 `collect.py` 的内容存储去重
- 内容存储去重对已经形成 **标准采集结果** 的内容生效：已存在 **内容条目** 且内容指纹未变化时只记录再次看到，内容指纹变化时新增 **原始内容版本**
- `collect_new_items` 和 `collect_all_items` 遇到已知 **条目候选** 时，不执行 **完整内容采集**、不比较内容指纹、不新增 **原始内容版本**，只更新 **内容索引** 的再次看到状态
- **列表页面** 的新增条目必须在同次采集中完成 **完整内容采集** 并返回完整 **标准采集结果**
- **列表页面** 不保存只有链接的占位 **内容条目**，也不依赖后续二阶段详情抓取队列
- **列表页面** 在 `collect_new_items` 下只处理当前列表候选窗口内 `scan.limits.max_items` 限制的 **条目候选**
- **列表页面** 在 `collect_new_items` 下不主动进入下一页，不承担历史回溯或全站导入职责
- **列表页面** 如果需要获取入口可达的全部候选或跨分页回溯，应使用 `collect_all_items`
- `collect_all_items` 可以作为显式 **采集意图** 配置，第一版没有明确产品需求时不作为默认选择
- 一个 **信息源** 拥有 **扫描配置**，用于控制 **定时采集** 和单次采集的安全边界
- **采集意图** 保存在 **信息源格式** 顶层，使用 `intent.type` 表达
- `intent.type` 取值为 `track_page_change | collect_new_items | collect_all_items`
- `intent.type` 只允许表达用户想跟踪目标变化、获取新内容还是采集本次发现的全部条目，不表达平台、账号、列表、公众号或内容业务类型
- 新配置、同步后的 SQLite 结构、本地 HTTP API 和前端表单都应使用 `intent.type`，不保留 `scan.semantics` 或 `scan.mode` 作为并行公共契约
- 旧配置中的 `scan.semantics` 和 `scan.mode` 只能由一次性配置迁移工具读取并改写为 `intent.type`
- 主同步、采集运行、本地 HTTP API 和前端运行路径不应把 `scan.semantics` 或 `scan.mode` 当作合法输入继续解析
- 未显式配置 `intent.type` 的 **信息源** 可以由 **采集通路** 默认值或系统匹配结果补齐
- **通路匹配** 时，**信息源** 的 `intent.type` 优先于 **采集通路** 的默认 **采集意图**
- **采集通路** 的 `capability.supported_intents` 表达兼容范围，`capability.default_intent` 只用于补齐未指定 **采集意图** 的 **信息源**
- 已声明 **采集意图** 的 **信息源** 只应匹配支持该意图的 **采集通路**
- 用户选择不兼容 **采集通路** 时应得到可解释提示，不应被系统静默覆盖或静默采集
- **扫描配置** 不保存 `mode`，单次 **采集运行** 也不覆盖 **采集意图**
- **扫描进度** 属于 **信息源** 与 **采集通路** 的组合，不属于单独的 **信息源**
- `source_routes` 属于 SQLite 运行状态和通路匹配结果，不属于 YAML 配置
- `collect_new_items` 只负责发现当前列表候选窗口内 `scan.limits.max_items` 限制的 **条目候选**，不主动进入下一页扩展候选列表
- `collect_all_items` 负责从目标入口和可识别分页入口尽可能发现全部 **条目候选**，再交给 **统一采集执行** 做已知候选预检查
- `collect_new_items` 和 `collect_all_items` 的已知 **条目候选** 不作为内容变化检查目标；`track_page_change` 仍用于跟踪单个目标入口本身的变化
- `collect_all_items` 不遍历该 **信息源** 历史上曾经保存过但当前入口不可达的全部 **内容条目**
- `collect_all_items` 受分页能力或 `scan.limits.max_items` 总上限等安全边界限制
- `collect_new_items` 历史 **内容条目** 未在本次入口中出现，不表示内容被删除，也不触发状态删除
- `collect_all_items` 历史 **内容条目** 未在本次入口中出现，也不表示内容被删除或下架
- `track_page_change` 每次采集目标入口本身，并通过内容指纹判断是否产生新的 **原始内容版本**
- 一个 **采集通路** 可以服务零个或多个 **信息源**
- 一个 **采集通路** 归属于一个 **平台** 或一个通用类别
- 通用 **采集通路** 使用 `platform: "generic"`，不使用空平台值
- **采集后端** 是 **RouteBackend** 的中文规范词，不表示 Web/API 服务端
- Feeds Agent 拥有 **统一采集执行**，不把上游工具的直接调用结果视为权威采集记录
- 一个 **RouteBackend** 拥有 **配置难度**，用于帮助用户判断配置成本
- **采集通路** 等同于 **RouteChannel**，不等同于 **RouteBackend**
- 一个 **采集通路** 只表达一个主要采集能力，`capability.name` 保持单数
- **采集通路** 可以声明支持的 **采集意图** 和默认 **采集意图**
- **采集通路** 的意图兼容性保存在 `capability.supported_intents` 和 `capability.default_intent`
- **采集通路** 的 `capability.name` 不等同于 **信息源** 的 `intent.type`
- 同一 **采集后端** 可以被多个 **采集通路** 复用，但不应通过一个 **采集通路** 承载多个主要采集能力
- 一个 **采集通路** 可以拥有多个 **替代采集后端**，用户或系统可以根据可用性和需求切换默认采集后端
- **采集后端** 只返回 **标准采集结果**，不直接写入 **内容存储** 或知识库文档
- **采集后端** 可以为 `collect_new_items` 或 `collect_all_items` 返回 **条目候选**，但候选范围控制和 **内容条目 ID** 判定属于 **统一采集执行**
- **采集后端** 可以用 **批量详情采集** 提升执行效率，但统一采集执行仍按单个 **条目候选** 进行身份、去重和保存判断
- 最小版本中每个 **标准采集结果** 必须包含可保存的 **原始内容**，不支持只发现链接后排队二次抓取
- **标准采集结果** 最小字段固定为 `title`、`raw_content`、`content_type` 必填，`url` 和 `external_id` 至少一个，`published_at`、`platform`、`metadata` 可选
- **标准采集结果** 的 `content_type` 只表达 **原始内容** 格式，不表达 tweet、video 或 article 等业务类型
- **标准采集结果** 不包含 **采集意图** 字段
- **统一采集执行** 根据 **信息源** 的 `intent.type` 判断 **标准采集结果** 应产生新 **内容条目** 还是新 **原始内容版本**
- 跨 **信息源** 重复发现同一 **内容条目** 时的归属和去重策略留到后续阶段，不作为当前 **RouteBackend** 配置目标
- 一个 **采集通路** 拥有一个或多个 **通路自检** 输入样例
- **通路自检** 的配置保存在 **配置主存储**，**通路自检结果** 保存在 SQLite
- 涉及安装工具、写入外部配置或改变用户本机环境的 **采集能力管理** 操作必须先生成 **安装计划**，用户确认后才能执行
- **采集通路** 关注“能否拿到内容”，**信息源** 关注“用户关心什么”，**处理规则** 关注“内容如何变得可用”
- **采集通路** 可以是通用能力，例如 RSS 或公开静态网页，也可以是平台内能力，例如某平台的个人主页、关键词搜索或榜单页面
- **CLI 采集后端** 使用 `backends[].method: cli_tool`，认证信息仍通过 **凭据引用** 或 CLI 自身配置管理
- **CLI 采集后端** 的命令细节先放在 `backends[].extra`，不升成通用字段
- **RouteBackend** 的 **标准采集结果** 必须经过 **统一采集执行** 适配后，才能保存为 **内容条目** 和 **原始内容**
- **内容条目 ID**、原始内容版本号和 **内容存储** 写入由 **统一采集执行** 生成，不由 **采集后端** 生成
- 一个 **RouteChannel** 对应一类 **采集通路** 能力，可以包装一个或多个 **RouteBackend**
- **RouteBackend** 负责具体采集执行，**RouteChannel** 负责能力边界、自检和统一输出适配
- **RouteChannel** 和 **RouteBackend** 都拥有自检；Channel 自检验证采集通路端到端能力，Backend 自检验证具体执行后端是否可用
- **RouteBackend** 自检不包含 sample，**RouteChannel** 自检使用 `target + params` sample
- 最小版本中 **RouteChannel** 使用第一个启用的 **RouteBackend** 作为默认后端，不自动 fallback 到其他后端
- **采集通路配置格式** 中的 `capability` 描述 **RouteChannel** 能力，`backends[].method` 描述 **RouteBackend** 的访问方式
- **配置难度** 使用 `backends[].setup.tier` 表达，取值为 `zero_config | simple_auth | complex_setup`
- 当前 **RouteBackend** 配置阶段优先覆盖低摩擦 **采集通路**，包括 RSS、通用网页、视频、代码仓库、社区内容、搜索结果和公开页面
- 用户体验中的 **采集通路** 列表以能力为主展示，并显示其所属 **平台** 或通用类别
- **采集通路** 页面提供 **通路自检** 和按通路批量触发 **采集运行** 的入口，但不作为采集结果的主要归属对象
- **RouteBackend** 可以通过 **凭据引用** 声明认证依赖，但不保存凭据本体
- `auth_required` 表达 **RouteBackend** 是否理论上需要认证，`credential_ref` 表达当前是否配置了凭据引用
- 当前阶段只规范 **凭据引用** 命名，不定义凭据存储格式
- 当列表项本身包含可保存的原始内容时，可以直接以列表项内容生成 **标准采集结果**
- 当 **条目候选** 自身已经包含可保存的 **原始内容** 时，可以不使用 **详情采集配置**，直接升级为 **标准采集结果**
- 当 **条目候选** 缺少可保存的 **原始内容** 且没有可访问详情入口时，不应创建 **内容条目**
- **列表页面** 条目不能只保存空壳链接；详情页可访问时优先保存详情内容
- **列表页面** 的详情内容默认来自列表项链接指向的页面
- **详情采集配置** 默认由执行 **条目发现** 的 **采集通路** 声明
- 单个 **信息源** 只有在需要特殊详情处理时，才覆盖默认 **详情采集配置**
- **条目候选** 只有在聚合列表、搜索结果或跨平台入口等详情来源不一致时，才覆盖默认 **详情采集配置**
- 平台专用 **条目发现** 默认优先使用同平台专用 **采集通路** 完成详情内容采集
- 只有缺少同平台专用详情采集能力、详情入口是公开网页且通用解析足够时，才回落到通用网页 **采集通路**
- **详情采集配置** 选择的是用于 **完整内容采集** 的一个或多个有序 **采集通路**，不是独立的异步详情队列
- **详情采集配置** 的回退通路只在同次采集中尝试，不形成持久详情重试队列
- **详情采集配置** 不直接指定 **采集后端**，具体 **采集后端** 仍由被选中的 **采集通路** 按优先级、自检和可用性决定
- **详情采集配置** 不改变最终 **内容条目** 的 **采集意图**，最终意图仍来自原始 **信息源**
- **批量详情采集** 只是 **完整内容采集** 的执行优化，不改变 **条目候选**、**内容条目** 或 **标准采集结果** 的领域边界
- **批量详情采集** 可以一次获取多个 **条目候选** 的详情，但返回后必须拆成多个 **标准采集结果**
- **批量详情采集** 允许部分成功；成功候选照常保存，失败候选不创建 **内容条目**
- **批量详情采集** 中的失败候选必须记录为 **采集运行事件** 并增加失败计数，不能被静默忽略
- 详情失败的 **条目候选** 不进入持久重试队列，后续只有再次被入口发现时才重新尝试 **完整内容采集**
- **完整内容采集** 可以补充标题、正文、发布时间、最终 URL、canonical URL、平台外部 ID 和元数据，但不覆盖 **条目候选** 已确定的稳定身份
- 详情内容提供的 canonical URL 或平台外部 ID 应记录为 **内容身份别名**，不直接替换已经生成的 **内容条目 ID**
- 创建新 **内容条目** 前，如果任一 **内容身份别名** 已经映射到既有 **内容条目**，本次候选应视为既有条目的再次出现，不创建新 **内容条目**
- 创建新 **内容条目** 前命中的既有条目可以追加本次候选 URL 等新 **内容身份别名**，但不新增 **原始内容版本**，也不自动做内容合并
- 如果 **完整内容采集** 已经取得 **原始内容** 后才发现 **内容身份别名** 命中既有 **内容条目**，本次 **原始内容** 作为未保存执行产物丢弃，不写入 **原始内容版本**
- 晚到的 **内容身份别名** 命中既有 **内容条目** 时，不做内容指纹比较，不触发已知内容刷新
- 晚到的 **内容身份别名** 命中既有 **内容条目** 时，应记录 `type = item_seen`、`status = succeeded` 的 **采集运行事件**
- 已经存在两个 **内容条目** 后，如果新的 canonical URL 或平台 ID 证明二者疑似重复，第一版只记录 `identity_conflict` **采集运行事件**，不自动合并两个 **内容条目**
- 第一版 **列表页面** 不配置单独的详情抽取选择器
- 当 RSS、公开 API 或平台专用 **采集通路** 可用时，优先使用专用 **采集通路** 而不是通用列表抽取
- 跟踪通用网页变化和通用网页 **列表页面** 抽取使用不同 **采集通路**
- `generic-web` 保留为通用网页变化跟踪采集通路，默认 **采集意图** 为 `track_page_change`
- `generic-web-list` 作为通用 **列表页面** 抽取采集通路，默认 **采集意图** 为 `collect_new_items`
- `generic-web-list` 默认 **详情采集配置** 指向 `generic-web` **采集通路**，不直接指定 `jina-reader` **采集后端**
- **扫描频率** 属于 **扫描配置**，最小版本使用分钟级间隔表达
- **扫描频率** 可以为空，表示不启用定时采集
- **扫描频率** 按单个 **信息源** 配置，不提供全局 **扫描频率** 作为配置主存储
- 新建 **信息源** 默认不启用 **定时采集**，`scan.schedule.interval_minutes` 为空
- **信息源** 启用表示允许被手动或批量 **采集运行** 选择，不等同于启用定时采集
- 停用的 **信息源** 不参与 **立即采集** 或 **定时采集**
- 停用 **信息源** 不清空其 **扫描频率**，重新启用后原定时采集配置仍然有效
- 前端配置 **扫描频率** 时以少量预设档位为主，并允许高级自定义分钟数
- 第一版 **扫描频率** 预设档位为 15 分钟、1 小时、6 小时和 24 小时
- 自定义 **扫描频率** 的最小间隔为 15 分钟
- 用户开启 **定时采集** 时，`collect_new_items` 默认 **扫描频率** 为 1 小时，`track_page_change` 默认 **扫描频率** 为 6 小时
- 新建 **信息源** 时可以开启 **定时采集**；默认关闭，开启后再写入 **扫描频率**
- `collect_all_items` 信息源开启 **定时采集** 时，用户必须明确选择 **扫描频率**，不使用自动默认频率
- 15 分钟是用户主动选择的高频 **扫描频率**，不作为新配置默认值
- **定时采集** 使用 **信息源** 的 **采集意图** 和 **扫描配置**，不再读取独立 **扫描模式**
- `collect_all_items` 允许配置 **定时采集**，但不作为默认选择；执行时必须继续受分页能力和 **扫描配置** 中安全边界限制
- **调度器** 不排除显式配置了 **扫描频率** 的 `collect_all_items` **信息源**
- 一次 **采集运行** 以 **信息源** 为主要执行单位，可以覆盖一个或多个 **信息源**，并产生零个或多个 **内容条目**
- **立即采集** 触发一次 `manual` **采集运行**，但不修改 **扫描配置** 或 **调度配置**
- **立即采集** 可以作用于单个 **信息源**，也可以作用于全部启用的 **信息源**
- 第一版 **立即采集** 在用户界面中等待对应 **采集运行** 完成后展示结果，不引入独立待处理队列
- **立即采集** 完成后刷新当前页面相关数据并展示本次结果，但不自动跳转到 **内容浏览** 或 **采集记录**
- 一次 **采集运行** 可以包含零个或多个 **采集运行事件**
- `collect_all_items` 的分页请求失败应记录为没有 `item_id` 的 `pagination_failed` **采集运行事件**，并停止继续翻页
- `pagination_failed` 不等同于 `item_failed` 或 `source_failed`，只表示跨分页条目发现链路中断
- `collect_all_items` 的分页请求失败只增加一次失败计数，不按未访问的剩余页面估算失败数量
- `collect_all_items` 分页请求失败但已有 **条目候选** 后续采集成功时，运行结果应表达为部分成功
- 当一次 **采集运行** 中部分 **条目候选** 详情失败但仍有内容成功保存时，运行结果应表达为部分成功
- 详情失败的 **条目候选** 不产生 **内容条目**，其失败通过没有 `item_id` 的 **采集运行事件** 记录
- `track_page_change` 首次采集创建新的 **内容条目**，会增加新发现计数和保存计数
- `track_page_change` 更新不增加 **采集运行** 的新发现计数，但会增加保存计数
- `collect_new_items` 和 `collect_all_items` 新增 **内容条目** 同时增加新发现计数和保存计数
- `collect_new_items` 和 `collect_all_items` 中已知 **条目候选** 的再次出现应记录为已看到或跳过事件，不增加新发现计数、保存计数或 **原始内容版本**
- `collect_new_items` 和 `collect_all_items` 的晚到身份命中按已知 **条目候选** 处理，记录 `item_seen` 成功事件，不增加新发现计数、保存计数或 **原始内容版本**
- 第一版 **定时采集** 必须由 **调度器** 触发 `scheduled` **采集运行**，不能只保存 **扫描频率** 或只展示配置状态
- **调度器** 到期检查只选择启用、有 **扫描频率** 且默认 **采集通路** 可用的 **信息源**
- 停用、缺少 **扫描频率** 或默认 **采集通路** 不可用的 **信息源** 不参与到期检查，也不因此产生失败 **采集运行**
- **调度器** 应将同一检查窗口内到期的多个 **信息源** 合并为一次 `scheduled` **采集运行**
- 合并后的定时 **采集运行** 通过 **采集运行** 的信息源列表记录本次覆盖的 **信息源**
- **调度器** 按上次尝试采集时间计算 **信息源** 是否到期，避免失败 **信息源** 被连续重试
- **信息源** 的上次尝试采集时间来自默认 **采集通路** 对应的 **扫描进度**
- **立即采集** 和 **定时采集** 都会更新 **信息源** 的上次尝试采集时间，并共同影响下一次到期判断
- 配置了 **扫描频率** 但从未产生采集尝试的启用 **信息源**，在下一次 **调度器** 检查时视为到期
- 本地第一版同一时间只允许一个 **采集运行** 执行，**调度器** 不并发启动新的 **采集运行**
- `running` 状态的 **采集运行** 表示当前采集执行权已被占用
- 本地服务启动时发现遗留的 `running` **采集运行**，应将其标记为失败，使新的 **立即采集** 或 **定时采集** 可以继续
- 已有 **采集运行** 执行中时，**调度器** 跳过本次启动，并在下一检查窗口重新判断到期 **信息源**
- 已有 **采集运行** 执行中时，**立即采集** 不进入队列，也不合并到运行中的 **采集运行**，而是提示当前已有采集占用执行权
- 最近成功采集时间用于 **信息源管理** 和 **采集记录** 的状态展示，不用于替代到期计算
- **定时采集** 失败只更新运行状态和错误提示，不自动停用 **信息源**，也不清空 **扫描频率**
- 第一版 **定时采集** 不触发系统通知，新增内容和失败结果只通过 **内容浏览**、**信息源管理** 和 **采集记录** 展示
- **定时采集** 产生 **信息提醒** 的策略留到后续 **处理流水线** 扩展中设计
- 第一版 **调度器** 内置在 **本地应用服务** 中运行，不依赖外部 cron 或 launchd 配置
- **调度器** 在 **本地应用服务** 运行期间按 **调度配置** 独立检查到期 **信息源**，不依赖用户打开页面或发起其他 API 请求
- 第一版 **定时采集** 只在 **本地应用服务** 运行期间生效，不包含系统级常驻、开机自启或机器休眠补偿
- **调度器** 是否启用是持久化配置，重启 **本地应用服务** 后应保留用户上次保存的选择
- **调度器** 保存为启用时，**本地应用服务** 启动后应立即执行一次到期检查
- **调度器** 初始默认关闭，由前端 **设置** 控制是否启用调度
- 两个新服务不再读取根目录 `config/scheduler.yaml`；各自数据库缺少调度状态时按 `enabled: false` 和 `check_interval_minutes: 1` 初始化
- 用户开启 **调度器** 后应立即执行一次到期检查，只触发已到期 **信息源** 的定时 **采集运行**
- 关闭 **调度器** 不清空任何 **信息源** 的 **扫描频率**
- 重新启用 **调度器** 后，已配置 **扫描频率** 的启用 **信息源** 继续参与 **定时采集**
- **Feed 核心进程** 与 **Feed 供给进程** 分别保存自己的调度状态，不共享调度开关或检查进度
- **调度配置** 不属于 **处理规则**，不写入 `config/processing.yaml`
- **调度配置** 不保存单个 **信息源** 的 **扫描频率**
- **调度配置** 的检查间隔是内部运行粒度，第一版前端不提供编辑入口
- 各服务的 SQLite 直接保存本服务 **调度器** 的启停、最近检查时间、最近触发运行和当前检查状态
- 核心侧订阅轮询频率保存在 `config/sources/` 的 **Feed 订阅** 配置中
- 供给侧采集频率保存在 `config/supplier/sources/` 的 **采集源** 配置中
- 单个 **信息源** 的最近尝试、最近成功、错误摘要和失败次数继续保存在 **扫描进度** 中
- 前端 **设置** 中的调度入口命名为 **定时采集**，不直接使用 **调度器** 作为页面名称
- **定时采集** 页面展示调度启停、最近检查、最近定时 **采集运行** 和到期 **信息源** 预览
- **定时采集** 页面可以提供“检查到期信息源”动作，该动作只触发已到期 **信息源**，不等同于 **立即采集** 全部启用 **信息源**
- **定时采集** 页面不直接编辑单个 **信息源** 的 **扫描频率**，只提供跳转到 **信息源管理** 的入口
- **调度器** 启用但没有 **信息源** 配置 **扫描频率** 时，**定时采集** 页面展示空状态并引导用户配置 **信息源**
- **扫描频率** 的主要配置入口在 **信息源管理** 的添加和详情体验中
- 添加或编辑 **信息源** 时，**定时采集** 开关放在主表单的 **扫描配置** 区域
- **快照抽取参数** 等低频细节可以进入高级设置，但 **扫描频率** 不应默认隐藏在高级设置中
- 启用或修改 **定时采集** 只保存配置，不自动触发立即 **采集运行**
- 前端应提供独立的立即采集动作，避免把配置保存和 **采集运行** 混为同一操作
- **信息源** 详情可以展示预计下次采集时间，但应表达为预计而非承诺
- **调度器** 关闭或已有 **采集运行** 占用执行权时，预计下次采集时间应提示其不保证立即执行
- **信息源管理** 列表应展示每个 **信息源** 的 **定时采集** 状态
- 停用 **信息源** 在列表中的 **定时采集** 状态优先显示为停用，而不是显示已保存的 **扫描频率**
- **设置** 可以展示调度状态、采集记录或默认建议，但不作为 **扫描频率** 的集中配置入口
- **内容存储** 是已采集内容的主存储，前端 **内容浏览** 默认读取 SQLite 而不是读取 Markdown 文件
- **媒体预览** 在保存 **原始内容版本** 时从采集后端显式媒体线索、JSON 原始内容字段、HTML 或 Markdown 正文中的首张可用图片依次确定
- **媒体预览** 属于 **原始内容版本**，不属于 **内容条目**；内容变化产生新版本时可以产生新的预览
- 第一版 **媒体预览** 承载在 **原始内容版本** 的版本元数据中，不新增独立媒体表或 **内容条目** 字段
- **采集后端** 已知封面或媒体入口时，可以通过 **标准采集结果** 元数据中的 `media_preview` 显式提供 **媒体预览**
- 第一版每个 **原始内容版本** 最多保存一个 **媒体预览**；多图、多视频或完整媒体集合仍只属于 **原始内容**
- 多个媒体线索同时存在时，**媒体预览** 按采集后端显式指定、首个可用封面或缩略图、正文首张图片、视频入口占位的顺序选择
- **媒体预览** 只从内容主体媒体中选择，不把作者头像、信息源 logo、favicon、分享图标、跟踪像素或页面装饰图作为候选
- 视频内容没有可用封面图时，第一版 **媒体预览** 可以只保存视频入口线索并由前端显示视频占位样式
- 第一版 **媒体预览** 只保存 `kind`、`preview_url`、`target_url`、`alt_text` 和 `source`；不保存宽高、文件大小、下载状态或多候选列表
- **媒体预览** 的 URL 第一版只接受 `http` 或 `https`；不接受 `file:`、`data:`、`javascript:`、本机路径或空白字符串
- `preview_url` 仅在视频占位场景允许为空；`target_url` 优先使用媒体目标地址，缺失时回退到 **内容条目** 的打开地址
- 第一版只为新保存的 **原始内容版本** 生成 **媒体预览**；既有旧内容缺失预览时不回填、不迁移
- 第一版 **媒体预览** 不进入 **处理批次**，不改变 AI 摘要、评分或推荐理由的输入范围
- **原始内容** 永远保留，**处理流水线** 只改变可见性、分数、分类和导出输出
- 同一 **内容条目** 默认保留首次 **原始内容**，只有内容指纹变化时才新增 **原始内容版本**
- `track_page_change` 的内容变化对应同一 **内容条目** 的新 **原始内容版本**，不创建新的 **内容条目**
- `collect_new_items` 和 `collect_all_items` 的新外部 ID 或 URL 对应新的 **内容条目**
- `collect_new_items` 与 `collect_all_items` 的主要差异是 **条目发现** 范围，不是已知内容刷新策略
- `collect.py` 持久化 **标准采集结果** 时，已存在外部 ID 或规范化 URL 会映射到同一 **内容条目**；内容指纹未变化时只记录再次看到，内容指纹变化时产生新的 **原始内容版本**
- `collect_new_items` 和 `collect_all_items` 中，详情采集后才发现身份命中既有 **内容条目** 时，已抓取的 **原始内容** 不进入 `collect.py` 内容存储去重
- `collect_new_items` 和 `collect_all_items` 都不负责维护历史 **内容条目** 的删除或下架状态
- `collect_new_items` 和 `collect_all_items` 的 **内容条目 ID** 默认由 **条目候选** 身份决定，详情采集结果不应让同一候选反复生成新 **内容条目**
- `track_page_change` 的 **内容条目 ID** 应稳定绑定到 **信息源** 或规范化目标入口，不应由内容哈希兜底生成
- `track_page_change` 首次创建 **内容条目** 时，应把 **信息源** 的 `target` 写入 `item_identities`，`identity_type = url`
- `track_page_change` 的 **内容身份别名** 只记录目标入口 URL，用于统一展示和追溯入口，不参与页面身份迁移
- `track_page_change` 默认不把详情采集或跳转得到的 canonical URL、final URL 写成 **内容身份别名**
- `track_page_change` 的页面变化检测仍只看内容指纹，不看 **内容身份别名**
- `collect_new_items` 和 `collect_all_items` 的 **内容条目 ID** 只能按外部 ID 或规范化 URL 生成；缺少二者的 **条目候选** 不应保存为 **内容条目**
- **内容身份别名** 参与后续 **条目候选** 预检查和重复内容判断，但不改变既有 **内容条目 ID**
- 详情页跳转后的最终 URL、canonical URL 或平台 ID 与列表候选 URL 不一致时，应增加 **内容身份别名**，而不是重建 **内容条目**
- `items.url` 保存当前最适合用户打开的主 URL，不作为 **内容条目 ID**、预检查或重复判断的身份依据
- `items.url` 的选择优先级为 canonical URL、final URL、候选 URL 或列表详情 URL
- 已创建 **内容条目** 的 `items.url` 只有在新采集发现更高优先级 URL 时才升级；同优先级 URL 的细微变化不应频繁覆盖 `items.url`
- **内容浏览** 打开原地址时使用 `items.url`；缺失时可以回退到最新 **内容身份别名** 中的 URL 类身份
- **内容身份别名** 进入 SQLite 最小 schema，表名为 `item_identities`
- `item_identities` 的 URL 类身份范围为 `source_id + normalized_value`，`url`、`canonical_url` 和 `final_url` 之间共享同一规范化 URL 身份
- `item_identities` 的 `external_id` 身份范围为 `source_id + identity_type + normalized_value`
- `identity_type` 对 URL 类身份主要表达身份来源，不隔离同一个规范化 URL
- 同一 **信息源** 下相同 `normalized_value` 的 URL 类身份重复出现时，应更新既有 **内容身份别名** 的 `last_seen_at`，而不是插入第二条别名
- `item_identities.normalized_value` 由 **统一采集执行** 按 **身份规范化** 规则生成，**采集后端** 不直接决定最终规范化值
- URL 类 **内容身份别名** 的 **身份规范化** 只小写 scheme 和 host、去掉 fragment、去掉默认端口，并把空 path 归一为 `/`
- URL 类 **内容身份别名** 不默认删除 query 参数，不重排 query 参数，不做额外 percent-decoding
- URL 类 **内容身份别名** 可以删除明确跟踪参数：`utm_*`、`fbclid` 和 `gclid`
- `external_id` 类 **内容身份别名** 只做 trim，不改变大小写
- **身份规范化** 失败时不写入 **内容身份别名**，避免错误合并
- `identity_conflict` **采集运行事件** 用于记录两个既有 **内容条目** 被同一身份证明疑似重复；事件 `item_id` 可以指向当前采集命中的内容条目，另一个冲突条目通过 `message` 描述
- `identity_conflict` 不增加保存计数或新发现计数，也不表示整个 **信息源** 失败
- `track_page_change` 的 **内容条目** 标题来自 **标准采集结果**，缺失时用 **信息源** 名称兜底
- **信息源** 名称是用户管理名称，不强制覆盖 **内容条目** 标题
- **信息提醒** 独立于 **内容条目**、**原始内容版本** 和 **采集运行事件**
- `track_page_change` 的内容变化可以产生 **信息提醒**
- `collect_new_items` 和 `collect_all_items` 的新 **内容条目** 可以产生 **信息提醒**
- 采集失败、登录失效或 **采集通路** 不可用也可以产生 **信息提醒**
- 并非每个 **内容条目** 或 **原始内容版本** 都必须产生 **信息提醒**
- 当前阶段只保留 **信息提醒** 的领域边界，不设计 **提醒策略** 或把提醒配置加入 **信息源格式**
- **提醒策略** 后续作为 **处理流水线** 的扩展讨论，不作为当前 **信息源管理** 的配置目标
- **内容索引** 记录内容条目的首次采集时间、最近看到时间和累计看到次数，用于区分“新发现”和“重复出现”
- **内容索引** 的最近看到时间和累计看到次数可以由 **条目候选** 预检查更新，不要求每次都重新取得完整 **原始内容**
- **内容条目** 的来源标签只继承 **信息源标签**，不继承 **关注主体** 标签
- **来源** 是 **内容浏览** 的前端过滤维度，不写入 **分类规则配置**，也不改变 **处理结果** 的 **一级分类** 或 **二级分类**
- **内容浏览** 可以把 **来源** 伪装成最后一个 **一级分类** 按钮展示，但它不是新的分类组
- 用户在 **内容浏览** 中选择 **来源** 后，二级筛选行显示推特、网页、RSS 等具体来源值；选择来源值才附加过滤，`来源` 下的“全部”不附加过滤
- 第一版 **来源** 不新增 **信息源格式** 字段，优先从 **内容条目** 实际采集时保存的 **采集通路** 和平台推导；推特通路显示为“推特”，RSS 通路或 `rss_feed` 后端显示为“RSS”，通用网页通路显示为“网页”，其他平台用平台名兜底
- `generic` 这类实现占位平台名本身不作为 **来源** 显示；只有具体通路线索能推导为网页、RSS 等用户可理解入口时才展示
- 第一版 **来源** 过滤与普通 **一级分类** 过滤互斥；选择 **来源** 时不叠加某个内容分类，选择普通 **一级分类** 时不叠加某个来源值
- **来源** 入口始终追加在当前可见 **一级分类** 列表末尾；不强行补出当前结果中没有出现的普通 **一级分类**
- **来源** 二级筛选项基于当前 **内容浏览** 结果动态出现，跟随当前视图、搜索、信息源和 **采集通路** 筛选结果变化；出现时优先按“推特、网页、RSS”的固定顺序展示，再补充当前内容中出现的其他来源值
- 当前 **内容浏览** 结果中没有可推导的来源值时，不展示 **来源** 这个伪一级分类入口
- 单条内容的 **来源** 从该 **内容条目** 实际采集时保存的 **采集通路** 和平台推导，不从 **信息源** 当前默认 **采集通路** 推导
- 第一版 **来源** 使用小型中文显示名表覆盖当前已有平台，例如微信、微博、知乎、GitHub、YouTube、B站、小红书、Reddit、V2EX、财联社、华尔街见闻、雪球、OpenBB、Exa 和 AI HOT；表外平台回退显示原始平台名
- 一个 **处理结果** 必须包含且只包含一个 **一级分类**
- **一级分类** 不属于 **条目标签**；**条目标签** 仍是多值补充标签
- **一级分类** 在 AI 回填 JSON、SQLite 和本地 HTTP API 中使用内部字段名 `primary_category`，前端显示为“一级分类”
- **一级分类** 必须来自 **分类规则配置** 中的当前一级标题
- **二级分类** 不属于 **条目标签**；能判断时用于 **知识库文件路径** 的第二层目录
- **二级分类** 在 AI 回填 JSON、SQLite 和本地 HTTP API 中使用内部字段名 `secondary_category`，前端显示为“二级分类”
- **二级分类** 必须来自 **分类规则配置** 中对应 **一级分类** 下的二级标题；不匹配时回填写入规范化为空
- **条目标签** 不自动参与知识库目录选择
- **分类规则配置** 属于 **处理规则** 的全局配置，前端可在 **设置** 中通过 **本地应用服务** 修改并写入 **配置主存储**
- **处理规则** 设置页可以编辑 **分类规则配置** 的一级分类名称、二级分类列表以及分类的增删
- **分类规则配置** 第一版前端不提供拖拽排序、导入导出或观察项管理
- 保存 **分类规则配置** 时必须校验 `categories` 非空、一级分类名称非空且不重复、同一一级分类下二级分类名称非空且不重复
- 读取 **处理规则** 时缺少 `taxonomy` 的旧配置使用内置默认正式分类表；保存设置后再写入 `processing.yaml`
- **分类规则配置** 允许某个一级分类暂时没有二级分类；AI 仍必须回填 `primary_category`
- 修改或删除 **分类规则配置** 中的分类时，已有 **处理结果** 不自动迁移；新处理结果按新的 **分类规则配置** 回填
- SQLite 中 `primary_category`、`secondary_category` 和 `taxonomy_hash` 允许为空以兼容旧 **处理结果**；新回填写入仍按当前契约校验
- 新 **处理结果** 回填缺少 **一级分类** 时应拒绝回填；仅旧数据兼容保存允许缺少 **一级分类**
- 新 **处理结果** 回填的 **一级分类** 不在当前 **分类规则配置** 中时应拒绝该处理结果
- 新 **处理结果** 回填的 **二级分类** 不属于对应 **一级分类** 时，不拒绝回填；写入 **处理结果** 时将 `secondary_category` 规范化为 `null`
- **原始内容** 保存到 SQLite 的 **内容存储** 中，文件系统 raw 归档不作为第一版主路径
- 一个 **信息源** 一次采集可以产生零个或多个 **内容条目**
- 最小版本中一个 **内容条目** 只归属一个 **信息源**，不建立多信息源归属关系
- **内容条目** 的 `route_id` 记录原始 **信息源** 常规采集使用的 **采集通路**，通常是执行 **条目发现** 的通路
- **完整内容采集** 实际使用的详情 **采集通路** 应记录在 **原始内容版本** 元数据或 **采集运行事件** 中，不覆盖 **内容条目** 的 `route_id`
- **原始内容版本** 元数据使用 `detail_route_id`、`detail_backend_id` 和 `detail_fallback_index` 记录详情采集执行信息
- `detail_fallback_index` 使用 0-based 编号，`0` 表示默认详情采集通路成功，`1` 表示第一个回退通路成功
- 当 **条目候选** 自身已包含可保存 **原始内容** 且未使用 **详情采集配置** 时，不写 `detail_route_id`、`detail_backend_id` 或 `detail_fallback_index`
- **采集运行事件** 需要表达详情采集执行信息时，应复用 `detail_route_id`、`detail_backend_id` 和 `detail_fallback_index` 这组字段名
- 详情采集成功或失败事件的主 `route_id` 仍记录来源 **采集通路**，失败的具体详情通路通过 `detail_route_id` 等详情执行字段表达
- 详情采集执行信息只用于追溯和排障，不进入 **内容条目** 主索引
- 一个 **内容条目** 保留对应的 **原始内容**，但不自动生成知识库文档
- 一个 **内容条目** 拥有一个稳定的 **内容条目 ID**，该 ID 不因标题、分类或分数变化而改变
- 当 **标准采集结果** 同时包含 `external_id` 和 `url` 时，**内容条目 ID** 优先使用 `platform + external_id` 生成
- **内容条目 ID** 可继续用于完整 Markdown 调试导出的稳定文件名；**知识库文档** 使用 **标题文件名**
- **清洗正文保存** 是“保存到知识库”的目标主语义；早期因为尚无可靠清洗后正文，前端“保存到知识库”暂时落到 **简要信息保存**
- **清洗正文保存** 由用户在前端触发，生成 **清洗正文文档**，不作为采集运行的默认产物
- **保存到知识库** 通过 `POST /api/items/{item_id}/save-to-knowledge-base` 执行，响应返回 `markdown_path` 和 `saved_as`
- `save-to-knowledge-base` 的 `saved_as` 表达本次保存形态：`cleaned_content` 表示保存了清洗正文增强版，`brief_info` 表示回退保存了简略内容
- **清洗正文保存** 必须先在 **设置** 中配置 **知识库路径**；未配置时前端不允许保存，后端也应拒绝请求
- **知识库路径** 本身必须已经存在且可写；不存在或不可写时拒绝 **清洗正文保存**
- **清洗正文文档** 的正文来自最新 **原始内容版本** 的清洗后展示内容，不读取或导出未清洗 **原始内容**
- **保存到知识库** 优先执行 **清洗正文保存**；当最新 **原始内容版本** 没有成功清洗后的展示正文时，允许回退到 **简要信息保存**
- **清洗正文保存** 只在最新 **原始内容版本** 的 **清洗状态** 为成功时产出 **清洗正文文档**；清洗降级、未配置清洗或清洗停用时不把默认展示内容伪装成清洗正文
- **清洗正文文档** 与 **简要信息文档** 使用同一个知识库文件路径；清洗成功时在摘要、推荐理由、评分和标签后追加正文，清洗不可用时同一路径回退为简略内容
- **知识库文件路径** 由当前有效 **一级分类** 和可选 **二级分类** 派生目录，并使用 **标题文件名**
- **标题文件名** 优先使用内容标题；同一分类目录下标题冲突时才追加短 ID 后缀
- **标题文件名** 的短 ID 后缀使用 **内容条目 ID** 前 8 位，格式为 `{标题}-{短ID}.md`；重保存同一 **内容条目** 时复用该条目已有文件路径
- 判断同目录标题冲突时应读取已有 Markdown frontmatter 的 `id`：若 `id` 等于当前 **内容条目 ID** 则覆盖原文件；若 `id` 不同或无法读取则改用短 ID 后缀文件名
- **标题文件名** 需要替换文件系统非法字符、压缩连续空白并截断过长标题
- **标题文件名** 主体最多保留 96 个字符，不包含 `.md` 扩展名和冲突时追加的短 ID 后缀
- 标题清洗后为空时，**标题文件名** 使用 `untitled-{短ID}.md`
- **清洗正文文档** 和 **简要信息文档** 有有效分类时应写入 `## 分类` 区块，包含 **一级分类** 和可选 **二级分类**；没有有效分类时不写该区块
- `## 分类` 区块应放在评分之后、标签之前，避免把 **一级分类** 或 **二级分类** 混作普通 **条目标签**
- **清洗正文文档** 的正文区标题统一使用 `## 正文`，不使用“清洗正文”作为读者可见标题
- **清洗正文文档** 应保留标题、原始 URL、采集时间、内容版本、清洗状态等必要来源追溯信息
- **简要信息保存** 由用户在前端触发，生成 **简要信息文档**，不作为采集运行的默认产物
- **简要信息保存** 可以继续由兼容接口 `POST /api/items/{item_id}/save-brief-info` 执行，但前端主动作不再调用该接口
- 兼容接口 `save-brief-info` 行为保持简略内容保存，不追加 `## 正文`，也不返回 `saved_as`
- **简要信息保存** 必须先在 **设置** 中配置 **知识库路径**；未配置时前端不允许导出，后端也应拒绝导出请求
- **知识库路径** 本身必须已经存在且可写；不存在或不可写时拒绝 **简要信息保存**
- **简要信息文档** 和 **清洗正文文档** 导出时按 **一级分类** 分目录保存，不再按 **采集日期** 分目录保存
- **知识库文件路径** 使用 **知识库路径** 下的 `{一级分类}/{二级分类?}/{标题文件名}.md`，不使用 `YYYY/MM/DD/{item_id}.md`
- 旧 **处理结果** 缺少 **一级分类**，或已有 **一级分类** 已不在当前 **分类规则配置** 中时，**知识库文件路径** 可以回退到 **知识库路径** 根目录下的 `{标题文件名}.md`
- **二级分类** 缺失、为空或不属于对应 **一级分类** 时，**知识库文件路径** 使用 `{一级分类}/{标题文件名}.md`
- **简要信息文档** 和 **清洗正文文档** 导出时可以自动创建 **知识库路径** 下缺失的分类子目录
- 重复导出同一 **内容条目** 时覆盖同一路径的 **简要信息文档**，不生成带时间戳或序号的历史副本
- **简要信息文档** 正文不包含 **原始内容** 或“原文”正文区；正文展示 **处理结果** 中的中文摘要、推荐理由、评分、标签和来源追溯信息
- 第一版 **简要信息文档** 不保存 **媒体预览**；外部图片或视频链接只作为 **内容浏览** 的卡片展示线索
- **简要信息文档** 的 frontmatter 保持简化，不保存摘要、推荐理由、评分、AI 标签、处理时间、skill 版本或 profile hash 等 **处理结果** 字段
- **简要信息文档** 的 frontmatter 只保留 `id`、`title`、`url`、`collected_at`、`content_version` 和 `exported_at`
- `save-to-knowledge-base` 的 `saved_as` 只用于 API 响应和前端提示，不写入知识库文档 frontmatter
- **简要信息文档** 依赖该 **内容条目** 最新 **原始内容版本** 的完整 **处理结果**；没有处理结果时不导出，不回退到 **原始内容** 或只有来源信息的空文档
- 前端“保存到知识库”只保存最新 **原始内容版本** 对应的知识库记录，不提供旧版本选择
- 如果后续支持显式导出旧 **原始内容版本**，导出时必须使用同版本 **处理结果**，不能混用最新 **处理结果**
- 前端“保存到知识库”在缺少完整 **处理结果** 时不能回退生成 **简要信息文档**，后端也应拒绝缺少处理结果的回退保存请求
- 关闭 **信息源 AI 处理开关** 的内容条目不能生成依赖摘要、评分和推荐理由的 **简要信息文档**；未来 **清洗正文保存** 可以不依赖 **处理结果** 单独保存正文
- 前端“保存到知识库”在缺少 **知识库路径** 或完整 **处理结果** 时保持按钮可见但置灰，并提供原因提示；未配置路径提示“请先在本地存储设置知识库路径”，未处理完成提示“需要先完成 AI 处理”
- **简要信息文档** 通常只从 `saved` 状态的内容条目导出，其他内容条目状态主要存在 SQLite
- **简要信息文档** 的 `collected_at` 表示该简要信息文档对应内容的首次采集时间；更细的出现次数和最近看到时间保存在 **内容索引**
- 既有完整 Markdown 导出能力可以继续保留给完整原文阅读和调试场景，但不应与 **清洗正文保存** 或 **简要信息保存** 混为同一导出语义
- 一个 **内容条目** 对应一条 **内容索引**，并在 **内容存储** 中保留正文和原始载荷；Markdown 是导出格式，不是主存储
- **处理规则** 暂时作为全局配置应用于已采集内容，不由 **信息源分组** 或单个 **信息源** 覆盖
- **处理流水线** 开启时必须生成完整 **处理结果**；评分、摘要、推荐理由、唯一 **一级分类** 和 **评估标签** 不由单独步骤开关控制
- `pipeline.enabled` 只控制是否运行 **处理流水线**，不控制 **处理结果** 内部字段是否生成
- **信息源 AI 处理开关** 默认开启；关闭后，该 **信息源** 的既有 **处理结果** 保留，但尚无处理结果的内容版本不再计入 **待处理条目**
- 重新开启 **信息源 AI 处理开关** 后，该 **信息源** 下尚无 **处理结果** 的内容版本重新成为 **待处理条目**
- 关闭 **信息源 AI 处理开关** 不删除、不隐藏、不标记既有 **处理结果**；已有结果继续可用于 **内容浏览**、**精选** 和 **简要信息保存**
- **处理规则** 当前不按 **关注主体** 配置或覆盖
- **关注主体** 作为 **处理流水线** 条件维度留到后续单独设计
- **信息源 AI 处理开关** 第一版不按 **关注主体**、**主体分组** 或 **信息源分组** 批量配置，也不设计继承或覆盖规则
- **处理流水线** 由全局 **处理规则** 定义为整体任务，不提供评分、摘要、标签或分类的独立步骤开关
- **信息源来源处理配置** 不属于 **清洗配置** 或全局 **处理规则**；它只声明单个 **信息源** 如何把 **来源自带处理信号** 转换为完整 **处理结果**
- **采集后端** 负责请求外部 API 并将响应转换为 **标准采集结果**；**来源自带处理信号** 只来自已采集载荷，不发起外部请求，也不成为第二套采集系统
- **来源自带评分信号** 和 **来源自带分类信号** 可以在关闭 **信息源 AI 处理开关** 时生成完整 **处理结果**，但必须满足当前 **处理结果** 契约和 **分类规则配置** 约束
- **采集后端** 不应写死用户偏好的评分和分类映射；**来源自带处理信号映射** 属于 **信息源** 配置，由统一保存逻辑按该映射生成完整 **处理结果**
- **来源自带处理信号映射** 第一版只支持固定值和 **原始内容版本** 元数据字段路径，不提供表达式语言、复杂条件或跨字段计算
- AI HOT 信息源默认使用 `/api/public/feed` 采集精选池，使用 `take=50`；仅当 feed 请求失败或响应不可用时，才回退请求 `/api/public/items?mode=selected`
- AI HOT 信息源的 `finalScore`、`qualityScore` 或 `score` 作为 **来源自带评分信号** 映射为重要性评分，固定用户相关程度评分为 95，固定时效性评分为 90；综合推荐分仍按 **处理结果** 的三维评分统一计算
- AI HOT 信息源的 `aiSelectedReason` 作为完整 **处理结果** 的推荐理由；旧 items 接口缺少该字段时，使用稳定默认理由
- AI HOT 信息源的 `aiTags` 或 `category` 作为 **来源自带分类信号** 保存在元数据和标签线索中；第一版完整 **处理结果** 统一映射到一级分类 `智能科技` 和二级分类 `AI与编程`
- AI HOT 信息源的 `aiSelected` 或 `selected` 第一版不参与本应用评分，只作为 **来源自带分类信号** 或来源标记保存在元数据中
- **来源自带处理信号** 应保存在 **原始内容版本** 元数据中；当信号不足以生成完整 **处理结果** 且 **信息源 AI 处理开关** 开启时，后续 AI **处理批次** 可以读取这些信号作为判断参考
- **内容浏览** 优先展示完整 **处理结果**；缺少完整处理结果时，可以从 **原始内容版本** 元数据中的 **来源自带处理信号** 回退展示可用的部分评分、分类、摘要或来源标记，但不能把这些部分信号当作完整 **处理结果**
- **来源自带处理信号映射失败** 不阻止 **内容条目** 和 **原始内容版本** 保存；系统应记录可追溯 **采集运行事件**，且不会因为 **信息源 AI 处理开关** 关闭而自动改走 **处理流水线**
- 由 **来源自带处理信号** 生成的 **处理结果** 不应伪装成 AI skill 产物；保存时应使用稳定的来源自带处理标识追溯结果来源，同时继续记录当前 **分类规则配置** 快照
- **综合推荐分** 由 **处理流水线** 根据 **处理结果** 的三维评分计算，默认权重为重要性 35%、时效性 25%、用户相关程度 40%，并四舍五入为 0-100 整数
- **处理结果** 绑定到 **原始内容版本**，同一 **内容条目** 产生新的 **原始内容版本** 后应重新成为 **待处理条目**
- `process read-batch` 读取 **处理批次** 时必须排除 AI 处理关闭 **信息源** 的内容版本
- `process write-batch` 不因 **信息源 AI 处理开关** 关闭而拒绝回填；它只校验 **原始内容版本** 标识和内容指纹等回填契约
- **处理结果** 独立于 **内容索引** 存储，AI 自动生成的 **评估标签** 不作为主存储双写到 `items.tags_json.ai`
- 第一版 **处理批次** 在数据库层不声明处理所有权，不新增“处理中”状态；**处理结果** 回填通过 **原始内容版本** 标识保持幂等
- 同一 **原始内容版本** 的 **处理结果** 可以在内容指纹匹配时幂等覆盖，并更新处理时间、`skill_version` 和 `profile_hash`
- 第一版 **处理结果** 回填不校验最近一次 **处理批次**，不维护批次 ID；只要 **原始内容版本** 标识和内容指纹匹配即可接受
- 自动 AI 后处理不属于 **采集运行**；采集完成后可以产生独立的 **处理触发**，AI 处理失败不反写采集运行为失败
- **采集运行** 完成后，只有本次实际新增了至少一个来自 AI 处理开启 **信息源** 的 **原始内容版本** 且 `processing.pipeline.enabled` 为 true 时，才自动产生一次后台 **处理触发**
- 如果本次新增的 **原始内容版本** 全部来自 AI 处理关闭的 **信息源**，本地应用服务不产生自动 **处理触发**
- 自动 **处理触发** 的采集后判断以保存层返回的新增 **原始内容版本** 数量为准；新 **内容条目** 首次保存和既有条目内容指纹变化产生新版本都算，重复发现、内容无变化或采集失败不算
- 本地应用服务启动时，如果 `processing.pipeline.enabled` 为 true 且存在 **待处理条目**，自动产生一次后台 **处理触发** 用于恢复处理
- 第一版不做定时扫描待处理、不在保存 **处理规则** 后立即触发，也不新增前端手动处理按钮
- 自动 **处理触发** 在后台执行；触发它的 **采集运行** 或前端请求不等待 AI 完成后再返回
- 同一时间只允许一个自动 **处理触发** 协调器执行；一个触发内可以按可配置 **agent 并行数** 并行调用多个 agent CLI，最大并行数为 5
- **agent 并行数** 默认值为 3，可配置范围为 1-5
- 自动 **处理触发** 执行中收到新的处理需求时不启动第二个触发协调器，也不建立多项队列，只合并为当前触发结束后的再跑一轮
- 自动 **处理触发** 的运行中状态第一版只保存在本地应用服务内存中，不新增 SQLite 处理状态表；服务重启后按现有 **待处理条目** 事实恢复触发
- 自动 **处理触发** 的协调器在内存中维护 `in_flight` 原始内容版本集合；分配 **处理批次** 时排除已分配给其他并行 agent 的版本，agent 成功、失败或超时后释放这些版本
- 服务重启会丢失 `in_flight`；重启后按 SQLite 中仍缺少完整 **处理结果** 的事实重新分配，重复回填由原始内容版本标识和内容指纹幂等保护
- 第一版只保证同一个本地应用服务进程内不重复分配 **处理批次**；如果用户同时运行多个服务实例，可能重复调用 agent，但重复回填由幂等覆盖保护
- 第一版不为跨进程处理并发增加 SQLite 锁表、租约或心跳
- `skill_version` 和 `profile_hash` 用于追溯 **处理结果** 的来源快照，不参与默认 **待处理条目** 判定；处理规则或 **用户画像文档** 变化不自动让已有 **处理结果** 重新进入待处理
- **内容浏览** 显示所有已保存 **内容条目**；没有 **处理结果** 的条目不被隐藏，AI 字段显示为空态或待处理状态
- 关闭 **信息源 AI 处理开关** 的内容条目仍显示在 **全部信息流**，但不会因缺少 **处理结果** 进入依赖综合推荐分的 **精选**
- **内容浏览** 默认仍按时间线排序，排序时间优先使用 `ai_published_at`，没有 AI 识别发布时间时回退到 `published_at`，再回退到首次采集时间；**综合推荐分** 先作为显示字段和可选排序或筛选条件
- **处理规则** 设置页第一版负责配置 **用户画像文档** 路径、生成 AI 处理 skill 和查看 **待处理条目** 数量
- **待处理条目** 数量包含没有完整 **处理结果** 的内容版本，并按 **原始内容版本** 去重
- **重处理** 是显式恢复动作；当前阶段提供单个 **内容条目** 当前 **原始内容版本** 的 **重处理请求**，并可在当前视图内对 **处理失败** 条目执行 **批量重处理**
- 当前阶段用户可见的 AI 处理异常聚焦 **处理失败**；AI 无法可靠处理某条内容时，若未形成完整有效 **处理结果**，应进入失败状态而不是伪装成成功回填
- 批量回填 **处理结果** 时逐条接受或拒绝，单条拒绝不阻断同批其他 **处理结果** 保存
- 第一版不单独记录 **处理流水线** 运行历史，**处理结果** 保存处理时间即可；后续需要审计或模型统计时再增加处理运行记录
- 自动 **处理触发** 不依赖已生成的 AI 处理 skill；本地应用服务每次触发时直接拼接完整 **处理提示词** 交给 agent CLI
- 手动 AI 处理 skill 和自动 **处理提示词** 共用同一个规则渲染源；三维评分口径、中文摘要要求、推荐理由要求和 **用户画像文档** 快照不能在两套模板中各自维护
- 手动 skill 在共享规则段外增加 `read-batch` / `write-batch` 循环说明；自动 **处理提示词** 在共享规则段外增加当前 **处理批次** JSON 和只需 `write-batch` 的回填说明
- **处理提示词** 包含 **用户画像文档** 内容快照、三维评分口径、中文摘要和推荐理由要求、当前 **处理批次** 内容，以及通过 `feeds-agent process write-batch --json -` 回填 **处理结果** 的要求
- **处理提示词** 应内联当前 **分类规则配置**，要求 AI 只从其中选择 `primary_category`，并在能判断时选择对应的 `secondary_category`
- **处理提示词** 不要求 AI 调用读取 CLI，不包含 SQLite 表结构或前端配置说明；**处理批次** 由本地应用服务按批次限制策略读取并内联到 prompt 中
- 自动 **处理触发** 与手动 `read-batch` CLI 复用同一个批次读取模块；该模块内部完成配置解释、待处理读取、正文裁剪和自适应等待，调用方只接收可处理批次或结束状态
- 默认 **处理批次** 使用自适应窗口：达到目标提示词税率、60000 正文字符、100 条硬上限、8 秒最长等待或 1.5 秒静默期中的任一释放条件时返回；固定字符预算和固定条数模式继续作为兼容配置保留
- 自适应等待状态只存在于批次读取模块内部，不通过 CLI 或协调器接口暴露 `waiting` 状态
- **处理回填检查点** 默认要求 agent 每完成 3 条或累计处理 6000 正文字符时调用一次 `write-batch`，以先到者为准；检查点只约束提示词协议，不拆分 agent 调用，也不是后端可强制保证的事务边界
- 自动 **处理触发** 不由本地应用服务解析 agent 的处理结果输出；agent 必须自行调用 `feeds-agent process write-batch --json -` 回填，服务只负责启动 agent、等待退出、agent 超时处理和记录命令级失败
- agent 回填完成后应在 stdout 输出简短 JSON 状态，调试信息写入 stderr；本地服务第一版只把退出码作为本轮 agent 调用成功或失败的判断
- 自动 **处理触发** 会持续分配 **处理批次** 并调用 agent CLI，直到没有新的 **待处理条目**；单次 agent 调用失败时只把尚未通过检查点回填的条目标记为失败，并停止本次触发
- 自动 **处理触发** 的并行 worker 动态领取 **处理批次**：worker 空闲时按当前数据库 **待处理条目** 和内存 `in_flight` 集合读取下一批，而不是触发开始时一次性切完整列表
- 任一 agent 调用失败或超时后，协调器停止分配新的 **处理批次**，等待已启动 agent 结束或超时，再结束本次触发；尚未通过检查点回填的内容版本进入 **处理失败**
- 第一版 **处理失败** 不做立即自动重试，不新增 retry、backoff 或自动恢复；失败内容版本只有在用户显式发起 **重处理** 后才再次进入 **处理流水线**
- **处理状态** 和 **处理异常** 由 **本地应用服务** 返回；前端不根据轮询时长、卡片局部状态或本地计数自行推断异常
- 内容浏览使用不占布局空间的 **处理状态提示** 概览 **处理失败**；用户可关闭提示，关闭不停止后台 **处理触发**，也不清除失败记录
- 用户关闭 **处理状态提示** 后，如果后续失败数量增加，提示应重新出现；如果失败数量清零，也应清除本地关闭状态
- **处理异常筛选** 是显式筛选条件；“查看失败项”会在当前阅读页应用 `processing=abnormal`，并提供一键清除
- **处理异常筛选** 当前只展示仍处于 **处理失败** 的内容版本；失败条目重新入队后会从异常视图移出
- **处理异常筛选** 的列表排序使用 **最近一次异常发生时间**，当前阶段由处理作业时间稳定计算
- **处理异常原因摘要** 用于列表卡片的快速理解；当前阶段不暴露逐条详情面板、失败类型枚举、原始 stderr 或完整日志
- 开启 **处理异常筛选** 后，进入 **处理失败** 的内容卡片可直接执行单条 **重处理**
- 单条 **重处理** 只重新处理该条目当前已保存的 **原始内容版本**，不隐式触发 **立即采集**、信息源刷新或新内容发现
- 单条 **重处理** 与 **批量重处理** 都复用现有 **处理触发** 协调器；若已存在活跃触发，重新入队的失败项并入后续处理流程
- **批量重处理** 只面向当前处于 **处理失败** 的条目，作用范围是当前已应用阅读视图条件下的完整匹配结果集，而不是仅限已滚动加载到页面的卡片
- 用户执行 **批量重处理** 前应看到确认，说明当前作用范围、失败条目数，以及该动作只重新入队 AI 处理、不触发重新采集
- **批量重处理** 支持预览和确认两步；执行结果应明确区分候选条目数、实际重新入队数和跳过数
- 自动 **处理触发** 通过可配置的 **agent 命令模板** 启动外部 agent CLI，业务代码不硬编码 `codex` 或其他具体 agent；模板支持 `{prompt_file}` 占位，默认超时为 900 秒
- **agent 命令模板** 只支持 argv 数组格式，每个数组元素对应一个进程参数；本地应用服务只替换 `{prompt_file}`，不通过 shell 执行，不支持管道、重定向或 shell 展开
- 复杂启动逻辑应放在用户自定义 wrapper 脚本中，再把脚本路径和参数配置为 **agent 命令模板**
- 自动 agent 可配置工作目录 `processing.agent.cwd`，默认使用本地应用服务当前工作目录；第一版不提供自定义环境变量配置
- agent 所需 token、API key 或其他环境变量由用户 shell、系统服务配置或 wrapper 脚本提供，不写入 Feeds Agent 配置
- 本地应用服务为每次 agent 调用把完整 **处理提示词** 写入临时文件，并通过 **agent 命令模板** 的 `{prompt_file}` 占位传入；agent 退出、失败或超时后删除该临时文件
- 第一版不长期保存 **处理提示词** 快照；日志只记录临时 prompt 文件路径、批次大小和退出状态，不记录完整内容正文或完整用户画像
- `processing.pipeline.enabled` 表示 **处理流水线** 能力开启，`processing.agent.command` 表示自动 agent CLI 可启动；两者分开配置
- 如果 **处理流水线** 已开启但 **agent 命令模板** 缺失、为空或不可执行，本地应用服务跳过自动 **处理触发** 并记录日志，不让 **采集运行** 失败，也不关闭手动 `read-batch` / `write-batch` CLI
- 第一版不把 agent 进程 stdout / stderr 写入 SQLite，也不新增处理运行历史表；本地应用服务只在日志中记录退出状态、命令级错误和必要的截断输出
- agent stderr 可作为命令级错误诊断信息记录到日志并截断；进入 **处理失败** 的内容版本不自动回到 **待处理条目**
- 自动 **处理触发** 使用的 CLI 在 stdout 只输出 JSON，调试信息和命令级错误写入 stderr；逐条回填拒绝属于正常 JSON 响应，不作为命令级失败
- AI 处理 skill 持有 **用户画像文档** 内容快照；**用户画像文档** 变化后需要重新生成处理 skill，而不是由 skill 在处理循环中读取该文档
- AI 处理 skill 持有生成当时的 **分类规则配置** 快照；**分类规则配置** 变化后需要重新生成处理 skill
- 自动 **处理提示词** 每次 agent 调用读取当前 **分类规则配置**，不复用旧分类快照
- AI 处理 skill 的 `skill_version` 由处理规则、评分权重、处理批次契约和回填契约等规则快照生成短 hash，`profile_hash` 由 **用户画像文档** 内容生成 hash，`taxonomy_hash` 由 **分类规则配置** 生成 hash
- `taxonomy_hash` 基于规范化后的 `taxonomy.categories` 结构计算，不基于 YAML 原文；规范化时保留一级分类顺序和各自二级分类顺序，再生成规范 JSON 和短 hash
- YAML 注释、缩进或格式变化不应改变 `taxonomy_hash`；分类顺序、分类改名或分类增删会改变 `taxonomy_hash`
- AI 处理 skill 通过 `feeds-agent process read-batch` 读取 **处理批次**，通过 `feeds-agent process write-batch --json -` 批量回填 **处理结果**
- AI 处理 skill 应自包含 **用户画像文档** 内容快照、三维评分口径、中文摘要和推荐理由要求、处理循环步骤，以及简短的读取和回填 JSON 示例；不包含 SQLite 表结构或前端配置说明
- AI 处理 skill 默认生成在 Feeds Agent 的运行产物目录中，不直接写入用户全局 Codex skills 目录
- 将 AI 处理 skill 安装到用户全局 Codex skills 目录属于应用外部环境变更，需要用户显式确认
- 自动 AI 后处理接入按窄垂直切片实现：先扩展 `processing.agent` 配置模型，再抽取共享规则渲染和自动 **处理提示词**，再实现内存 **处理触发** 协调器，随后接入采集完成和服务启动，最后在设置页最小展示 agent 配置状态
- 前端顶层导航按使用频率组织，优先顺序为 **内容浏览**、**信息源管理**、**采集能力管理**，不以平台或工具作为顶层导航
- 前端顶层导航包含 **内容浏览**、**信息源管理**、**采集能力管理** 和 **设置**
- 前端全局导航采用左侧侧边栏，**设置** 固定在侧边栏底部或末尾
- 第一版前端侧边栏不显示计数或状态徽标，异常状态在对应页面内展示
- 第一版前端页面路由为 `/items`、`/sources`、`/sources/:id`、`/routes`、`/routes/:id`、`/settings`、`/settings/processing`、`/settings/sync`、`/settings/install`、`/settings/storage`、`/settings/runs` 和 `/settings/scheduler`
- 第一版前端视觉系统参考 AIHOT 的深色内容监控台风格，复用深色默认主题、左侧侧边栏、紧凑卡片、分段控件、搜索输入和 cyan accent
- AIHOT 的按日期时间线结构只作为 **内容浏览** 的参考，不套用到 **信息源管理**、**采集能力管理** 或 **设置**
- 第一版 **内容浏览** 不伪造评分、摘要或推荐理由；这些字段缺失时显示为待处理状态或隐藏
- 评分、摘要、推荐理由和分类由 **处理流水线** 产出；字段缺失时显示为空态或隐藏
- 第一版 **内容浏览** 只展示成功进入内容存储的内容条目（当前状态为 `saved`），不提供状态分段筛选；失败和跳过结果归入 **采集记录** 排障

- **内容条目** 不直接保存 **关注主体** 归属
- **内容浏览** 统一读取 **内容条目**，不按 **采集意图** 建立独立内容池
- `collect_new_items` 新增显示为新的 **内容条目**

- 第一版 **内容浏览** 不提供内容条目详情页或详情抽屉；信息卡片标题直接打开原地址，卡片标题旁提供“保存到知识库”动作
- 内容卡片中的 **媒体预览** 参考 AIHOT 卡片顺序放在摘要下方、条目标签上方
- 内容卡片最小展示 **一级分类** 和可选 **二级分类**；有二级分类时显示为“一级分类 / 二级分类”，没有二级分类时只显示一级分类，没有处理结果或旧数据缺分类时不显示分类
- 第一版 **内容浏览** 不提供多图宫格、轮播或人工选择封面
- **内容浏览** 的内容卡片只消费本地 HTTP API 返回的 **媒体预览**，不在前端从正文或原始载荷中临时解析媒体链接

- 图片型 **媒体预览** 的 `preview_url` 缺失或加载失败时，内容卡片隐藏媒体区域
- 视频型 **媒体预览** 没有封面或封面加载失败时，内容卡片保留紧凑视频占位和播放标识
- 第一版 **内容浏览** 不内联播放视频；视频 **媒体预览** 只展示封面或占位和播放标识，点击后打开原地址

- 前端默认首页是 **内容浏览**，但 **内容浏览** 内部信息架构和阅读体验留到后续单独定义

- **信息源管理** 允许直接添加未归属 **信息源**，后续再归属到 **关注主体**
- **信息源管理** 编辑 **信息源** 归属时允许内联创建新的 **关注主体**
- **信息源管理** 添加或编辑时可以根据目标入口、默认采集通路和关键参数提示疑似重复，但不硬性阻止保存
- 当用户要关注关键词主题时，可以先创建 **关注主体**，再在该主体下添加多个搜索入口 **信息源**
- **信息源管理** 第一版实施范围只包括 **关注主体** 配置、**采集意图** 配置和按 **关注主体** 重组信息源管理体验
- **信息源管理** 第一版不实现 **信息提醒**、按 **关注主体** 的内容浏览筛选或按 **关注主体** 的 **处理规则**
- **信息源管理** 提供 **关注主体** 详情或展开视图，但第一版不要求独立路由
- **关注主体** 详情或展开视图承载主体名称、描述、**主体分组**、标签、其下 **信息源** 列表、添加信息源、批量启停和按主体采集入口
- **关注主体** 详情或展开视图不承载内容浏览列表或 **提醒策略**
- **关注主体** 编辑入口放在右侧 **关注主体** 折叠条或展开区域，编辑名称、**主体分组**、描述和标签
- 左侧 **主体分组** 导航只承载过滤和分组级操作，不直接编辑具体 **关注主体**
- **信息源管理** 包含信息源列表和独立的信息源详情页面；信息源详情承载单个 **信息源** 的配置、默认 **采集通路**、最近采集状态和操作入口
- 第一版 **信息源** 详情页面至少支持启停 **信息源**、配置 **扫描频率**、查看最近采集状态和触发 **立即采集**
- **信息源** 详情页面可以展示候选 **采集通路**、匹配原因和最近自检状态
- **信息源管理** 以 **关注主体** 为主要组织视角展示 **信息源**
- **关注主体** 不作为前端顶层导航，属于 **信息源管理** 内部组织视角
- **信息源管理** 中 **关注主体** 可以显示为可折叠条目，展开后显示其内部 **信息源**
- **关注主体** 折叠条可以展示主体名称、**主体分组**、信息源数量、派生启停状态、最近成功采集时间和错误摘要
- **关注主体** 折叠条上的运行状态和聚合状态均为派生信息，不写入 **关注主体格式**
- **关注主体** 展开后的 **信息源** 行展示信息源名称、平台或默认采集通路、**采集意图**、目标入口、**信息源分组**、标签、启用状态、最近采集状态和主要操作
- **关注主体** 展开后的 **信息源** 行不重复展示所属 **关注主体**
- **主体分组** 和 **信息源分组** 在 **信息源管理** 中作为辅助分类和筛选，不替代 **关注主体** 组织视角
- **信息源管理** 按 **主体分组** 筛选时筛选 **关注主体**
- **信息源管理** 按 **信息源分组** 筛选时筛选 **信息源** 行，并隐藏没有匹配信息源的 **关注主体** 折叠条
- **信息源管理** 搜索可以匹配 **关注主体** 或 **信息源**；匹配主体时显示该主体下信息源，匹配信息源时只显示匹配行
- 第一版 **信息源管理** 不在 **关注主体格式** 或 **信息源格式** 中保存手动排序字段
- 第一版 **信息源管理** 中 **关注主体** 和 **信息源** 使用前端稳定排序规则展示
- **信息源管理** 列表以 **信息源** 为主要行对象，不按静态页、列表、账号或公众号拆分页面
- **信息源管理** 列表展示 **采集意图**，并支持按 **采集意图** 筛选
- **信息源管理** 列表中的启用 **信息源** 行可以直接触发单源 **立即采集**
- 第一版 **信息源管理** 不提供硬删除 **信息源**；常规移除动作是归档，用户通过启用或停用控制未归档 **信息源** 是否参与采集，历史内容和采集记录继续保留
- **信息源管理** 列表支持选中多个启用 **信息源** 后触发批量 **采集运行**，执行时使用各 **信息源** 自身的 **采集意图**
- **信息源** 详情页面支持立即触发该 **信息源** 的 **采集运行**；`collect_all_items` 信息源触发前应展示分页范围和安全边界
- `collect_all_items` 信息源触发 **立即采集** 前应要求用户确认；`collect_new_items` 和 `track_page_change` 不需要确认
- **采集记录** 主要用于查看历史、事件和重跑既有 **采集运行**，不作为全部启用 **信息源** 的 **立即采集** 主入口
- **采集能力管理** 包含采集通路列表和独立的采集通路详情页面；采集通路详情承载 **通路自检**、**替代采集后端**、凭据引用、样例输入、关联 **信息源** 和按通路触发 **采集运行** 的入口
- **采集能力管理** 列表按 **采集通路** 分组展示，每个分组呈现该 **RouteChannel** 的状态、所属 **平台**、能力、默认 **RouteBackend**、替代 **RouteBackend** 和主要操作，暂不展示关联 **信息源** 摘要
- 第一版 **采集能力管理** 不提供添加 **采集通路** 的前端入口；新增 **采集通路** 先保留为配置文件或开发流程
- 第一版 **采集能力管理** 不提供启用或停用 **采集通路** 的前端操作
- 第一版 **采集能力管理** 展示 **替代采集后端**，但不提供切换默认 **RouteBackend** 的前端操作

- **采集运行** 不作为前端顶层导航，前端在 **设置** 中通过 **采集记录** 次级入口查看 **采集运行** 和 **采集运行事件**

- **处理规则** 页面第一版只允许启停全局 **处理流水线** 和固定步骤，不提供自由编排或单个 **信息源** 覆盖规则
- 第一版 **设置** 采用设置总览页加 **设置子页面**；**设置** 包含 **采集记录**、**处理规则**、**归档配置**、本地存储路径、配置同步和 **环境安装** 等 **设置子页面**
- **设置** 总览页的 **设置子页面** 顺序为 **处理规则**、配置同步、**归档配置**、**环境安装**、本地存储和 **采集记录**；**采集记录** 属于低频排障入口，不按日常高频入口排序
- **配置同步** 页面显示最近同步状态、配置文件变更和可解释错误，并提供手动立即同步入口；前端或 **本地应用服务** 启动时可以自动检查并同步配置
- **环境安装** 页面生成并展示 **安装计划**，用户确认后由 **本地应用服务** 执行本机工具安装或配置写入
- **本地存储** 页面第一版展示本地路径和存储状态，并允许用户配置 **知识库路径**；`config_dir`、`db_path` 和既有完整 Markdown 导出目录仍只读，不提供数据迁移能力
- **采集记录** 页面支持从单条 **采集运行** 重跑同一批 **信息源**，不在重跑入口编辑运行参数
- 前端产品体验应允许用户管理 **信息源**、检查 **采集通路**、配置或切换 **替代采集后端**、触发 **采集运行** 和进行 **内容浏览**
- **通路自检** 验证采集能力是否可用，但不绑定也不替代真实 **信息源**
- **原文锚点源** 是 **信息源** 的筛选子类；第一批国际/政策源优先建立低噪声原文基准，不承担新闻雷达或舆情监测职责
- **解释分析补充源** 可以少量伴随 **原文锚点源** 进入第一批，但只用于结构理解和风险框架，不替代事实、政策、法律或官方立场的原文基准
- **国际事实报道补充源** 是独立于第一批 **原文锚点源** 的补充层，用于事实基线交叉验证、背景入口、地区视角和市场影响线索；涉及正式立场、法律文件、制裁名单、国际组织记录时仍回到 **原文锚点源**
- 同一 **国际事实报道补充源** 层可以保留多个角色互补的媒体源，例如 FT 和 Bloomberg 同时覆盖地缘经济、政策影响、市场和公司新闻，但仍应作为独立 **信息源** 观察信息量
- 第一批国内政策 **原文锚点源** 聚焦 **国家产业政策主线**；陕西、西安、教育考试、人社招聘和公共资源交易等地方或事务入口属于后续批次，不混入第一批政策基准流
- 第一批 **原文锚点源** 默认每个机构只选择一个代表入口；只有用户明确高关注的机构或议题，才拆成多个同机构入口
- 高频人道危机、灾害和地区冲突聚合源属于后续专题过滤源，不默认进入第一批国际 **原文锚点源**
- 第一批新增 **原文锚点源** 默认不启用 **定时采集**；先通过单源或当前分组 **立即采集** 观察信息量和处理质量，再决定是否配置 24 小时等 **扫描频率**
- 第一批国际/政策补源先登记已验证可解析的 RSS/Atom 入口；没有稳定 RSS/Atom 的来源不强行用网页列表或 JSON 入口替代，留到后续专项处理

## Flagged ambiguities

- “量子位”曾可能通过假聚合 Feed、FOLO List 特化或新增关注主体来聚合公众号与 Bilibili 内容； resolved: FOLO 融合首期暂不实现跨平台主体聚合，也不引入上述替代模型。
- “归档”曾可能被视为 FOLO 融合的首期必需能力； resolved: 当前融合阶段暂不提供配置归档与恢复，后续有明确误删恢复需求时再设计。
- “基于 FOLO”曾可能表示继续以 FOLO 官方云作为业务权威服务； resolved: 当前选择以 **自有权威服务** 为主，FOLO 官方 API 仅通过 **FOLO 官方能力适配器** 按需复用。
- `feed_supplier` 曾被纳入本轮 FOLO 融合方案； resolved: 当前先不讨论它，后续仅把它作为新的 RSS 发布器应用接入。
- **处理结果** 可能是 Entry 的全局属性，也可能因应用所有者、用户画像或 Taxonomy 不同而属于用户个性化数据； resolved: 它属于应用所有者的个性化数据，首期单人部署不增加固定 `user_id`，未来多用户化时显式迁移。
- 使用 FOLO 官方 RSSHub 集群和托管轮询可能要求创建 **官方影子订阅** 并让官方保存对应 Feed 与 Entry； resolved: 允许在单个 Feed 获得 **官方获取授权** 后创建，不上传其他本地订阅、阅读状态或处理结果。
- 本地取消订阅、切换获取提供方或撤销 **官方获取授权** 后，应立即删除官方影子订阅，还是保留一段时间便于恢复； resolved: 立即停止使用并进入七天 **影子订阅待删除期**，到期后自动删除，既有本地 Entry 保留。
- 创建官方影子订阅应阻塞本地订阅保存，还是先保存本地订阅再由后台异步建立； resolved: 先保存本地订阅，后台异步建立 **官方获取连接**，失败不回滚本地主数据。
- **官方获取连接** 多次失败后，应自动切换到已配置的自建 RSSHub 等候选提供方，还是等待用户手动选择； resolved: 仅自动切换到用户预先配置的候选提供方，降级后不自动切回官方。
- 哪些错误和失败次数应触发 **获取提供方降级**； resolved: 不可重试能力拒绝立即降级；暂时故障连续三次且跨至少三十分钟后降级；授权失效给予二十四小时恢复窗口。
- 在官方 RSSHub 与自建 RSSHub 之间切换时，如何识别并消除同一条内容的重复 Entry； resolved: 本地订阅身份不变，重叠拉取最近七天，按 GUID 或 canonical URL 与发布时间确认重复，弱信号只生成候选。
- 确认是同一 Entry 后，如果新提供方返回更完整但不同的标题、正文或媒体，是否允许覆盖既有不可变 Entry； resolved: 只补齐空字段并记录来源，非空冲突保留首次导入值并写入诊断元数据。
- Feed 获取提供方、降级状态、影子订阅和重复候选等运维细节，在 FOLO 前端应默认直接展示，还是只在异常和设置详情中渐进披露； resolved: 正常状态只显示轻量来源标签，异常显著展示，底层细节进入订阅详情的 **获取诊断**。
- 用户从 RSSHub 发现页选择路由时，默认获取提供方应是直接/自建 RSSHub，还是 FOLO 官方托管获取； resolved: 自建 RSSHub 优先；仅在无自建实例且已关联官方账号时推荐官方，并逐 Feed 确认授权；无提供方时也可先保存本地订阅。

- “主体分组”曾可能被建成独立配置对象； resolved: **主体分组** 是 **关注主体** 上的自由字符串，增删改通过批量修改 **关注主体** 的 `group` 值完成。
- “主体分组 API”曾可能被设计成完整 CRUD； resolved: **主体分组** 不是独立资源对象，只提供重命名和删除等动作型资源来批量修改 **关注主体** 的 `group` 字段。
- “重命名主体分组”曾可能在目标名称已存在时报错； resolved: 允许确认后合并到既有 **主体分组**。
- “删除主体分组”曾可能被理解为删除或归档分组下对象； resolved: 删除 **主体分组** 只清空分组下 **关注主体** 的 `group` 字段，不删除、归档或停用任何对象。
- “静态页、列表、账号、公众号”曾可能被建成互斥的信息源类型； resolved: 第一版用 **采集意图** 区分“跟踪目标变化”和“获取新内容”，平台和账号形态留给 **平台**、**采集通路** 与 **信息源** 参数表达。
- “监测语义”曾可能被误认为恢复 **信息源** kind/category； resolved: 下架 **监测语义**，改用 **采集意图** 直接表达用户对 **信息源** 的原始采集目的。
- “静态页面里的列表”曾可能被建成新的信息源类型； resolved: 它是使用 `collect_new_items` 的 **列表页面**，通用列表抽取能力属于 **采集通路**，具体 **列表抽取参数** 属于 **信息源**。
- “列表详情抓取”曾可能引入单独的详情选择器配置； resolved: 第一版默认进入列表项链接抓取详情页面，不配置单独的详情抽取选择器。
- “scan.mode”曾可能被理解为独立于 **采集意图** 的新增、刷新或全量行为轴； resolved: 新配置不再保存 `scan.mode`，由 `intent.type` 表达跟踪目标变化、只采集新条目或采集本次发现的全部条目。
- “采集意图迁移”曾可能采用兼容期同时支持 `scan.semantics`、`scan.mode` 和 `intent.type`； resolved: 当前阶段采用立即强迁移，旧字段只允许作为一次性迁移输入，不作为同步、API 或前端的并行公共契约。
- “强迁移”曾可能被理解为必须人工改写所有旧 YAML； resolved: 可以提供一次性配置迁移工具读取旧字段并改写为 `intent.type`，但主同步和运行路径必须拒绝旧字段。
- “collect_new_items 的已知候选”曾可能被完全忽略； resolved: 已知 **条目候选** 不做 **完整内容采集**，但应更新 **内容索引** 的再次看到状态并记录已看到事件。
- “collect_all_items 的已知候选”曾可能被理解为需要重新抓取详情并刷新内容； resolved: `collect_all_items` 只扩大 **条目发现** 范围，已知 **条目候选** 同样只更新再次看到状态，不做 **完整内容采集** 或内容指纹比较。
- “collect_all_items”曾可能被理解为绕过所有去重； resolved: 它表达扩大 **条目发现** 范围并跨分页获取候选，已知候选预检查和 **标准采集结果** 持久化仍执行各自去重。
- “已知条目预检查”曾可能被当作 `collect_new_items` 和 `collect_all_items` 的主要差异； resolved: 二者主要差异是 **条目发现** 范围和是否跨分页获取候选，已知候选预检查是列表型采集意图的共同前置步骤。
- “max_items”曾可能被理解为每页候选上限； resolved: `scan.limits.max_items` 是单次采集的候选总上限，`collect_all_items` 跨分页累计计数。
- “下一页识别”曾可能被要求每个 **信息源** 都配置； resolved: **分页识别规则** 默认由 **采集通路** 提供，单个 **信息源** 只在特殊页面需要时用 `params` 覆盖。

- “分页失败事件”曾可能复用 `item_failed` 或 `source_failed`； resolved: 分页失败事件类型为 `pagination_failed`，没有 `item_id`，也不表示整个 **信息源** 失败。
- “条目候选”曾可能被理解为必须包含详情入口； resolved: **条目候选** 最小只要求稳定身份，只有保存为 **内容条目** 时才必须在同次采集中得到完整 **原始内容**。
- “条目候选身份”曾可能使用内容哈希兜底； resolved: `collect_new_items` 和 `collect_all_items` 的 **条目候选** 必须有平台外部 ID 或规范化 URL，内容哈希只作为 **原始内容版本** 的指纹，不作为候选身份。
- “详情 canonical 身份”曾可能被用于替换已经生成的 **内容条目 ID**； resolved: 详情采集发现的 canonical URL 或平台 ID 记录为 **内容身份别名**，参与后续预检查和重复判断，但不重写主 ID。
- “内容条目的 url 字段”曾可能被当作身份判定来源； resolved: `items.url` 只表达用户打开用的主 URL，身份判定和去重统一使用 **内容身份别名**。
- “track_page_change 的内容身份别名”曾可能记录 canonical 或 final URL； resolved: `track_page_change` 只把 **信息源** `target` 作为 `url` 身份写入 `item_identities`，页面变化仍由内容指纹判断。
- “URL 身份类型”曾可能被理解为互相隔离的唯一维度； resolved: `url`、`canonical_url` 和 `final_url` 共享 `source_id + normalized_value` 唯一身份，`identity_type` 只表达来源。
- “身份冲突”曾可能被自动合并； resolved: 第一版只在创建前复用已命中的既有 **内容条目**，已经存在两个 **内容条目** 后发现重复时记录 `identity_conflict`，不自动合并。
- “晚到身份命中”曾可能因为已经抓到详情而写入新 **原始内容版本**； resolved: `collect_new_items` 和 `collect_all_items` 详情采集后才命中既有身份时，丢弃本次 **原始内容**，记录 `item_seen` 成功事件并按已知候选更新再次看到状态。
- “身份规范化”曾可能被理解为激进 URL 清洗； resolved: 第一版只做最小稳定规范化，保留非跟踪 query 参数，`external_id` 只 trim 且不改大小写。
- “采集全部条目”曾可能被理解为重爬某个 **信息源** 历史上的全部 **内容条目**； resolved: `collect_all_items` 只采集从目标入口和分页入口可达的 **条目候选**，候选未出现不表示删除。
- “generic-web-list 用 Jina Reader 抓详情”曾可能被理解为直接绑定 `jina-reader` **采集后端**； resolved: `generic-web-list` 默认委托 `generic-web` **采集通路** 做 **完整内容采集**，具体 **采集后端** 由 `generic-web` 决定。
- “页面局部监测”曾可能和列表抽取混在一起； resolved: **快照抽取参数** 只影响 `track_page_change` 的内容和指纹输入，仍然只产生一个 **内容条目**。
- “target”曾可能保存采集后端的专用参数； resolved: **信息源格式** 中的 `target` 保存用户可识别的稳定入口，专用采集参数保存在 `params`。
- “capability”曾可能被改成列表以承载多个采集能力； resolved: 一个 **采集通路** 只表达一个主要采集能力，意图兼容性通过 capability 元数据表达。
- “标准采集结果”曾可能携带 **监测语义**； resolved: **采集意图** 属于 **信息源**，由 **统一采集执行** 读取，不由 **采集后端** 返回。
- “页面快照 ID”曾可能被复用为每次页面变化的 Feed 条目身份； resolved: **页面观测快照** 只作为采集供给端的比较状态，每次确认变化都生成新的 **页面变化消息** 和新的 Feed 条目身份。
- “重复信息源”曾可能被后端硬性禁止； resolved: 当前配置层允许重复 **信息源**，前端只做疑似重复提示。
- “页面更新提醒”曾可能更新同一个 Feed 条目或创建新的核心内容版本； resolved: `track_page_change` 每次确认变化都由采集供给端发布新的 **页面变化消息**，信息流核心不保存同一 Feed 条目的内容版本。
- “提醒”曾可能被塞进 **内容条目** 或 **采集运行事件**； resolved: 值得打扰用户的通知事实称为 **信息提醒**，独立于内容事实和运行记录。
- “全部信息流”曾可能被理解为只展示 **内容条目**； resolved: **全部信息流** 是默认时间线视图，可以混排 **内容条目** 对应的内容卡片和 **平台行为** 对应的 **行为卡片**，但二者底层语义独立。
- “新收藏/新关注产生内容卡片”曾可能被理解为创建普通 **内容条目**； resolved: 新收藏或新关注这类用户动作产生 **行为卡片**，外观可混排到 **全部信息流**，但不进入 **内容条目** 语义。
- “行为卡片”曾可能被理解为一条平台行为只能生成一张卡片； resolved: 第一版 Bilibili 新关注按一次 **平台行为同步** 合并为 **关注合并行为卡片**，Bilibili 新收藏视频按单个视频生成 **收藏视频行为卡片**。
- “行为卡片保存”曾可能被理解为复用内容条目的 **清洗正文保存** 或必须等待 AI 处理； resolved: **行为卡片保存** 保存平台行为和 **对象快照**，不要求 **完整内容采集** 或 AI **处理结果**。
- “收藏视频行为卡片像内容卡片”曾可能只被实现为 UI 相似； resolved: 收藏视频信息足够时应通过 **收藏内容条目化** 成为真正 **内容条目**，进入 **内容存储**、AI **处理流水线** 和普通 **保存到知识库** 语义。
- “AI 后处理失败”和“采集失败”曾可能混在一起； resolved: AI 后处理失败只表示当前 **原始内容版本** 没有形成完整 **处理结果**，不代表信息源采集失败。
- “AI 后处理是否卡住”曾可能由前端按轮询时间自行猜测； resolved: **处理状态** 由 **本地应用服务** 返回，前端只展示后端状态和失败统计。
- “顶层 AI 后处理通知关闭”曾可能被理解为停止后台处理； resolved: 关闭只隐藏当前 **处理状态提示**，不改变后端 **处理触发**、处理作业或 **处理失败** 记录。
- “关闭后的顶层 AI 通知”曾可能对后续失败永久静默； resolved: 失败数量增加或失败清零后，前端会重置本地关闭状态，使新失败可以重新提示。
- “查看失败项”曾可能被理解为跳到单独页面或偷偷改筛选； resolved: 它在当前阅读页显式应用 **处理异常筛选**，并显示可一键清除的筛选标记。
- “失败原因”曾可能直接把底层 stderr 或退出细节抛给前端； resolved: 当前阶段只展示简短 **处理异常原因摘要**，底层输出仍留在日志或诊断层。
- “重处理”曾可能顺带重新采集信息源； resolved: 当前阶段单条 **重处理** 只重新入队该条目当前 **原始内容版本**，不触发重新采集。
- “单条重处理”曾可能额外拉起一套独立处理流程； resolved: 单条 **重处理** 只重新入队并触发现有 **处理触发** 协调器消费。
- “当前视图里的失败项”曾可能只按已加载卡片理解； resolved: **批量重处理** 作用于当前已应用阅读视图条件下的完整匹配结果集。
- “批量重处理”曾可能点下即执行、用户看不到成本边界； resolved: 执行前必须预览并确认失败条目数，同时说明“不重新采集”。
- “批量重处理确认时的临时筛选输入”曾可能被当作当前视图； resolved: 当前视图以已应用筛选为准，不使用尚未提交的筛选草稿。
- “批量重处理执行结果”曾可能只说成功或失败； resolved: 结果应区分候选条目数、实际重新入队数和跳过数。
- “收藏内容条目化”曾可能等待封面、作者、简介或统计字段齐全； resolved: 第一版最小条件只要求平台、视频 ID 或 BV 号、标题和视频链接，其他字段能填则填，缺失不阻塞。
- “新关注 UP 主”曾可能被当作可条目化内容； resolved: **关注合并行为卡片** 保持纯 **平台行为** 记录，新关注对象可以成为后续信息源或关注主体候选，但第一版不生成普通 **内容条目**。
- “Bilibili 关注/收藏”曾可能被建成普通 **信息源**； resolved: 第一版由独立的 **平台行为同步** 读取 **平台状态快照** 并生成 **平台行为**，不进入 **信息源管理** 或 **采集运行** 统计。
- “平台行为主存储”曾可能被放进 PersonalOS 平台资产暂存； resolved: 第一版运行时主存储放在 Feeds Agent SQLite，PersonalOS 只作为可选导出或长期归档位置。
- “平台行为同步”曾可能被自动接入 **调度器**； resolved: 第一版只提供用户手动触发，不做自动定时同步。
- “收集个人行为”曾可能复用 **立即采集**； resolved: **收集个人行为** 是独立产品动作，触发 **平台行为同步**，不计入 **采集运行** 或信息源采集统计。
- “收集全部信息源”曾可能被理解为 `collect_all_items` 的 **采集全部候选**； resolved: **收集全部信息源** 是阅读页上的全局动作，触发全部启用 **信息源** 的 **立即采集**。
- “收集个人行为”曾可能只放在 **全部信息流**； resolved: **全部信息流** 和 **精选** 页面都提供 **收集个人行为** 与 **收集全部信息源** 两个全局动作。

- “提醒策略”曾可能进入 **信息源格式** 或形成新的 AI 流程概念； resolved: 当前阶段暂不设计提醒策略，后续作为 **处理流水线** 的扩展讨论。

## External References

Agent-Reach is a reference for **RouteChannel** diagnostics and CLI backend checks. Feeds Agent adopts the idea that each channel owns availability checks and can wrap one or more backends, but does not fork Agent-Reach or reuse its Channel abstraction directly.

## Shared formats

### 配置文件组织

```text
config/
  subjects/
    openai.yaml
    some-blogger.yaml
  sources/
    openai-blog.yaml
    supplier-bilibili-some-up.yaml
  supplier/
    sources/
      bilibili-some-up.yaml
    routes/
      bilibili-search.yaml
  processing.yaml
```

配置文件按服务与对象类型分目录，并采用单对象一个 YAML 文件；YAML 是静态配置主存储，SQLite 保存各服务独立的运行状态。
除 `processing.yaml` 外，配置文件 basename 必须等于 YAML 内的 `id`。
`processing.yaml` 是 Feed Core 的单例全局处理配置，不使用 **配置对象 ID**。

### 运行产物组织

```text
data/
  core/
    feeds.sqlite
    generated-skills/
      feed-core-process/
        SKILL.md
  supplier/
    feeds.sqlite
    credentials/
  legacy/
    feeds.sqlite
```

`data/core/` 保存 Feed Core 的内容、版本、处理和订阅状态；`data/supplier/` 保存 Feed Supplier 的采集状态、物化 Feed 数据和凭据文件。两个目录不得作为同一可写卷挂载。旧单体数据库只读归档在 `data/legacy/feeds.sqlite`，两个新服务均不读取它。

```yaml
      subcategories: [职场运营, 项目职称]
    - name: 政治社会
      subcategories: [时政社会]
    - name: 国际局势
      subcategories: [全球形势]
    - name: 兴趣爱好
      subcategories: [摄影, 音乐, 舞蹈, 影视, 电影, 设计艺术, 时尚穿搭]

    - name: 自我管理

```

`user_profile_document` 保存 **用户画像文档** 的本地 Markdown 路径，用于生成 AI 处理 skill 时提供用户背景。
`pipeline.enabled` 只保存 **处理流水线** 是否运行；处理结果中的评分、摘要、分类和标签字段属于完整 **处理结果** 契约，不再用半生效的固定步骤开关表达。
`taxonomy.categories` 保存 **分类规则配置**；`name` 是允许的 **一级分类**，`subcategories` 是该一级分类下允许的 **二级分类**。
缺少 `taxonomy` 时读取层使用内置默认正式分类表，避免旧配置或新安装缺少分类规则导致 AI prompt 和回填校验失效。
保存 `taxonomy.categories` 时必须拒绝空分类表、空分类名称和同级重复名称。

### SQLite 最小表集合

- `sources`: 保存 **信息源格式**
- `routes`: 保存 **采集通路配置格式**
- `route_backends`: 保存 **RouteBackend** 配置快照
- `route_checks`: 保存 **通路自检结果**
- `source_routes`: 保存 **信息源** 与候选 **采集通路** 的匹配结果、默认通路和 **扫描进度**
- `items`: 保存 **内容索引**
- `item_identities`: 保存 **内容身份别名**
- `content_versions`: 保存 **原始内容版本** 的载荷、指纹和版本元数据
- `item_processing_results`: 保存绑定到 **原始内容版本** 的 **处理结果**
- `runs`: 保存 **采集运行**
- `run_events`: 保存 **采集运行事件**

SQLite 最小 schema 记录在 `docs/schema.sql`。
YAML 配置可通过 `scripts/sync_config.py` 同步到 SQLite 配置快照表；该同步默认不删除缺失的历史配置快照。
热榜和趋势观察历史暂不进入最小表集合；后续需要时再增加类似 `item_observations` 的通用观察表，记录位置、热度信号和采集运行。

### 处理批次最小格式

```yaml
processing_batch:
  status: ok | done
  message: null
  items:
    - item_id: item_id
      content_version: 1
      content_fingerprint: content_fingerprint
      title: title
      url: null
      source_name: source_name
      published_at: null
      collected_at: "..."
      content: "有长度上限的正文"
      content_truncated: false
      content_char_count: 0
```

`status: done` 表示没有新的 **待处理条目**，此时 `items` 为空；`message` 可提供给 AI 读取的结束说明，但不作为处理循环判断条件；`content` 来自 **原始内容版本** 的可读正文并受长度上限约束，默认每条最多 12000 字符；`content_truncated` 和 `content_char_count` 用于说明正文是否被截断；第一版 **处理批次** 不向 AI 提供图片或视频内容。
**处理批次** 的返回规模由可配置的批次限制策略决定。默认自适应窗口在提示词固定开销与正文规模达到目标比例后尽早返回，同时受 60000 正文字符、100 条硬上限、8 秒最长等待和 1.5 秒静默期保护；固定字符预算与固定条数模式继续兼容已有配置。
**处理批次** 默认按时间倒序读取 **待处理条目**：优先使用发布时间，其次使用采集时间，并用 **内容条目 ID** 保持稳定排序。

### 处理结果最小格式

```yaml
processing_result:
  item_id: item_id
  content_version: 1
  content_fingerprint: content_fingerprint
  importance_score: 0
  timeliness_score: 0
  relevance_score: 0
  overall_score: 0
  ai_published_at: null
  primary_category: 智能科技
  secondary_category: AI与编程
  summary: "约 100 字中文摘要"
  reason: "一句话推荐理由"
  tags: []
  skill_version: skill_version
  profile_hash: profile_hash
  taxonomy_hash: taxonomy_hash
  processed_at: "..."
```

`item_id`、`content_version` 和 `content_fingerprint` 标识该 **处理结果** 对应的 **原始内容版本**；`importance_score`、`timeliness_score` 和 `relevance_score` 是 AI 回填的三维评分；`overall_score` 由 **处理流水线** 根据三维评分计算；`ai_published_at` 是 AI 从正文识别出的发布时间，保存为 ISO 8601 字符串，无法识别时为空；`primary_category` 是唯一必填 **一级分类**；`secondary_category` 是可选 **二级分类**；`summary` 应为中文摘要，通常约 100 字，特长内容可到约 200 字；`reason` 应为一句话；`tags` 是 AI 自动生成的 **评估标签**；`skill_version`、`profile_hash` 和 `taxonomy_hash` 分别记录处理契约、用户画像和分类规则快照；`processed_at` 表示处理结果保存时间。该格式属于 SQLite **处理结果** 主存储，主键为 `item_id` 和 `content_version`；分类相关列允许为空仅用于旧数据兼容。

### 处理结果回填请求最小格式

```yaml
processing_result_write_request:
  results:
    - item_id: item_id
      content_version: 1
      content_fingerprint: content_fingerprint
      importance_score: 0
      timeliness_score: 0
      relevance_score: 0
      ai_published_at: null
      primary_category: 智能科技
      secondary_category: AI与编程
      summary: "约 100 字中文摘要"
      reason: "一句话推荐理由"
      tags: []
```

AI 处理 skill 通过对象顶层的 `results` 数组回填 **处理结果**；`overall_score`、`skill_version`、`profile_hash`、`taxonomy_hash` 和 `processed_at` 由 **处理流水线** 保存时生成或补齐，不要求 AI 回填。

### 处理结果回填响应最小格式

```yaml
processing_result_write:
  status: succeeded | partial | failed
  accepted: 0
  rejected: 0
  results:
    - item_id: item_id
      content_version: 1
      status: accepted | rejected
      reason: null
```

`accepted` 和 `rejected` 统计同批 **处理结果** 的逐条回填结果；`reason` 仅在单条 **处理结果** 被拒绝时说明原因。
